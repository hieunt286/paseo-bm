## 1. Context

Paseo (paseo.sh) has had an official plugin API since 0.8. The owner works through a PRD → plan → beads process, built on the beads CLI (`br`/`bd`/`bv`), the reporting tool `bva` and a set of agent skills. The goal of the `paseo-bm` repo (**BM = Beads Management**) is to bring this beads management into Paseo as an *"Agents Bead Reporter / Tracker / Implementation"* plugin.

### 1.1 Core value: orchestration, not just installation

Without paseo-bm, turning a feature request into workable beads means running the whole chain by hand: read the request, decide which documents are needed, write or edit the PRD/design/plan, convert it into beads, then ask another agent to review the documents and the beads — over many hours, and wholly dependent on whether the person driving it remembers every step.

**This product automates that chain.** After install, Paseo gains a **Beads Manager** — itself **an agent**, not a screen. The user chats with Manager as with any other agent; Manager takes the request and **hands it straight** to a **Beads Worker** in the same workspace. Manager keeps the managing role: it tracks progress, keeps control, and answers when the user asks about the state of the running agents — it uses Paseo's own tools to do that. Worker sizes the request and uses only the process that size needs (REQ-022, REQ-036): a small change is done and proved directly; larger work gets beads — new ones, **or** updates to existing unfinished beads the request already falls within — documents where they are needed, and a review by a sub-agent (REQ-024), **and Worker carries on until the implementation is done**. There is no hard limit on time or number of steps: whenever it gets stuck, Worker asks the user and then carries on.

The installation is therefore **not the product**; it is the path that brings the capability above to the user's machine. The two parts are described in the same PRD because they only make sense together: an install without Manager is used by no one, and a Manager that cannot be installed is reached by no one. That path is the plugin itself ([ADR-012](../adr/ADR-012-plugin-is-the-product.md); up to 0.3.1 it was the `npx paseo-bm` installer), installed from paseo.cafe or with Paseo's plugin install command: the plugin creates the roles by itself, the steps that need the user's consent are on Setup, and Paseo takes care of updates. The four problems below are why the product has an installation part.

**Problems of the installation part:** without it, bringing this plugin onto another machine takes many error-prone manual steps:

1. Get the plugin code, put it in a fixed folder, run the command that registers the plugin with the daemon.
2. Know that Paseo **disables** plugins by default (`pluginsEnabled` in `config.json`), enable it yourself and then reload the daemon. If you forget, the plugin "does not show up" without any clear error.
3. When a new version comes out, repeat everything; no way to know which files were edited by hand; no way to uninstall cleanly.
4. The plugin works best when the machine already has the set of bead skills for agents, but new users usually do not know that, nor where to install them.

**Settled boundary on skills:** paseo-bm **does not copy, edit or delete skills files by itself**. Ownership of skills belongs to the user and to the official skills installer. But paseo-bm **does help**: when it detects that the machine does not have enough skills, it offers to run the official skills installer on the user's behalf from the recommended source (`github.com/cuongntr/agent-skills`, another author's repo — [Appendix A](#12-appendix-a--survey-of-the-recommended-skills-source)) after the user's explicit consent. This spares new users from figuring it out alone, while keeping the principle intact: every skills file on the machine is managed by the skills installer, not by paseo-bm. It is also how the biggest risk is avoided: on the owner's machine, 5 bead skills are managed by `npx skills` in `~/.agents/skills` and symlinked into `~/.claude/skills`; if paseo-bm copied same-named skills in there itself, it would overwrite another tool's copies.

### 1.1 Lessons from paseo-room

paseo-bm was designed against [paseo-room](https://github.com/cuongntr/paseo-room), the "one `npx` command to set up Paseo" model. Its install-flow lessons (preview before writing, a confirmation that defaults to "No", idempotent re-runs, an install record, backups of edited files) applied to the 0.3.x installer and are in git history; since 0.4.0 Paseo downloads and keeps the package, and paseo-bm has no payload on disk to protect. The lessons that remain: write only inside its own folder and its own part of the Paseo configuration; remove only what it owns and never touch credentials (paseo-room's uninstall deleted its whole folder, credentials included); ask for consent before opening permissions; use Paseo's own plugin management; keep the macOS/Linux scope and test the packed package itself.

## 3. Out of scope

- **Copying, editing or deleting skills files by itself.** paseo-bm only detects, guides and (with consent) calls the official skills installer to do that — see REQ-007.
- Owning or maintaining the content of the skill set: that is another author's repo (`cuongntr/agent-skills`).
- Installing Paseo, Node.js, the beads CLI (`br`/`bd`/`bv`), Claude Code, Codex; signing in to providers.
- **Merging, committing or creating pull requests by itself.** Worker writes code but does **not** touch git; the user looks at `git diff` and decides (amended by the autonomy PRD: effectful actions only through the owner's policy or a one-use grant, its REQ-112, REQ-141).
- **A bead progress report board in Paseo:** owned by the [Dashboard PRD](./paseo-bm-dashboard-prd.md), not this one.
- **Guessing intent from every chat message.** Manager takes on work only when the user hands it over explicitly; the plugin does not silently read and interpret every message in the chat.
- Remote daemons (`--host`), Docker.
- **Paseo 0.8.** Paseo 0.8 users keep release 0.3.1 or upgrade Paseo.
- **Turning on Paseo's global plugin switch (`pluginsEnabled`).** That switch belongs to Paseo and the user; a plugin that is not running cannot do anything.
- Native Windows. WSL may work like Linux but is not tested.
- Per-role credential isolation in the paseo-room style (separate home folders, separate sign-in sessions). paseo-bm **does** register providers and agent profiles (REQ-031), but only as derived entries that reuse the existing sign-in sessions.
- Managing plugins, providers, profiles created by other tools or by the user.
- Silent self-updates, notices that a new version is out.
- Telemetry.

## 4. Personas / Affected Actors

- **Individual Paseo operator (owner)**
  - *Context:* uses Paseo desktop with Claude Code/Codex daily, following the PRD → plan → beads process, on several machines (personal, work).
  - *Goal:* rebuild the environment quickly and keep the plugin version in sync across machines.
  - *Pain:* skills are already managed by another tool, so they do not want any tool touching them on its own; forgetting to enable `pluginsEnabled` means the plugin silently does not run.
- **A colleague the toolkit is shared with**
  - *Context:* has Paseo installed, is not familiar with the `~/.paseo` structure, has never heard of beads skills.
  - *Goal:* one command and done, skills included, without having to go and find the repo.
  - *Pain:* does not want to break a working Paseo configuration; needs to know in advance what will change and to be able to remove it.
- **Release maintainer** (the owner in a different role)
  - *Context:* releases new versions of the plugin.
  - *Goal:* users update with one command; bug reports come with enough diagnostic information.
  - *Pain:* does not know which version the user's machine is running, or whether it has all the skills.
- **Automated bootstrap script** (dotfiles, new machine setup; a non-interactive actor)
  - *Needs:* runs without prompts, clear exit codes, machine-readable output, and an explicit decision on whether skills installation is allowed.
  - *Since 0.4.0 (ADR-012):* no separate path. The script uses Paseo's plugin install command; the steps that need consent (agent tools, skills) still have to be clicked on Setup, because a flag is not consent.
- **The person handing over work** (the owner and colleagues themselves, but in a different role once installed)
  - *Context:* has a repo's workspace open in Paseo and comes up with a feature request or something to fix.
  - *Goal:* describe the request in words and get back workable beads, without having to remember every step of feature-workflow or open each skill by hand.
  - *Pain:* doing it by hand takes hours and often skips the review step; but handing it to an unconstrained agent means it usually jumps straight into writing code, skips the documents, and creates beads that duplicate what already exists.

**Non-human actors:**

- **Beads Worker** — an agent created by Manager, running in the same workspace, responsible for the whole chain from analysing the request until there are beads.
- **Reviewer** — a sub-agent created by Worker, which only reads and comments on the documents or beads that Worker has just touched.

## 5. User / Operational Journeys

Journeys J-1 → J-5 and J-8 describe the install from paseo.cafe (since 0.4.0, ADR-012); up to 0.3.1 they went through the `npx paseo-bm` installer (git history).

- **J-1 First install on a bare machine:**
  1. The colleague opens paseo.cafe, picks paseo-bm and installs it (or types `paseo plugin add npm:paseo-bm-plugin`). If Paseo's plugin switch is off, Paseo says so itself; turning it on is the user's job in Paseo.
  2. The plugin runs. The colleague opens Beads Manager: the three roles have been created with the default provider and model; the Setup screen says so and points to where to change them.
  3. Setup lists what is still missing: Paseo tools for agents are off, Claude Code and Codex have no skills yet, `bv` is not installed, Codex is not signed in (with Codex's own sign-in command).
  4. The colleague clicks "allow agent tools", reads the warning that the switch applies to every agent on the machine, and consents.
  5. The colleague clicks "install skills", sees **exactly the command that will run**, the source `cuongntr/agent-skills` and the note that it is a third-party tool, then consents; Setup runs the command, shows the result and detects again.
  6. The colleague installs `bv` with the provided button, and runs the Codex sign-in command in a terminal themselves. Setup has nothing missing any more.
- **J-2 Update:**
  1. The maintainer releases a new version; the owner runs Paseo's plugin update command (`paseo plugin update paseo-bm`).
  2. Paseo downloads the new version and reloads the plugin. The roles, every value the owner set on them, the fallback chains and the history remain intact.
- **J-3 Diagnosis:**
  1. Beads Manager cannot create a Worker; the owner opens Setup.
  2. Setup reports "Paseo tools for agents are off" with a button to turn them on, and "2 required skills missing for Codex" with an install button.
  3. The plugin shows nothing in Paseo → the README points to `paseo plugin ls` and `paseo plugin logs paseo-bm`.
- **J-4 Removal:**
  1. The colleague clicks "remove paseo-bm's settings" on Setup and reads the list of what will be deleted: the roles paseo-bm created in Paseo, and the agent-tools switch is given back because paseo-bm itself turned it on. Skills and `br`/`bv` are not on the list.
  2. The colleague confirms; a second question asks whether to delete paseo-bm's data (history, fallback settings) — kept by default.
  3. Setup shows Paseo's plugin remove command; the colleague runs it.
- **J-5 Non-interactive bootstrap:** *dropped from 0.4.0.* The script runs Paseo's plugin install command; the part that needs consent waits for the user to click on Setup (§4).
- **J-6 Handing over a new feature request (the product's main flow):**
  1. The owner has the repo's workspace open in Paseo, opens Beads Manager and **chats**: "add a monthly report export screen, with filtering by department".
  2. Manager does not do it itself but hands it over right away: it creates a Beads Worker in that workspace, passes on the request verbatim along with the repo context and the location of the beads store, then tells the owner which Worker is holding the work.
  3. Worker reads the request, compares it with the existing documents and beads, and concludes: this request touches the UI and a new data contract, so documents need to be added first.
  4. Worker writes the necessary documents following feature-workflow, then creates a sub-agent to review the documents. The review returns two blocking points; Worker fixes both.
  5. Worker converts the documents into beads, then creates a sub-agent to review the beads. The review points out one bead that holds two outcomes; Worker splits it.
  6. Midway Worker hits a point that needs a decision: the request touches a frozen document. It **stops and asks**. The owner chats directly with Worker to settle the direction, without having to go through Manager.
  7. Worker reports done. The owner asks Manager "how is it going" and Manager answers: which documents changed, which beads were just created, which beads are ready to work on.
  8. The owner reviews the result and decides whether to archive or delete the Worker. No agent deletes an agent by itself.
- **J-7 A request that duplicates work already in the beads store:**
  1. The owner hands over: "the report export needs a CSV format too".
  2. Worker finds an open bead about report export, which nobody has worked on yet.
  3. Instead of creating a new bead, Worker updates that bead and states the reason; if the scope grows beyond one outcome it splits it into child beads instead of duplicating.
  4. Manager reports: which bead was updated, no duplicate bead created.
- **J-8 First agent configuration:**
  1. On the first opening, paseo-bm creates the three roles with the first provider Paseo reports as usable and its first model, without asking.
  2. The owner opens Setup → Agents: changes the provider, model, thinking, mode of each role (REQ-064), sees the sign-in status of each provider with that tool's own sign-in command.
  3. Changes apply to agents created after saving; the next update does not touch them.
- **J-9 An existing user moves to the install from paseo.cafe:**
  1. The owner installed with `npx paseo-bm` earlier. npm reports that package as discontinued and points to the migration command.
  2. The owner runs the last `npx paseo-bm` release once: it recognises the old install, says it will remove the directory install and install the npm release of the same version, then asks.
  3. The owner consents; the new plugin runs, the roles, switches and history remain intact. If the npm release does not come up, the old one is reinstalled and the owner is told why.
  4. Later, an old `npx paseo-bm` still in the cache that is run by mistake stops without changing anything.

## 7. Non-Functional Requirements

- **Performance:** the machine status on Setup (REQ-011) shows in ≤ 5 seconds with a local daemon, including skills detection and sign-in status. The time the skills installer takes to run is not counted because it depends on the network and a third party.
- **Security:**
  - No `sudo` or administrator rights required; paseo-bm writes by itself only to the locations listed in the README.
  - For skills folders, paseo-bm has **read-only** access. The only change there comes from the skills installer the user has allowed to run.
  - **Running external commands:** runs only exactly the command shown to the user, only after the user clicks and confirms. Provider sign-in commands are never run on the user's behalf. The default skills source is a constant in the package, not taken from untrusted input. If changing the source is allowed, that source must be shown before running.
  - Never read, print or write credentials. A daemon password passed through an environment variable (if any) is masked in all output, JSON and logs included.
  - The data folder is readable/writable only by the account owner.
  - Downloading the package (by Paseo, or by `npx` for the migration command) **must not** change the system by itself; no package has install lifecycle scripts.
  - The plugin payload installs exactly the content of the package version the user chose. If the Technical Design needs to download extra code at install time (see Q-004), the reason is recorded in an ADR and the user is shown that source in the preview.
  - The npm package is published with provenance linked to the GitHub source code.
  - No telemetry (§3).
- **Reliability:** never leave the Paseo configuration in a state the daemon cannot load: every write paseo-bm makes to the configuration goes through the daemon, which checks it and reverts by itself on error; the migration command reinstalls the old release when the new one does not come up (REQ-070 c).
- **Compatibility:**
  - Operating systems: macOS, Linux. On native Windows, report unsupported and exit cleanly.
  - Paseo ≥ 0.9.0 (since 0.4.0; 0.3.1 needs ≥ 0.8.0).
  - Node ≥ 22 (Q-008).
- **Availability:** once Paseo has downloaded the package, the plugin runs entirely locally. Installing skills and `br`/`bv` **needs the network** and depends on GitHub, npm and third-party tools; without a network, the rest still works and Setup only warns.
- **Diagnosability:** every error has a stable message and code; Setup always has the paseo-bm version, the skills status, agent tools, sign-in and the path of the data folder.

**Non-functional requirements of the orchestration part:**

- **Cost and stopping points:** each request spawns at least three agent sessions (Worker plus the Reviewers). Worker must have clear stopping points instead of running forever: when the scope is done it stops, when stuck it asks the user rather than widening the work by itself. The user can cancel a Worker at any time, and cancelling must also stop its sub-agents.
- **Observability:** every action of Worker and Reviewer must be traceable from Paseo — the user can always see which agent is doing what and which files it has edited.
- **Permissions:** Worker and Reviewer run with the user's own permissions in that workspace. Worker runs in the provider's no-prompt mode; Reviewer runs in an automatic mode that opens neither full access nor network access (REQ-026c). Manager runs in no-prompt mode (REQ-026c) and does not approve other agents' permission requests by itself. Known risk: the safety boundaries of Manager and Worker live only in the role instructions; for Reviewer on Pi, and on OpenCode when the OpenCode agent the user picked does not restrict permissions, the read-only rule also lives only in the instructions.
- **Privacy:** the request content and source code go to the model provider the user chose for that role. paseo-bm sends data nowhere else and has no telemetry. The only exception: after recognising that a paseo-bm agent has hit its usage limit (REQ-065 i), the plugin asks the daemon to read the usage limits of the Claude or Codex plan; the daemon calls that provider's own usage-limit API with its sign-in session. paseo-bm does not see the credentials and sends no content.
- **Fault tolerance:** a Worker dying midway must not leave the documents or the beads store in a broken state; what has been written must be readable and Manager must state clearly where it stopped.
- **Determinism (to a reasonable degree):** the same request must not produce duplicate beads when run again; REQ-023 is the main mechanism that ensures this.

## 8. Boundaries & Dependencies

- **Depends on:**
  - Paseo desktop/daemon + CLI ≥ 0.9.0: the plugin API, the npm source and the plugin update command, the SDK's `config.patch`, Paseo's own `pluginsEnabled` switch.
  - The skills folder conventions of Claude Code, Codex and the shared folder `~/.agents/skills` — paseo-bm only **reads**.
  - The official skills installer (currently `npx skills`) — the party that makes every change in the skills folders.
  - The third-party skills repo: `https://github.com/cuongntr/agent-skills` (author `cuongntr`). Its content, skill names and availability are outside paseo-bm's control.
  - The npm registry (package `paseo-bm-plugin`; `paseo-bm` remains only for the migration command) and paseo.cafe; the GitHub repo `hieunt286/paseo-bm` (source code, releases).
  - The beads CLI (`br` or `bd`): **required** for the orchestration part, because Worker uses it to create and update beads. Still not required for the install alone.
  - **Paseo's agent creation capability** (daemon-side SDK): the foundation for the plugin to spawn Workers. If Paseo changes this contract, the orchestration part breaks.
  - **The agent providers the user chooses** (Claude, Codex, OpenCode…) along with their usage limits and sign-in state.
  - Pi's pi-mcp-adapter extension (third party, optional): without it, Pi agents have no Paseo tools.
  - **The feature-workflow skill set** on the machine: determines the quality of Worker's output.
- **Does NOT own:**
  - **The content and lifecycle of skills**: belong to the skills repo's author and the skills installer. paseo-bm does not maintain, fork or patch them.
  - **The model's reasoning quality and the cost of using the model**: paseo-bm picks the tool per the user's configuration and stops there.
  - **The final quality of the code**: Worker writes code and runs the repo's tests, but reviewing it and deciding to put it into git history remain the user's.
  - **Branch and git management**: Worker does not commit, push or merge.
  - The lifecycle of Paseo and the daemon. In `config.json`, paseo-bm touches only `daemon.mcp.injectIntoAgents` (when the user clicks) and the `bm-*` entries of `agents.providers` and `daemon.agentProfiles`; the plugin is the only writer (creating missing roles, saving on the REQ-064 screen, removing settings — ADR-008, ADR-012). Plugin registration and the `pluginsEnabled` switch belong to Paseo.
  - Plugins, providers, profiles created by other tools or by the user.
  - Beads data in projects; credentials and provider sign-in.
  - The plugin's business features (Reporter/Tracker/Implementation): a separate PRD.

## 12. Appendix A — Survey of the recommended skills source

[cuongntr/agent-skills](https://github.com/cuongntr/agent-skills), surveyed on 2026-09-14 (commit `efc5000`): each skill is a folder at the repo root containing a `SKILL.md`; no LICENSE, README, tag or version yet (Q-012, Q-013). Size figures and the full survey are in git history.

| Skill | Group | Role |
|---|---|---|
| `feature-workflow` | Required | End-to-end process by risk level: Intake → PRD → Design → Plan → Beads → feature closure |
| `reviewing-plan` | Required | Reviews and directly fixes an execution plan until it is fit to be converted into beads |
| `converting-plan-to-beads` | Required | Converts a plan into a hierarchical, dependency-aware bead graph, using `br`/`bd` |
| `polishing-beads` | Required | Audits the readiness of a bead graph: leaf size, correctness of dependencies |
| `implementing-beads` | Required | Picks a workable bead, executes it, accepts it per its DoD, closes the bead |
| `architecture-premise-audit` | Optional | Whole-project audit when the architecture style is suspected to be the wrong choice; used only when explicitly asked |
| `authoring-workspace-protocol` | Optional | Writes/edits a repo's `docs/WORKSPACE_PROTOCOL.md` |

The five required skills cover the whole beads lifecycle, so they are the list paseo-bm detects (REQ-007 b); the two optional ones are only suggested, and missing them raises no warning. Detection goes by folder name, because the source has no versions to compare (Q-013).
