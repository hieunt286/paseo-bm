## 0. Principles (from the PRD §3) and what they mean in code

1. **Artifacts, not conversation.** A handoff is a typed record with one identity; chat text is a view of it.
2. **Workflow before agent.** Routing, ordering, deduplication, limits, authority are code. A model is woken only for judgement.
3. **Control matches risk** through declared effects, the owner's policy and one-use grants — never through prose patterns alone.
4. **Measure before promoting.** Every phase exit runs the evaluation suite (Evaluation design §6) and the replay.
5. **Delete what is superseded** in the same phase (§A.14, and each Part's retirement list).

**One idea carries Parts A and B: agents keep writing typed blocks with side-effect-free tools (ADR-010), and the plugin materialises state from those blocks at the end of the turn that wrote them** — keyed idempotently, because Paseo reuses turn ids. The Orchestrator, whose endpoint knows its caller (the secret path), writes state directly. This keeps caller identity out of the Worker, Manager and Reviewer tools.

## Part A — Phase 1 MVP: one source of truth for decisions and handoffs

### A.1 Scope

Owns: the decision model and store; materialising decisions from blocks; answering and delivering; the Orchestrator's decision tools, prepared actions and grants; typed commands (`BM-COMMAND` v2) and authority from declared effects; fallback incidents as decisions; the event bus to the Orchestrator and the Inbox's alerts; bounded coordinator context; capability limits per role; the rewritten role instructions; the new management surface and card system; the Phase 1 retirement.

Does not own: decision classes, policy and delegation (Part B); evidence classification (Part C); holding actions before they run (Part D).

### A.2 Architecture

```
 Worker ── bm_report(blocked, questions+effects) ──► BM-REPORT + BM-QUESTIONS ── send_agent_prompt ──► Manager
                                                             │ Manager turn_ended
 Manager ── bm_answers after the owner's typed message ──────┤ (collector → decision materialiser)
 Owner types in a Worker's chat ─────────────────────────────┤ Worker turn_ended
 Fallback incident (usage limit, login, …) ──────────────────┤
 Orchestrator ── bm_ask_owner / bm_decisions (secret endpoint)┤ direct write
                                                             ▼
                              decisions store  <data>/decisions/<workspaceId>.json
                  ▲ decisions.answer (Inbox, chat cards)     │ delivery by the plugin (notice queue):
                  │                                          │   answers → Worker · prepared action → Manager/Worker/fallback
 Inbox · Work · chat cards (renderer) ◄── decisions.list/get ┘   · owner's words → Orchestrator (with a grant)
                                                             │
 events: decision.opened · request.finished · request.stalled · worker.signal
        └─► event bus ──► Orchestrator (one batched message per idle moment) · Inbox alerts
```

### A.3 The decision model

`plugin/shared/decisions.ts` (zod, shared by server and client):

| Field | Meaning |
|---|---|
| `id` | Deterministic key: `q:<requestId>:<Qn>` (Worker question), `o:<uuid>` (Orchestrator), `f:<incidentId>` (fallback) |
| `workspaceId`, `requestId` | `requestId` null only for fallback incidents outside a request and Orchestrator decisions about a whole project (a Worker question always has one) |
| `askedBy` | `{ role: worker \| orchestrator \| plugin, agentId \| null }` |
| `askedAt`, `round` | first-seen time; the Worker's report round (for grouping on one card) |
| `question`, `subject` | text (≤ 1,000); `subject` a short slug the asker gives (used by supersession now, by precedents in Part B) |
| `options[]` | `{ key, label, recommended, effects: Effect[], action?: PreparedAction }`; one recommended at most |
| `effects` | `none, commit, push, publish, deploy, real-data, migration, dependency-install, network, outside-workspace, security, cost` — declared by the asker per option |
| `status` | `open → answered \| superseded \| withdrawn \| expired`; `open → needs-confirmation` when an owner message in a chat may have answered it (A.5 c) |
| `answer` | `{ by: owner \| orchestrator \| policy \| precedent, via: inbox \| chat-card \| chat-manager \| chat-worker \| chat-orchestrator \| autopilot, optionKey \| words, at, reason?, class?, predictor?, precedentId? }` — `orchestrator` (`via: autopilot`, an option only, a `reason` ≤ 300 characters) from change-004 (A.6) until Phase 2: stored ones are still read, but `answerDecision` refuses a new `by: orchestrator` answer (`invalid-answer`; bead `bm-consolidation-81y2.23`), the Orchestrator now answers `by: policy` with predictor `orchestrator`; `policy` and `precedent` since Phase 2 (§B.3 as built) |
| `grant` | `{ effects, expiresAt, usedAt \| null }` — REQ-112 (b) |
| `delivery` | `{ to, kind, at, outcome: sent \| queued \| failed }` |
| `supersedes`, `supersededBy` | ids |

Rules: a Worker question may re-ask with `supersedes: "Q3"` (new optional field of the `bm_report` question schema) or with the same normalised text → the old one becomes `superseded`. An Orchestrator decision supersedes the open Orchestrator decision of the same request unless it passes `separate: true`. A superseded, withdrawn or expired decision is never answerable; the tool that caused it returns the id it replaced.

**Expiry of a Worker question** (code review 2026-09-30 §2.7, bead `bm-consolidation-81y2.26`, decided by Claude under the owner's delegation). A `q:` decision that is `open` or `needs-confirmation` expires when its request's `finished` report is recorded: at a Manager's turn end, a `BM-REPORT` with `phase: finished`, in an incoming message that is neither the owner's nor a plugin notice, expires every such question of the request the report names that was asked no later than the report (`settledAt` = the report's message time). The materialiser (`expireFinished`) writes each in its own store transition after the turn's openings and answers (§A.5), so an answer given meanwhile, or by the owner in the same turn, stands; a question asked after the report stays open. `o:` and `f:` decisions never expire this way; the owner's open overrides (`r:`, §B.7) of a request's questions expire with them, overrides of `o:` and `f:` decisions never do. An expired decision leaves the Inbox, is refused by `decisions.answer` (`E_DECISION_SETTLED`), `bm_decide` and `bm_predict`, and is never delivered; its card reads **Expired** with "The request finished."

`PreparedAction` is a union: `answer-worker` (implicit for Worker questions: deliver the answer), `command { to: manager | worker, agentId, intent, body, effects }` (Orchestrator decisions; P5), `fallback { action: switch | wait | resend | dismiss, target }` (fallback incidents).

Two bookkeeping fields complete the record: `settledAt` (set exactly when the status is final) and `needsConfirmation { via: chat-manager | chat-worker | chat-orchestrator, at }` (set exactly while `needs-confirmation`). The transitions are pure functions in the same module (`answerDecision`, `markNeedsConfirmation`, `confirmDecision`, `supersedeDecision`, `withdrawDecision`, `expireDecision`, `useGrant`); each returns the next record or a refusal and never reads a clock. An answer grants the chosen option's effects, or every effect the decision declares for own words (`none` never granted; nothing to grant → no grant). A chat answer the owner confirms (`decisions.confirm`) records no option, no words and no grant, because the plugin never read what was authorised.

### A.4 The store

`plugin/server/decision-store.ts`: `<data>/decisions/<workspaceId>.json` = `{ version: 1, entries: Decision[] }`, `0600` files in a `0700` folder, atomic writes, on the JSON store factory (`createJsonFileStore`, `server/data-files.ts`; code review 2026-09-30 §3.1, beads `bm-consolidation-81y2.3`, `.6`): a missing or corrupt file reads as empty, a bad entry is skipped alone, a file a newer paseo-bm wrote reads as empty and is never written (a coded error), symlinks are refused, and no lock is needed because every operation is synchronous. The alert, policy, precedent, intervention and coordination stores below follow the same factory rules. Open decisions are never evicted; settled ones keep the newest 500 per workspace. A malformed entry is skipped alone. `decisions.list` reads every workspace file with an mtime cache. Cleanup deletes the folder; deleting a request's traces deletes its settled decisions. Like `orchestrator-store.ts`, the store takes no lock: every operation is synchronous in the one plugin-server thread, so a read-modify-write cannot interleave. Opening is idempotent by id, and a `supersedes` naming an unsettled decision of the workspace supersedes it in the same write. A file with a newer `version` reads as empty and is never written.

### A.5 Materialisation (`plugin/server/decision-materialiser.ts`, on the collector's `onRecorded`)

The `BM-QUESTIONS` block carries the new fields as optional bracketed tags, so the text stays readable and older blocks still parse (each tag is optional; an unknown tag is ignored):

```
BM-QUESTIONS
requestId: req-20260929T073348Z
Q4: Push both backends to origin/dev? [subject: push-backends] [supersedes: Q2]
- a: Push contract only (recommended) [effects: push]
- b: Push both, manifest by hand [effects: push]
- c: Hold
```

`bm_report` gains the matching optional fields (`subject` ≤ 60 characters `[a-z0-9-]`, `supersedes` a `Qn` of the same request, `effects` per option from §A.3's list) and writes the tags; `parseQuestions` reads them; `bm-format.ts` accepts them.

a. **Open** — at a Manager's turn end, each `BM-QUESTIONS` in an inbound message that is not the owner's (today's `qa-ledger.questionsIn` logic, moved) opens `q:<requestId>:<Qn>` if absent; re-reading the same turn (reused turn ids) changes nothing.
b. **Answer through the Manager** — at a Manager's turn end whose inbound messages include the owner's typed message (`origin: "user"`), each `BM-ANSWERS` block the Manager wrote in its reply (built with `bm_answers`) settles those decisions with `via: chat-manager`. The Manager no longer sends answers to the Worker; the plugin delivers (A.6).
c. **Answer in a Worker's chat** — at a Worker's turn end, an owner-typed message holding a `BM-ANSWERS` block settles the named questions (`via: chat-worker`); any other owner text in that Worker's chat while decisions of its request are open marks them `needs-confirmation`: the Inbox asks "Answered in the Worker's chat? · Close · Keep open".
d. **Fallback** — each pending incident of `role-fallback-state.json` opens `f:<incidentId>` with the options the fallback card offers today (switch, wait, resend, dismiss) as prepared actions; resolving the incident any other way withdraws it.

Detail as built for a–c (`server/decision-materialiser.ts`):
- The collector hands `onRecorded` the record it just wrote (texts already masked); a–c read that record's `sent` (with `origin`) and `received`, never the store back. The block readers are the ledger's (`readableOf`, `questionBlockOf`, `answerBlockOf`), moved here; `qa-ledger.ts` calls them until it is retired.
- Open: `askedBy.agentId` is the live Worker labelled `bm.requestId = <requestId>` (the Manager's child first, else the only one of the workspace), null when not known for certain. A block's questions share one round: the stored round of any of them, else the request's highest round plus one. `askedAt` is the carrying message's time. A `[supersedes: Qn]` tag links only a question that is stored; the text match (case, punctuation and spacing ignored) replaces only an unsettled question.
- Answer lines: a leading option letter (`a — …`, `(a) …`, `a: …`, a bare `a`) is the option when the decision has it; otherwise the line, without an `other —` prefix, is the owner's words. The answer's time (and so the grant's hour) is the owner's message time — the last owner message of a Manager turn. A Manager's replies are read one by one and joined, so a streamed block still reads.
- `needs-confirmation` applies to the open `q:` decisions of the Worker's request (the record's `requestId`) and is remembered by owner message (agent, time, text) for the plugin run, so re-reading a record never re-marks a question the owner kept open.
- The decisions a turn answered go to the same `onSettled` hook as `decisions.answer` (`settledByKind` in `index.server.ts`), which the delivery (A.6) completes.

### A.6 Answering and delivery

RPCs (`plugin/shared/contracts.ts`, additive; handlers in `plugin/server/decision-rpc.ts`): `decisions.list { scope: inbox | workspace | request, workspaceId?, requestId?, status?, limit? }` → `{ decisions, truncated }` (`inbox`: unsettled decisions of every workspace or of `workspaceId`, oldest asked first; `workspace` and `request`: every stored one, newest asked first; `limit` ≤ 500, default 200; no usable data folder reads as none), `decisions.get { id }` → `{ decision }`, `decisions.answer { id, optionKey?, words?, confirmed?, via?: inbox | chat-card }` → `{ decision }`, `decisions.confirm { id, answered: boolean }` → `{ decision }`. An answer that would grant `push`, `publish`, `deploy`, `real-data`, `migration`, `security` or `cost` needs `confirmed: true` (experience concept X-4: release, data, security, cost). Error codes: `E_DECISION_NOT_FOUND`, `E_DECISION_SETTLED` (answered, superseded — the message names the replacing id —, withdrawn or expired), `E_DECISION_ANSWER_INVALID` (not exactly one of `optionKey`/`words`, blank words, unknown option), `E_DECISION_NOT_CONFIRMED`, `E_DECISION_NOT_NEEDS_CONFIRMATION` (`confirm` on a decision not waiting for one), `E_DECISION_WRITE_FAILED`, and `E_DATA_HOME_UNAVAILABLE`; every refusal writes nothing. After the answer and grant are stored, the handler hands the settled decision to an injectable `onSettled(decisions, { paseo })` hook — the delivery below; a failing hook is logged and never fails the answer. The client polls an open decision every 5 s while shown (REQ-111 b); a settled one stops polling.

Delivery, by the plugin through the notice queue:
- **Worker question (DQ-2, owner 2026-09-29: answers go to the Worker at once, coordination is proactive):** each answer is delivered as soon as it is given — at the Worker's next idle moment, one `BM-ANSWERS` block holding every settled, undelivered question of that request (kind `answers:<requestId>`, so a newer block replaces an unsent older one); questions still open stay open and the Worker carries on with what it has. No **Send** button, no waiting for the whole round.
- **Orchestrator decision with a prepared command:** the `BM-COMMAND` v2 (A.7) goes to its target with `authority: owner (decision <id>)` and `approved: <the option's effects>` — the owner's choice needs no further gate.
- **Orchestrator decision answered in words:** a `BM-ANSWER` block (`decisionId`, the words, the grant) goes to the Orchestrator; the grant allows exactly the decision's declared effects for one command within 60 minutes.
- **Fallback:** `fallback.act` with the prepared action.

Detail as built for Worker questions (`server/decision-delivery.ts`, wired as the `question` kind of `settledByKind` and as the materialiser's `afterTurn`):
- The message is `Continue <requestId>.`, a blank line, then `answersText` over every answered `q:` decision of the request whose `delivery` is null or `queued`, in question order (`Qn: a — <label>`, `Qn: other — <words>`). Target: the request's sole live Worker of the workspace (`soleWorkerOf` over the agents' labels, fallback-replaced Workers left out); none or several → every included decision is recorded `failed` (to the asking Worker) and nothing is sent. A queue `dropped` (archived, closed, gone, send failed) is `failed` too; a `failed` delivery is never retried.
- Recorded per included decision: `sent` (the Worker was idle), `queued` (held for its turn end). A `queued` decision becomes `sent` when a Worker's turn record carries an answers block naming it (the block arrived), or when this run's queue no longer holds its `answers:<requestId>` notice; it is then left out of the next block.
- An answer given in the Worker's own chat (`via: chat-worker`, including a confirmed chat answer) is not sent: it is recorded `sent` at the answer's time. Without a Paseo handle or data folder nothing is recorded and a later trigger delivers it.
- Once per plugin run — at the first settlement or recorded Manager or Worker turn with a Paseo handle, after that turn's arrivals are noted — every answered `q:` decision whose delivery is null or `queued` is delivered again, one block per request. A `queued` block sent just before a reload can therefore reach the Worker twice; an answer is never lost. One delivery runs per request at a time; a settlement meanwhile makes it look once more.

Detail as built for the Orchestrator's decisions (`server/orchestrator-decide-tools.ts` `bm_ask_owner`, `server/orchestrator-decisions.ts`, wired as the `orchestrator` kind of `settledByKind`):
- `bm_ask_owner { workspaceId, requestId?, managerId?, question, recommendation, options?[≤ 5]{ label, effects[], recommended?, command?{ to: manager | worker, agentId, intent, body } }, subject?, separate? }` stores `o:<uuid>` with keys `a`–`e`; the stored question is the question, a blank line and `Recommendation: …` (≤ 1,000 in all); at most one option is recommended; an option's `effects` are also its command's. A prepared command is checked as it will be sent: its target is a live, non-archived paseo-bm agent of that role in the project (never a Reviewer), the block can be written, and the backstop finds no category in the option's label and body that its effects do not declare. Supersession: the Orchestrator's unsettled `o:` decision of the same request (or, both without one, of the same project) — the newest of the same `subject` when there is one, else the newest; the answer returns `{ decisionId, replaced }`, `replaced` only when the store did supersede one.
- Prepared command chosen: `BM-COMMAND` v2 `from: orchestrator` (it prepared it), `via: tab` (the owner's tap), `re:` the option's label, `why: The owner chose "<label>" on decision <id>.`, `authority: decision:<id>`, `approved:` the option's effects the answer granted, `limits:` derived. Queue kind `command:<id>`; a Worker's Manager gets the `copy: yes` block. The target is re-checked at delivery; the command then leaves through the one send pipeline of `bm_send_command` and `bm_direct_worker` (`server/command-send.ts`, Orchestrator design §7): the grant is claimed and spent only once delivered, the command is written to the commands store (`proposals.json`, source `chat`) and so counts toward the loop guard. The owner's own choice is counted and never refused there; a choice by the policy or a precedent is refused when the guard is full. A command that cannot be delivered or is refused spends nothing, is recorded `failed`, and the Orchestrator gets the `BM-ANSWER` with a `delivery:` line saying why, so it can act on the unused grant.
- `BM-ANSWER` (a plugin notice, matched as a whole word so the owner's `BM-ANSWERS` never is): `decisionId`, `workspaceId`, `requestId` (or `none`), the question's first line, `answer:` (`option <key>: <label>`, or the owner's words after the header), `grant: <effects>, for one command with decisionId <id>, until <expiresAt>` (or `none`), then one instruction line. Queue kind `answer:<id>`, to the current main Orchestrator; with none open it is recorded `failed` and the Orchestrator reads it later with `bm_decisions`. An option without a command gets the same notice.
- Each decision is delivered once (a recorded `delivery` is never repeated); a confirmed chat answer (no option, no words) delivers nothing. The old tab's `orchestrator.ask { decisionId }` still answers the Orchestrator-store decisions recorded before this build, until the retirement sweep (A.14); new decisions are not on the tab.

Detail as built for the Orchestrator's answer to a Worker's question (change-004, bead `bm-autonomy-phase1b-dbdv.9`: §B.5's `bm_decide` brought forward with Phase 1's authority; `server/orchestrator-decide-tools.ts`). *Phase 2 retired that authority with Autopilot (§B.8) and gave `bm_decide` the policy's instead (§B.5 as built, bead `bm-autonomy-phase2-t9lm.11`): it now decides a `q:` or `f:` decision whose class is `delegate` with the predictor `orchestrator`, answering `by: policy`. The first bullet is Phase 1's; the answers it stored (`by: orchestrator, via: autopilot`) stay readable. The delivery, first-answer and refusal-of-settled rules below are unchanged.*
- `bm_decide { decisionId, optionKey, reason }` (reason 1–300 characters, redacted) answers an **open** `q:` decision with one of its options, `by: orchestrator`, `via: autopilot`, with the grant the owner's choice of that option would give (`answerDecision { by, reason }`). It is refused, writing and sending nothing and naming why (`decideRefusalOf`), when the id is not a `q:` decision (`o:` and `f:` are the owner's) or is not stored; when the decision is answered — "already answered by the owner / the Orchestrator at …; the first answer stands" —, needs confirmation, is superseded (naming the replacement), withdrawn or expired; when the project's Autopilot is off; when the option does not exist; when its effects hold one of `CONFIRM_EFFECTS`, `network` or `outside-workspace` (`OWNER_ONLY_ANSWER_EFFECTS`); or when they hold `dependency-install` and the project's allowed categories lack `dependency`. From the read to the write nothing awaits, so no other answer comes between (§A.4).
- The answered decision goes to the same `onSettled` hook as `decisions.answer` (`settledByKind`, wired in `index.server.ts`), so the Worker gets it as `BM-DELIVERY answers` at its next idle moment, in one block with the request's other undelivered answers; the tool's reply says whether it was sent, queued or could not be delivered. A failing delivery is one log line; the answer stands. The first answer wins both ways: the owner's later answer is refused `E_DECISION_SETTLED` with "is answered by the Orchestrator", and every refusal of a settled decision now names who answered.
- `bm_direct_worker` and `bm_send_command` refuse a command whose `BM-ANSWERS` block names a `Qn` that has a stored decision of that request — the block's `requestId:`, else a request id in the text, else the command's `requestId`, else (to a Worker) the Worker's `bm.requestId` label: open → "answer it with bm_decide, not in a BM-ANSWERS block"; answered → "already answered by the owner / the Orchestrator"; needs confirmation, superseded, withdrawn or expired → said as such (`refuseStoredAnswers`). A block naming only questions the store does not hold is sent as before.
- Views: the decision card reads "answered by the Orchestrator · <time>", with "Answered by: the Orchestrator" and the reason under Details and no answer buttons; Work's timeline says "The Orchestrator chose …"; the Inbox's Needs you no longer lists it (it is settled). `bm_decisions` hands out each answer's `by` and, for the Orchestrator's, its reason.

### A.7 Typed commands and authority (`BM-COMMAND` v2)

Header lines added: `intent: answer | continue | redirect | stop | release | other`, `effects: <list or none>`, `authority: owner | decision:<id> | policy:<class>` (`policy:<class>` since Phase 2, §B.9; Phase 1's `autopilot` is retired, §B.8, and only read in stored history), `approved: <effects the authority covers>`. `limits:` is derived: the fixed limits (no commit/push/deploy, no real data) minus what `approved` covers — a delivered command never carries a limit that contradicts its approval. The parser reads v1 blocks (no `intent`) as before.

Authority check for `bm_send_command` / `bm_direct_worker` (replaces the gate as the authority): every declared effect must be covered by a live grant (`decisionId` input), or — for effects outside `release, real-data, migration, security, cost` — by the owner's policy (§B.9) or the owner's own word in the Orchestrator's chat (Phase 1 also had Autopilot; Part B retired it, §B.8). The regex gate (`decision-gate.ts`) stays as a **backstop**: a category it finds that the declared effects do not include refuses the command with "declare the effect or ask the owner" — never a silent send.

Detail as built (`shared/orchestrator-command.ts`, `server/command-authority.ts`):
- Header order after `re:`: `intent`, `effects`, `authority`, `approved`, then `limits` (only `from: orchestrator`). `effects`/`approved` list real effects in `EFFECTS` order, or `none`. A fixed limit that is partly approved is split into `no-<effect>` for what it still withholds (`approved: push` → `limits: no-commit, no-deploy, no-real-data`); the parser refuses a v2 block whose limits withhold an approved effect, or that carries only some of the four v2 fields.
- Both tools require `intent` and `effects` (`["none"]` for none). The decision-only effects are `CONFIRM_EFFECTS` (push, publish, deploy, real-data, migration, security, cost). Without `decisionId`: a command declaring one of them is refused first ("needs the owner's decision"), whatever else holds; then the owner's policy (`authority: policy:<class>`, §B.9), else the owner's own latest word in the Orchestrator's chat (`authority: owner`) — each covers every effect except those. Every command the Orchestrator sends itself leaves `via: chat` and is recorded with source `chat` (§B.8 as built).
- The policy authority (bead `bm-autonomy-phase2-t9lm.19`): the policy is read at each send (`autonomy-store.ts` `currentPolicy`, the one read every reader uses; a store that cannot be read reads as every class `owner`). The command's classes are its declared effects' (`commandClassesOf`: §B.1's map, `commit` — and a command that declares no effect — counting as `reversible-technical`). When every one is `delegate` for the project (`modeOf`), the command goes with `authority: policy:<riskiest>` and `approved` its declared effects, without reading the Orchestrator's chat, `via: chat`. It comes before the owner's word, so a command both cover names the policy. Otherwise the refusal names the classes not delegated, riskiest first, then the owner's missing word ("reversible-technical is not delegated in this project and the owner has not just told you to send; ask the owner with bm_ask_owner, with this command prepared on an option"). The parser and the builder take `policy:<class>` for each of the nine classes and refuse any other; the owner's own command still carries only `owner`. The command card's authority reads "Policy · <class>". A `policy:<class>` authority never approves push, publish, deploy, real-data, migration, security or cost: the builder and the parser refuse such a block (bead `t9lm.10`), whatever produced it. The same authority carries the prepared command of an option the owner's policy chose as the decision opened (§B.5 as built): the decision's class, `via: chat`, `approved:` the option's effects its answer granted. With `decisionId`: it must name an `o:` decision of the project that the owner answered and, when it has a request, the same request; the grant (`grantRefusal`) must cover every declared effect, and a grant the owner's policy gave (§B.5) never covers push, publish, deploy, real-data, migration, security or cost. It needs no word in the chat (`via: chat`). A decision that granted nothing authorises only a command that declares no effect.
- The grant is spent (`useGrant` through the store's `transition`) only after the command is delivered; an in-memory claim keeps two concurrent calls from spending one grant. A delivery that fails spends nothing.
- No tab sends commands any more (§A.14): an option the owner picks on an `o:` decision delivers its prepared command as v2 `via: tab` with `authority: decision:<id>`; `from: owner` is only read from older builds. Since Phase 2 nothing silences the backstop: the owner's allowed categories and the stop-word exemption are retired (§B.8). The fixed limits stay only as the base the `limits:` line is derived from.

### A.8 Events to the Orchestrator and the Inbox

`plugin/server/event-bus.ts` replaces `BM-STALL`, `BM-EVENT` and the `autopilot-on` prompt with typed events: `decision.opened` (by its own rule: Phase 1's filter, then §B.9's per-cell rule), `request.finished`, `request.stalled` (no Worker or Reviewer of an unfinished request running for 5 min; a review over budget), `worker.signal` (the live watch's signals) — the last three only for the projects in the owner's policy scope (Scope below; Phase 1 scoped every event to Autopilot projects). `waiting-user` and `manager-turn` are dropped: a question now waits in the Inbox, and the Manager relays nothing.

Open alerts live in `<data>/inbox/alerts.json` (`{ version: 1, entries: { <key>: { workspaceId, kind, subject, since, clearedAt } } }`, same file rules as the decision store): raised once per key, cleared when the condition ends (an agent runs again, the permission is answered, the Worker's turn ends); this replaces the stall and signal keys of `orchestrator/stalls.json`.

Delivery: to the Orchestrator, all events pending at its idle moment go as **one** `BM-EVENTS` message (the notice queue gains a batch kind), each event one short line with the ids to look up; an event is dropped when its subject settled before delivery. To the owner: `request.stalled` and the `permission`, `danger`, `stuck` signals are **Inbox alerts** — never messages.

Detail as built (`server/event-bus.ts`, `server/alert-store.ts`, `shared/alerts.ts`; `server/stall-watcher.ts` and `server/worker-watch.ts` as its sources):
- **Scope** (as built in Phase 2, bead `bm-autonomy-phase2-t9lm.4`; change-007 C1). `request.finished`, `request.stalled` and `worker.signal` are published only for a project with at least one class above `owner` in the policy (§B.2: a `shadow` or `delegate` cell; `projectsAboveOwner` in `shared/autonomy.ts`), and dropped at delivery when that project fell back to all-`owner` meanwhile (a reset, or its cells set back to `owner`) — elsewhere the Orchestrator acts only when the owner talks to it, and what needs the owner is in the Inbox. The scope is read from `autonomy/policy.json` at each publish and at delivery (`eventScopeOf`); a policy that cannot be read is the empty scope, with one log line. The challenger switch alone does not put a project in the scope. `decision.opened` is not scoped by it: it follows the per-cell rule of §B.9 alone (the next two bullets). Nothing reads Autopilot to scope an event any more, and the Orchestrator's instructions say: "a decision only to decide or predict it, the rest only where the owner's policy shadows or delegates a class". `decision.opened` comes from the `q:` decisions the materialiser opened in the recorded turn and, since bead `t9lm.11`, from the `f:` decision a new fallback incident's listener opened (`registerFallbackRpcs`' `onDecisionsOpened` → the bus's `decisionsOpened`, as stored after a precedent or the policy answered it); an `o:` decision is the Orchestrator's own and never raises one. `request.finished` comes from each `finished` report of a recorded Manager turn, in the same `onRecorded` call as the turn's questions, so they reach the Orchestrator together.
- **The challenger's prediction** (as built in Phase 2, bead `bm-autonomy-phase2-t9lm.7`; change-007 C1). A decision the Orchestrator did not ask, still `open`, of a delegable class in an `owner` or `shadow` cell of a project whose challenger is on, opened with its predictions recorded and not predicted yet (`predictionRefusalOf` in `shared/autonomy.ts`), raises a `decision.opened` with `asks: "prediction"`. Its line ends "A prediction is asked: read it with bm_decisions and give the option you expect the owner to choose with bm_predict. The owner decides it: answer nothing and tell the owner nothing." Same type and dedupe key as every `decision.opened`, and at most one event per decision. It is published whatever the policy scope — a project whose cells are all `owner`, every new project, included — and never for a `delegate` cell or a release, data, security or cost decision. The policy is read at the turn's publish and again at delivery (`eventPolicyOf`; unreadable = no challenger on), and the event is dropped when the decision may no longer be predicted: settled or waiting for a confirmation, the challenger turned off, its cell delegated, or predicted already. A fallback incident (`f:`) raises it from its listener (Scope above; bead `t9lm.11`); the start-up pass and the pass after an action raise none, and `bm_predict` accepts such an incident all the same (§B.3).
- **The delegation to the Orchestrator** (as built in Phase 2, bead `bm-autonomy-phase2-t9lm.11`; §B.5). A decision the Orchestrator did not ask (`q:`, `f:`), still `open`, of a delegable class that is `delegate` in its project with the predictor `orchestrator` (`decideRefusalOf` in `shared/autonomy.ts`) raises a `decision.opened` with `asks: "decision"`, whose line ends "A decision is asked: the owner's policy delegates its class to you. Read it with bm_decisions and choose the option the owner would, with bm_decide and your reason in one line." The two rules never both hold (a `delegate` cell is not predicted). The policy is read at the publish and again at delivery, and the event is dropped when the decision may no longer be decided: settled or confirming, its cell set back, reset, demoted or given to the recommended option. A cell of the recommended predictor raises nothing (its decision was answered at open, §B.5), nor an `owner` or `shadow` cell with the challenger off. A decision that waits for `bm_decide` and gets none stays open in the Inbox for the owner: nothing times out into an answer, and it is not told again.
- **Only a judgement wakes** (REQ-115 b, as built after the Phase 1 live check measured 3 of 3 wakes with no action): a decision raises `decision.opened` only when the policy asks the Orchestrator to decide or predict it (the two bullets above; bead `t9lm.11` replaced Phase 1's filter — a `q:` without a `CONFIRM_EFFECTS` option, in any project — by that per-cell rule). Release, data, security and cost, by a proposed class or any option's effect, are the owner's alone (X-4, REQ-121 c) and wake nobody whatever the policy file says; a `finished` report raises `request.finished` only when it shows work left — ready beads, open review findings, blockers, or failing checks (`workLeftOf`). Phase 3 (C.3) adds `finished-unverified` to what counts as work left.
- **Dedupe keys.** `decision.opened:<id>`, `request.finished:<ws>:<requestId>@<report time>`, `request.stalled:<ws>:<requestKey>@<alert since>`, `worker.signal:<ws>:<worker>:<signal>@<alert since, or the turn start>`; a key is published once per plugin run. Across reloads the sources dedupe themselves (a decision opens once, an alert is raised once, a turn is recorded once); only `failing`, `heavy` and `outside` may be told once more after a reload mid-turn.
- **Settled** (dropped at delivery): a decision no longer open or needs-confirmation; a stall or signal whose alert was cleared; a `failing`/`heavy`/`outside` signal whose Worker's turn ended.
- **Batch kind.** `enqueueBatch(target, { name: "BM-EVENTS", compose }, items)`: the items of one call are queued, then delivered once; at the target's idle moment every pending item of that batch goes as one message, oldest first, each item's `isCurrent()` read synchronously right after the idle read. A batch counts as one notice (the queue's one-per-idle-moment rule), and a batch whose every item settled sends nothing and lets the next notice go.
- **Stall pass.** Always on (no switch), every project with activity in 24 hours: `idle-unfinished` (5 minutes, the last report neither `finished` nor `blocked`) and `review-over-budget`; a `blocked` request is not stalled (its question waits in the Inbox), a malformed report alone is no stall. One `request-stalled` alert per request (subject the request key, `detail` the reasons); `orchestrator.state` reads it as a project's `stalled` state.
- **Worker watch.** Running Workers of **every** project, every 2 minutes, at most `MAX_WATCHED_WORKERS` (5, the newest) per pass, 300 timeline entries each; with no running Worker nothing is refreshed or read (Phase 2; Phase 1 watched Autopilot projects only). `stuck`, `permission` and `danger` raise the Worker's `stuck`, `permission-waiting`, `danger` alert (subject the Worker id, `detail` the redacted evidence, ≤ 300 characters) in every project: they cost no model call. Only in the policy scope does the pass that raises an alert publish its `worker.signal` event, a newly raised `danger` open the interrupt allowance (still in `orchestrator/stalls.json`, its one remaining key), and `failing`, `heavy` and `outside` become events; an alert raised while its project was outside the scope is not told when the project enters it. `stuck` and `permission` clear when no longer seen; all three at the Worker's recorded turn end or when it stops running. A project that leaves the scope keeps its alerts; its pending events are dropped at delivery.
- **Alerts file.** `<data>/inbox/alerts.json`, key `<kind>:<workspaceId or ->:<subject>`, optional `detail`; the cleanup button deletes `inbox/`. Open alerts are never evicted, cleared ones keep the newest 500. Other producers: `pairing-mismatch` (`role-pairing.ts`, through `raiseInboxAlert`), `fallback-failed` (an answered `f:` decision whose `delivery.outcome` is `failed` while its incident is pending; cleared once the incident is not). `outdated-agent` (`outdated-agents.ts`, §A.11): one per live Manager, Worker or Reviewer on older instructions, cleared once it is current, replaced, archived, closed or gone. `autonomy-demoted` (`autonomy-rpc.ts`, §B.4): one per project and class taken back after a reversal, cleared by the owner's next change of that cell, a reset of the project, or the class eligible again.
- **Wakes recorded.** Each delivered `BM-EVENTS` message is one wake in `orchestrator/wakes.json` (the notice queue's batch `onSent`: Orchestrator id, time, projects, number of events); the Orchestrator's next turn end (the batch's `onTurnEnded`, called by the queue at that turn end before it delivers anything else) sets `endedAt` on its oldest open wake. Ids, times and a count only; the evaluation's A-7 reads it (evaluation design §4).
- **Retired.** `BM-STALL` and `BM-EVENT` (producers and notice prefixes), `server/autopilot-events.ts` (`question`, `finished`, `manager-turn`, `autopilot-on`), the Watch switch (the settings file no longer has `watch`; its RPC went with the sweep, §A.14), the stall, event and Worker-signal keys of `orchestrator/stalls.json` (ignored, dropped at the next write). Measured on a synthetic day in `test/event-bus.test.ts`: 160 events, 119 wakes, none without a pending event.

## Part B — Phase 2 MVP: calibrated autonomy (ADR-018)

*Active since 2026-09-30, the Phase 2 start (bead `bm-autonomy-phase2-t9lm.1`). It was re-checked against the field data then available (evaluation baseline report §5); [change-007](../plans/paseo-bm-plan-autonomy-change-007-phase2-start.md) records what changed and what was confirmed.*

### B.1 Classes

`class` added to `Decision`: `reversible-technical, scope, preference, environment, dependency, release, data, security, cost`. The asker proposes it (`bm_report` question field; `bm_ask_owner` field). The plugin checks it against the declared effects — `push, publish, deploy` → `release`; `real-data, migration` → `data`; `security` → `security`; `cost` → `cost`; `dependency-install` → `dependency`; `network, outside-workspace` → `environment` — and keeps the riskier class on conflict (order: security, data, release, cost, dependency, environment, scope, preference, reversible-technical). A fallback incident is `environment`.

Detail as built (`shared/decisions.ts`, bead `bm-autonomy-phase2-t9lm.2`):
- **The map.** `DECISION_CLASSES` holds the nine in conflict order and `CLASS_OF_EFFECT` maps every effect; `none` and `commit` imply no class. `riskierClass`, `classOfEffects` (null when no effect implies a class) and `checkedClass(proposed, effects)` are pure. `HARD_OWNER_CLASSES` is release, data, security and cost, exactly the classes of `CONFIRM_EFFECTS` (derived from them through `CLASS_OF_EFFECT`, as `GATE_CATEGORY_EFFECTS` is from `CLASS_OF_EFFECT`); `isHardOwnerClass` names them for the policy (B.2).
- **The stored field.** `class` is an optional field of the record, and the store stays `version: 1`. Every decision opened from this build carries it. A Worker question (`decision-materialiser.ts`) and an Orchestrator decision (`bm_ask_owner`) keep the riskier of the proposal and the classes of their options' declared effects (their union, `declaredEffects`), or `reversible-technical` with neither. A fallback incident is `environment`. Opening is keyed by id, so reading a turn again never changes a stored class.
- **Reading it.** Readers go through `decisionClassOf`, which checks the stored class again against the effects. A decision stored before classes reads as `environment` when it is a fallback incident (`f:`), else as its effects' class, else as `reversible-technical`.
- **Proposing it.** The Worker gives `bm_report`'s optional `class` per question, written as `[class: <class>]` after `[subject: …]` and `[supersedes: …]`. `parseQuestions` reads it and ignores a value that is not one of the nine; the block check (`bm-format.ts`) already accepted any tag. The Orchestrator gives `bm_ask_owner`'s optional `class`, and the tool's answer names the class kept. worker.md asks for one per question (the nine, riskiest first, the riskier when unsure); orchestrator.md names the field.
- **Showing it.** Both faces of `bm_decisions` return each decision's `class`, and a decision card's Details has a `Class:` line.

### B.2 Policy

`<data>/autonomy/policy.json` `{ version: 1, projects: { <workspaceId>: { <class>: owner | shadow | delegate } }, challenger: { <workspaceId>: boolean } }`; absent cell = `owner` with shadow on (Q-102). `release, data, security, cost` cannot be set to `delegate` (the RPC refuses). RPCs `autonomy.policy`, `autonomy.set { workspaceId, class, mode, confirmed }`, `autonomy.reset { workspaceId }`, `autonomy.set-challenger { workspaceId, enabled }` (§B.3). Settings shows the matrix per project. Phase 4 adds an optional `boundary` map and `autonomy.set-boundary`, the action boundary's per-project switch (§D.2, change-010).

Detail as built (bead `bm-autonomy-phase2-t9lm.3`):
- **Schema** (`shared/autonomy.ts`, pure). A cell is an object, not a bare mode: `{ mode: owner | shadow, at }` or `{ mode: delegate, predictor: recommended | orchestrator, at }`, `at` being when it was set. `modeOf(policy, workspaceId, class)` reads an absent cell or project as `owner`; `predictorOf` gives a delegated cell's predictor; `canDelegate(class)` is false for the four `HARD_OWNER_CLASSES`. A cell is read on its own: an unknown class, an unknown mode, a `delegate` without a predictor or a `delegate` of a hard-owner class is skipped alone (it reads `owner`) and dropped by the next write; so is a challenger entry that is not a boolean. The workspace id `__proto__` is refused.
- **Store** (`server/autonomy-store.ts`): the alerts store's file rules (0700 folder and 0600 file created by a write only, atomic replace, symlinks refused, no lock). A missing or corrupt file reads as the empty policy; a newer `version` reads as it too and is never written, not even by a reset. The challenger map is kept on every write; its RPC is `autonomy.set-challenger` (§B.3). The cleanup button deletes `autonomy/`.
- **RPCs** (`server/autonomy-rpc.ts`; contracts in `shared/contracts.ts`):
  - `autonomy.policy { workspaceId? }` → `{ policy }`, the whole policy or one project's; reads only. No usable data folder or an unreadable store reads as the empty policy (every cell `owner`, the safe side), with one log line. `readAutonomyPolicy` is the same read for the plugin's own readers.
  - `autonomy.set { workspaceId, class, mode, confirmed?, predictor? }` → `{ policy }` (the whole policy). Checked in this order, before the data folder is looked at: an unknown project, class, mode or predictor → `E_AUTONOMY_INVALID`; `delegate` of release, data, security or cost, confirmed or not → `E_AUTONOMY_OWNER_ONLY`; `delegate` without `confirmed: true` → `E_AUTONOMY_NOT_CONFIRMED`. Then no usable data folder → `E_DATA_HOME_UNAVAILABLE`; a newer or unwritable store → `E_AUTONOMY_WRITE_FAILED`. `predictor` defaults to `recommended` for a caller that names none — **Delegate?** always names the one that made the cell eligible (§B.4) — and is read only for `delegate`. A change of a cell ends its `autonomy-demoted` alert (§B.4). `owner` and `shadow` are accepted for every class and need no confirmation.
  - `autonomy.reset { workspaceId }` → `{ policy }`: that project's cells are removed in one write (an absent cell reads `owner`); other projects, the challenger and the classes' last demotions (§B.4) are untouched; a project with no cell writes nothing; the project's `autonomy-demoted` alerts end. No confirmation.
  - `autonomy.set-challenger { workspaceId, enabled }` → `{ policy }`: §B.3.
  - Every refusal writes nothing. No agent tool sets the policy.
- **Settings → Autonomy** (`client/settings-autonomy.tsx`, `settings-autonomy-model.ts`; wired from `settings-section.tsx`, the launcher passing the projects Insights names): the group's folded line counts the delegated and shadow classes across projects ("Every decision is yours, in every project" otherwise). Opened: what the modes mean in one line, project tabs (a project with classes above `owner` carries their count; a project the policy holds cells for that no longer has a name is "Unnamed project", never its id), and the chosen project's matrix. The delegable classes come first, least risky on top, each with **Owner** / **Shadow** (one press, `autonomy.set`); a delegated cell shows "Decided for you by the recommended option (or the Orchestrator) since <date>" and can be set back. Release, data, security and cost are "Owner (fixed)" rows with a one-line reason and no choice. No row offers `delegate`: that is **Delegate?** in Insights (§B.4). **Return all to owner** (`autonomy.reset`, one press) is enabled while a class of the project is above `owner`.

### B.3 Shadow and the agreement ledger

For every decision answered by the owner: `prediction.recommended` (the option marked recommended, at open time) and, when the project's challenger is on, `prediction.orchestrator` (the Orchestrator is sent the decision in a `BM-EVENTS` line and answers with `bm_predict { decisionId, optionKey, reason }`, never seen by the owner before answering). `plugin/shared/autonomy-ledger.ts` (pure) computes per project × class × predictor: agreement, count, first/last time, reversals. **Reversal** of a decision: re-asked with the same `subject` in the same request after it was settled; overridden from the digest; or a bead closed under it reopened with a reason citing it.

Detail as built (bead `bm-autonomy-phase2-t9lm.6`; change-007 C4):
- **On the record** (`shared/decisions.ts`, additive, the store stays `version: 1`):
  - `prediction { recommended: { optionKey } | null, orchestrator: { optionKey, reason, at } | null }`, each naming one of the decision's options. `openingPrediction` sets it where each kind opens — the materialiser (`q:`), `bm_ask_owner` (`o:`) and the fallback decisions (`f:`, `recommendedActionOf`). It is `recommended: null` when no option is recommended and `orchestrator: null` until `bm_predict` (the challenger's bead) writes it. Opening is keyed by id, so opening again changes nothing. A decision opened before this build has no `prediction` and is in no cell: nothing is read back from its options (change-007 §3.3).
  - `reversals[] { kind: re-asked | overridden | reopened, at, ref }`, at most 20, only on an answered decision. `ref` is the re-asking decision's id, the override's id or the reopened bead (`last-touched` when the reopen names none). Every reversal goes through `recordReversal`, which keeps one entry per kind and `ref` and refuses a decision never answered (`not-answered`).
  - `answer.by` is `owner | orchestrator | policy | precedent`. `orchestrator` stays readable for Phase 1's `bm_decide` answers. A `policy` answer is an option and names its `predictor`; a `precedent` answer names its `precedentId` and may be the owner's standing words. Either may carry the cell's `class`. `via: autopilot` is refused for `owner` and `precedent`. `precedent` is written at open since bead `t9lm.14` (§B.6), and `policy` since bead `t9lm.10` (§B.5, `via: inbox`).
- **Reversals detected.**
  - (1) In the materialiser: a new `q:` of the same request with the `subject` of an **answered** question reverses that answer, `ref` the new id. Re-asking an unsettled one is supersession only.
  - (3) At every recorded Manager or Worker turn (the materialiser, on the collector's `onRecorded`): each `br reopen` in the turn's shell evidence is read with its beads and its `--reason`/`-r`. A reason that cites `q:…` or `o:…`, or a bare `Qn` (of the request ids it names, else of the record's request), reverses that decision when it is answered and the reopen is not earlier than the answer. A reopen whose reason cites nothing is a review finding, the baseline's noise, and records nothing.
  - (2) The digest's Override records `overridden` through the same `recordReversal` (bead `t9lm.15`).
- **The ledger** (`shared/autonomy-ledger.ts`, pure, derived on demand) reads answered decisions only. Per `(workspaceId, class, predictor)` a cell holds:
  - `count`: owner answers with an option or words that carry that predictor's prediction;
  - `agreed`: the answers that chose the predicted option (own words never agree);
  - `unread`: chat answers the owner confirmed, whose content was never read — in neither `count` nor `agreed`;
  - `firstAt`/`lastAt`: over the counted answers;
  - `reversals`: decisions reversed at least once, and `reversalsByKind`, each decision once per kind.

  `delegated[]` counts answers `by: policy` (per `predictor`) or `by: precedent`, with `overridden` (A-4) and `reversals`/`reversalsByKind` (A-5). An answer `by: orchestrator` is in neither figure (change-007 C4). Options: `workspaceId`, and `since`, so a demoted cell can count only the decisions after its demotion (§B.9).
- **Read-only RPC** `autonomy.ledger { workspaceId? }` → `{ cells, delegated }` (`server/autonomy-ledger-rpc.ts`). It gives numbers and times only, never a prediction. No usable data folder reads as none.
- **The owner never sees the challenger first.** `decisions.list`, `decisions.get` and `decisions.confirm` return an unsettled decision through `ownerViewOfDecision`, with `prediction.orchestrator` set to null; once it is settled it is shown. The store keeps it throughout. `bm_decisions` hands out no prediction at all.

Detail as built for the challenger (bead `bm-autonomy-phase2-t9lm.7`; change-007 C1):
- **The switch.** `challenger[workspaceId]` in `policy.json`; absent or `false` is off (DQ-4). `autonomy.set-challenger { workspaceId, enabled }` → `{ policy }` (the whole policy) needs no confirmation (§B.9): it only records predictions. An unknown project or a value that is not a boolean → `E_AUTONOMY_INVALID`, before the data folder is looked at; then `E_DATA_HOME_UNAVAILABLE` and `E_AUTONOMY_WRITE_FAILED` as for `autonomy.set`. `false` is kept as the owner's answer rather than removed; a switch already in that state writes nothing; the project's cells are untouched, and `autonomy.reset` leaves the switch as it is.
- **The rule** (`predictionRefusalOf`, `shared/autonomy.ts`, pure). A prediction is asked and accepted for a decision the Orchestrator did not ask (`q:`, `f:`), still `open` (not waiting for a confirmation), of a delegable class, in an `owner` or `shadow` cell, where that project's challenger is on, opened with its predictions recorded (a decision stored before them is in no cell) and not predicted by the Orchestrator yet. The rest of the project's policy does not matter. The event bus asks by it (§A.8), and `bm_predict` records by it.
- **`bm_predict { decisionId, optionKey, reason }`** (face in `shared/bm-tools.ts`, run by `server/orchestrator-decide-tools.ts`). The policy is read at the call, and the rule is checked again inside the store's write, so one decision holds one prediction. Refusals name why and write nothing: its own decision, a settled or confirming one, a hard-owner class, a `delegate` cell, the challenger off, a second prediction, a decision stored before predictions, an option the decision does not have, an unknown id. - **Settings → Autonomy.** Each project's matrix has **Orchestrator predictions** Off / On above the rows, one press each way, with what they do and cost in one line. A project with the predictions on that no longer has a name stays listed as "Unnamed project", so they can be turned off.

### B.4 Promotion and demotion

A cell is **eligible** when a predictor's agreement ≥ 90 % over ≥ 20 decisions spanning ≥ 14 days with no reversal. Insights shows **Delegate?** on an eligible cell; `autonomy.set` with `confirmed` applies it and records the predictor that earned it. A reversal or an owner override of a delegated decision demotes the cell to `shadow` at once, with an Inbox alert.

Detail as built (bead `bm-autonomy-phase2-t9lm.9`):
- **Eligibility** (`eligibility(cell, now)` in `shared/autonomy.ts`, pure) judges one agreement cell of the ledger (§B.3): `ELIGIBLE_MIN_AGREEMENT` 0.9 (`agreed / count`), `ELIGIBLE_MIN_DECISIONS` 20 (`count`), `ELIGIBLE_MIN_SPAN_DAYS` 14 (`lastAt − firstAt`, the last read no later than `now`, so a clock that ran ahead never lengthens it; a time that does not read is no span), and no reversal. It returns `{ eligible: true }` or the first unmet reason in the order `owner-only` (release, data, security and cost: never), `agreement`, `count`, `span`, `reversal`.
- **After a demotion only the answers since count** (§B.9). The policy file keeps each class's last demotion: `demotions: { <workspaceId>: { <class>: <time> } }`, beside `projects` and `challenger`, absent while there is none; read entry by entry (a hard-owner class or a time that does not read is skipped); written only by a demotion, which replaces an older time; kept when the owner sets the cell again, delegates it again or resets the project — it is history, not a mode, so a class demoted a minute ago cannot be offered again on the answers that came before. `agreementLedger`'s `demotions` option leaves out of a demoted class's agreement cells the owner's answers given before it (an answer at the demotion's own time counts); the delegated figures stay whole for A-4 and A-5. `autonomy.ledger` reads the policy and applies it, so Insights shows the figures eligibility is judged on. *Why a separate map and not the cell's `at`:* a Shadow pressed in Settings would then restart the count, and a reset would forget the demotion.
- **Delegate?** (`client/insights-model.ts`, `client/insights.tsx`). On each predictor's figures of Insights → Autonomy whose cell is eligible at the time of reading, for a delegable class that is not `delegate` (either `owner` or `shadow`, §B.9); a secondary button that only opens the confirmation in place, under the class. The confirmation names the class and the project, who would decide (the recommended option or the Orchestrator), the figures that earned it ("it matched 19 of your 20 answers (95 %) from … to …, none reversed"), and that a reversal or an override takes it back at once and Return all to owner in Settings → Autonomy undoes it; Cancel comes first and is the default. Confirming sends `autonomy.set { workspaceId, class, mode: delegate, confirmed: true, predictor }` with the predictor that earned it, and writes the returned policy into the query Settings reads. While a confirmation is open or its call runs, every offer waits; a confirmation for a cell no longer eligible is not shown; a failure is said under it. The note above the figures gives the thresholds and says a class that went back to Shadow counts again from then; a demoted class's row says "Went back to Shadow on <day> after a reversal; counted from then." The RPC itself still does not check eligibility (§B.9).
- **Demotion** (`demoteOnReversal(decision, kind, { home, now?, log? })` in `server/autonomy-rpc.ts`), called wherever a reversal is recorded: the materialiser's re-ask and cited `br reopen`, right after `recordReversal` adds a new entry (§B.3), and the digest's Override (§B.7, bead `t9lm.15`). When the decision was answered `by: policy | precedent` and its cell (the answer's `class`, else the decision's) is `delegate`, the store's `demote` sets the cell `{ mode: shadow, at: now }` and `now` as its last demotion in one write, and an `autonomy-demoted` alert is raised. An owner's answer, a cell that is not `delegate` (already demoted, or never delegated) and a decision not answered change nothing, so a second reversal in the same class raises no second alert. It never touches the decision or its delivery: only what happens to the class's next decision. A failed write is one log line and raises no alert.
- **The alert** `autonomy-demoted` (`shared/alerts.ts`, last in `ALERT_KINDS`), key `autonomy-demoted:<workspaceId>:<class>`, subject the class, detail "<Class> decisions are back in Shadow: <decision id>, answered for you by <the recommended option | the Orchestrator | your precedent>, <was asked again in the same request | was overridden by you | was reversed: a bead closed under it was reopened citing it>. They come to you again; Insights offers Delegate? once the class earns it anew." It clears when the owner next sets that cell (`autonomy.set`, any mode) or resets the project (`autonomy.reset`, every class of it), after the write and never failing it; or when the class is eligible again: after every settlement (the `onSettled` hook in `index.server.ts`), `clearRenewedDemotions` looks at the classes the owner's answers fall in, and only while such an alert is open reads the project's answered decisions and clears it when a predictor's cell, counted from the demotion, passes `eligibility`. It leaves the cell in `shadow`: delegating again is the owner's Delegate?. There is no separate dismiss: the owner's next change of the cell is the dismissal.
- **The Inbox line** (`client/inbox-model.ts`): "<Class> decisions went back to Shadow after a reversal · <project> · <time>", in the warning colour, with nothing to open; the detail and the alert's key and time under Details on a tap.

### B.5 Delegation

When a decision opens in a `delegate` cell: predictor `recommended` → the plugin answers with the recommended option at once (`answer.by: policy`); predictor `orchestrator` → a `decision.opened` event asks the Orchestrator to decide with `bm_decide { decisionId, optionKey, reason }`. Both deliver exactly as an owner answer would (A.6), with `authority: policy:<class>`. The Orchestrator's Autopilot and **Allow…** are removed (the Watch switch went in Phase 1).

As built: Autopilot and Allow… are removed (§B.8 as built, bead `bm-autonomy-phase2-t9lm.5`); the recommended predictor answers by code (bead `t9lm.10`, below) and the Orchestrator with `bm_decide` (bead `t9lm.11`, below).

Detail as built for the recommended predictor (bead `bm-autonomy-phase2-t9lm.10`; REQ-121, REQ-123):
- **The rule** (`recommendedDelegationOf`, `shared/autonomy.ts`, pure). The policy answers a decision that is `open`, whose class (`decisionClassOf`) can be delegated and is `delegate` in its project with the predictor `recommended`, and that has exactly one recommended option. The answer is that option. Nothing else is answered by code:
  - an `owner` or `shadow` cell, or another project's delegation;
  - a cell whose predictor is the Orchestrator (`t9lm.11` decides it);
  - release, data, security or cost, which never read `delegate` whatever the file says;
  - a decision with no recommended option.

  Since the class is checked against every option's effects, a release, data, security or cost effect anywhere keeps a decision the owner's.
- **At open, after the precedents** (`resolveByPolicy`, `server/policy-resolve.ts`; `resolveAtOpen` there runs the precedent, then the policy, for every opening point). The three opening points call it right after `resolveByPrecedent` (§B.6): the materialiser (`q:`), `bm_ask_owner` (`o:`), and a new fallback incident's listener (`f:`).
  - `bm_ask_owner` skips both — no precedent and no policy answers at open — while the loop guard of its request is full (Orchestrator design §6A; an unreadable command log counts as full): the answer would be a command the guard refuses, so the owner gets the question.
  - It runs only when no precedent bears on the decision. A precedent that answers is the owner's own standing word. One that is only suggested (a hard-owner class, a fallback incident's words) leaves the decision to the owner rather than to the recommended option.
  - The materialiser also leaves to the owner a subject that the policy or a precedent already answered in the same request. Asked again, that answer did not do; the re-ask is a reversal that demotes the class (§B.4).
  - A fallback incident's decision is answered only where its action can run at once, as a precedent's is (§B.6).
  - The policy is read at the call; one that cannot be read reads as every class `owner`, with one log line. The rule is checked again on the stored decision in the write that answers it, so an answer given meanwhile stands.
- **The answer.** `answerDecision { by: policy, via: inbox, optionKey, class, predictor: recommended, reason: "The recommended option: <class> is delegated to it in this project" }`, stamped when it is resolved. `via: inbox` as a precedent's: nothing was typed in a chat. It grants the option's effects as the owner's choice of it would. As a second line, `answerDecision` refuses a policy answer that would grant push, publish, deploy, real-data, migration, security or cost.
- **Delivered as an owner answer**, through the same `onSettled` (`settledByKind`):
  - A `q:` answer goes to the Worker in the same `BM-DELIVERY answers` block as an owner answer, and is not cited: its provenance is shown to the owner, not to the Worker (decided at conversion).
  - An `o:` option with a prepared command goes as `BM-COMMAND` v2 `from: orchestrator`, `via: chat` (nobody tapped; every command on the policy's authority leaves `via: chat`, §A.7) and `authority: policy:<class>`, the answer's class. `approved:` is the option's effects the answer granted, and `why:` is `Policy chose "<label>" on decision <id>.`, shorter than the owner's, so every command `bm_ask_owner` accepted can be written. The grant is claimed and spent as for the owner's choice.
  - An `o:` option without a command goes as the `BM-ANSWER` notice, with a `policy: <class> is delegated to the recommended option in this project; the owner was not asked` line.
  - An `f:` answer runs `fallback.act`.
  - `bm_ask_owner` says it was answered at once by the owner's policy and adds `answeredBy: "policy"` and `predictor` to its JSON.
  - No `decision.opened` goes out for a `q:` answered at open.
- **The guard** (REQ-121 c, REQ-112). Only the owner's grant covers push, publish, deploy, real-data, migration, security and cost:
  - The builder and the parser refuse a `policy:<class>` authority whose `approved` holds one of them (`shared/orchestrator-command.ts`).
  - The Orchestrator delivery sends no policy command whose `approved` would; it records `failed`, spends nothing and tells the Orchestrator in its `BM-ANSWER`.
  - `bm_send_command`/`bm_direct_worker` refuse to spend a policy answer's grant on one of them.

  A hard-owner decision stays open, delivers nothing and raises no `decision.opened`. Phase 1's filter now also skips a class only the owner decides when it was proposed with no effect (§A.8).
- **Counted as delegated.** The ledger counts a `by: policy` answer in `delegated[]` per predictor, never as an owner agreement (§B.3). Re-asked, reopened or overridden, it demotes its class (`demoteOnReversal`, §B.4). `autonomy.reset` stops every delegation of a project at once. It is not an Orchestrator intervention (§G.3).
- **Shown to the owner.**
  - A decision card reads **Decided**, "decided for you by the policy · recommended option · <time>", with no answer buttons and no **Save as precedent** (not the owner's answer). Details has `Answered by: your policy (recommended option, <class> delegated)` and the reason.
  - Work's timeline says `Decided for you by the policy (recommended option): "<label>"`.
  - The Inbox's digest of such answers is §B.7's (bead `t9lm.15`).

Detail as built for the Orchestrator's predictor (bead `bm-autonomy-phase2-t9lm.11`; REQ-121, REQ-123):
- **The rule** (`decideRefusalOf(policy, decision)`, `shared/autonomy.ts`, pure). The Orchestrator may decide a decision it did not ask — a Worker's question (`q:`) or a fallback incident (`f:`); its own `o:` stays the owner's whatever the cell (§B.9) — that is `open`, whose class (`decisionClassOf`) can be delegated and is `delegate` in its project with the predictor `orchestrator`. Otherwise it names why: its own decision; answered ("already answered by the owner / the Orchestrator / the policy / an owner precedent at …; the first answer stands"), needs confirmation, superseded (naming the replacement), withdrawn or expired; a hard-owner class ("… is always the owner's; leave it to the owner"); not delegated to it (an `owner` or `shadow` cell, another project's delegation); delegated to the recommended option. The event bus asks by it (`decision.opened`, `asks: "decision"`, §A.8) and `bm_decide` answers by it.
- **`bm_decide { decisionId, optionKey, reason }`** (face in `shared/bm-tools.ts`, run by `server/orchestrator-decide-tools.ts`; input unchanged since change-004). The policy is read at the call (unreadable = every class `owner`); the rule is checked on the stored decision, then the option must exist, then the rule is checked again inside the store's write. It stores `answerDecision { by: policy, via: inbox, optionKey, class, predictor: orchestrator, reason }`, the reason redacted and on one line (at most 300 characters): `via: inbox` as the other policy answers, since nothing was typed in a chat. It grants the option's effects as the owner's choice would; `answerDecision` still refuses a policy answer granting a release, data, security or cost effect. A refusal writes, delivers and logs nothing.
- **Delivered as an owner answer**, through the same `onSettled` (`settledByKind`): a `q:` answer reaches the Worker in the same `BM-DELIVERY answers` block as an owner answer, uncited; an `f:` answer runs `fallback.act`. The tool's reply names the class, what the delivery did (sent, queued, failed; for an incident, the action ran or not), and asks the Orchestrator to send nothing more and tell the owner in one line. Its JSON: `decisionId`, `optionKey`, `class`, `answeredBy: "policy"`, `predictor: "orchestrator"`, `grant`, `delivery`. Since it never answers an `o:` decision, it never produces a command: `authority: policy:<class>` is carried only by the prepared command of an `o:` option the recommended predictor chose (above). A `q:` decision's grant authorises no command either (`decisionId` takes only an `o:` decision), so a command's `approved` never holds release, data, security or cost without the owner's grant.
- **Logged and measured.** The answer is an `answer` intervention (§G.3, `interventionOfDecision`: triggered by its wake's `decision.opened` when the wake carried it, else on the Orchestrator's own look), and its wake's action for A-7 (evaluation design §4). The ledger counts it in `delegated[]` under the predictor `orchestrator`, never as an owner agreement (§B.3); re-asked, reopened or overridden it demotes its class like any policy answer (§B.4). The cards and Work's timeline already name it ("decided for you by the policy · the Orchestrator's choice").
- **Not decided.** A decision the Orchestrator leaves stays open in the Inbox for the owner; nothing times out into an answer.
- **Instructions** (`plugin/roles/orchestrator.md`, 100 lines): "Asked to decide (the owner delegated its class to you): choose as the owner would with `bm_decide`, your reason in one line."; the tools line names `bm_decide` "(a delegated decision)".

### B.6 Precedents

`<data>/autonomy/precedents.json`: `{ id, scope: <workspaceId> | all, subject, text, sourceDecisionId, createdAt, expiresAt (default 30 days), supersededBy }`. Created from an answered decision (**Save as precedent** on its card) or by the owner in Settings. At agent creation the hook appends `## Owner precedents` (active, the workspace's and global, newest 20) to the Manager's and the Worker's runtime facts. A decision opening with a `subject` equal to an active precedent's is resolved by it when its class is not `owner`-fixed, citing the precedent; otherwise the precedent is shown on the card as a suggestion.

Detail as built (bead `bm-autonomy-phase2-t9lm.12`; injection and resolution are `t9lm.13` and `t9lm.14`):
- **Record** (`shared/precedents.ts`, pure). `id` is `p:<uuid>`; `subject` follows `SUBJECT_PATTERN`; `text` is at most 1,000 characters, an option label's cap rather than own words' 4,000, since it goes into agents' runtime facts; `sourceDecisionId` is null for one added in Settings.
  - `isActive(p, now)`: not superseded, and `expiresAt` later than now.
  - `activeFor(precedents, workspaceId, now)`: the workspace's and the global ones, newest first by `createdAt`.
  - The text an answered decision gives is its option's label, else the owner's words. A chat answer the owner confirmed has none, so the owner writes it.
- **Store** (`server/precedent-store.ts`): `{ version: 1, entries }`, with the policy store's file rules (0700 folder, 0600 file, atomic replace, no symlink, no lock).
  - An entry that does not validate, or repeats an id, is skipped alone and dropped by the next write. A newer `version` reads as none and is never written.
  - A save supersedes every active precedent of the same scope and subject in the same write (REQ-124 c). An expired one is left as it is. Supersession compares the text: an owner answer on the subject whose words differ from the precedent's — even one that means the same, such as an option label worded otherwise — ends it (seen in the Phase 2 live check, 2026-09-30); a precedent saved with the option's own label avoids that.
  - **End** sets `expiresAt` to now; ending one already inactive writes nothing.
  - Every active precedent is kept, and the 500 newest inactive ones. The cleanup button deletes `autonomy/` with them.
- **RPCs** (`server/autonomy-rpc.ts`, beside the policy's). No agent tool saves or ends a precedent. Every refusal writes nothing.
  - `precedents.list { workspaceId? }` → `{ precedents }`: active only, newest first. No usable data folder, or an unreadable store, reads as none (one log line). `readActivePrecedents` is the same read for the plugin's own readers.
  - `precedents.save { decisionId?, scope, subject?, text?, expiresInDays? }` → `{ precedent, superseded }`, `expiresInDays` 1–365 (default 30).
    - With `decisionId`: the decision must be answered **by the owner** (not by the Orchestrator, the policy or a precedent) and carry a subject. The scope is `all` or the decision's own workspace; a given subject must be its own; a given text replaces the answer's.
    - Without it: `scope` (`all` or a workspace id), `subject` and `text`.
    - Checked in this order: the input alone → `E_PRECEDENT_INVALID`, before the data folder is looked at; no usable data folder → `E_DATA_HOME_UNAVAILABLE`; an unknown decision → `E_DECISION_NOT_FOUND`; a decision that cannot become a precedent → `E_PRECEDENT_INVALID`; a newer or unwritable store → `E_PRECEDENT_WRITE_FAILED`.
  - `precedents.end { id }` → `{ precedent }`. Not a precedent id → `E_PRECEDENT_INVALID`; unknown → `E_PRECEDENT_NOT_FOUND`.
- **The card** (`client/chat-card.tsx`; `precedentOfferView` in `chat-card-precedent.ts`). A decision the owner answered, with a subject, shows **Save as precedent…**, a secondary button; the Inbox's card is the same card.
  - It opens in place: what a precedent does, the answer to keep (prefilled, editable), **This project** / **All projects**, then Cancel first and **Save precedent** — one `precedents.save` with the decision's id.
  - Once saved, the card says for where and until when.
- **Settings → Autonomy → Precedents** (`client/settings-precedents.tsx`; model in `settings-autonomy-model.ts`), below the matrix. Read once when shown, and again after each change there or on a card.
  - Each active precedent, newest first: subject · project (by name, *All projects*, or *Unnamed project* — never an id), the answer, until when and the days left, and whether it came from your answer or was added in Settings.
  - **End** on each, with its confirmation in place, Cancel first.
  - **Add precedent…** opens a form: the matrix's projects and *All projects* (the project shown is chosen first), the subject (checked as typed), the answer, Cancel first.
- **Injection** (bead `bm-autonomy-phase2-t9lm.13`; `server/role-instructions.ts`, renamed from `role-extras.ts` in `t9lm.16`, and `server/role-hook.ts`). `runtimeFactsText` adds `## Owner precedents` after `## Runtime facts`, for the Manager and the Worker only; the instructions are the role file, the runtime facts and the precedents, nothing else. One line per precedent, ``- `<subject>` — <text, on one line> (this project | all projects, until <YYYY-MM-DD>)``, newest first, at most 20 (`MAX_INJECTED_PRECEDENTS`); none → no heading.
  - The workspace: `manager.ensure` and a fallback Manager pass their own (`readInstructions(workspaceId)` → `currentInstructions(…, { workspaceId })`). The `agent.create` hook resolves it from `config.cwd`: the one live workspace `workspaces.list` gives that folder (`workspaceOfFolder`). None, several or an unreadable list → only the global precedents, never another project's.
  - Read with `readActivePrecedents`, in parallel with the mode and skill lookups and inside the hook's time budget. A read failure injects nothing, logs one line and never blocks the creation. A `BM-SETTINGS` notice (`childFactLine`) reads none.
  - The hook keeps a Manager prompt `manager.ensure` already built (its role text followed by Runtime facts, precedents or additions), so a store read a moment later never adds a second copy.
  - Only at creation: an existing agent keeps the precedents it started with. `bm.instructions` hashes the role file only, so precedents never make an agent outdated (§A.11).
  - The role files (§A.11): the Manager's brief carries the precedents that bear on the request in its **Context**; the Worker looks at its `## Owner precedents` before asking, follows and cites (by `subject`) one that answers the question, and asks what it leaves open, or what rule 1 guards, with that `subject`.

Resolution as built (bead `bm-autonomy-phase2-t9lm.14`; `server/precedent-resolve.ts`, the rules pure in `shared/precedents.ts`):
- **Which precedent** (`precedentFor`): an active one with the decision's `subject` that holds in its workspace — the workspace's own before a global one, the newest of each. A decision without a subject matches none.
- **At open, before any policy delegation** (`resolveByPrecedent`), where each kind opens: the materialiser (`q:`), `bm_ask_owner` (`o:`), a new fallback incident's listener (`f:`). `precedentResolutionOf` decides:
  - A class that is not hard-owner is answered: `by: precedent`, `via: inbox`, its `precedentId`, the `reason` `The owner's precedent on "<subject>" [for all projects], saved <day>`, the `class`, at the time it is resolved. The answer is the option whose label is the precedent's text (whitespace aside), else the text as the owner's own words, with the grant an owner answer of that form gives — never a hard-owner effect, which would have made the class hard-owner. An `owner` or `shadow` cell does not stop it.
  - Release, data, security or cost: the decision stays open and nothing is written.
  - A fallback incident's decision (subject `fallback-<role>`) only with one of its options, since own words run no action, and only where its delivery can run at once: a new incident's listener hands the pass `fallback.act`; the start-up pass and the pass after an action do not, and leave it open.
  - The materialiser leaves to the owner a subject a precedent already answered in the same request: asked again, the same answer did not do. The re-ask is a reversal of that answer as any other (§B.3).
- **Delivered as an owner answer**, through `onSettled`. A `q:` answer's `BM-DELIVERY` cites it on one line per such question above the block (`Qn was answered by the owner's precedent <id> on "<subject>": it is the owner's standing answer.`); an `o:` answer's `BM-ANSWER` has a `precedent:` line; `bm_ask_owner` says it was answered at once and adds `answeredBy` and `precedentId` to its JSON. A `q:` resolved at open reaches the event bus answered, so no `decision.opened` goes out for it. A precedent's answer is not an Orchestrator intervention (§G.3) and is not logged as one.
- **The suggestion** on the card (`precedentSuggestionView` in `chat-card-precedent.ts`): while an open decision with a subject is shown, the card reads `precedents.list { workspaceId }` (one query per project). When an active precedent bears on it — a hard-owner class, a subject asked again, or a precedent saved after it opened — it shows "Precedent: <text> (saved <date>)" and **Use this answer**: its option as a tap on that option (a release, data, security or cost effect asks its confirmation first), or the own-words box filled with its text for the owner to send. **Use** is not offered while a confirmation or the own-words box is open, nor for a fallback incident's words. The Inbox's card is the same card.
- **Answered by a precedent**, the card says "answered by your precedent · <time>" (own words as "Your precedent: …"); Details has `Answered by: your precedent <id>` and the reason. Such an answer cannot be saved as a precedent in turn.
- **Supersession** (REQ-124 c; `supersedePrecedentsBy`, after `decisions.answer` and after the owner's answers the materialiser settles): the owner's answer with a text — an option's label or own words — on a decision with a subject supersedes the active precedents of that subject that hold in its workspace, in the order they apply, up to the first whose text it repeats; so the next decision meets the owner's latest word. `supersededBy` is then the decision's id: the field takes a precedent id or a decision id. A chat answer the owner confirmed has no text and supersedes nothing. The store's `supersede` writes once, and refuses a superseder that is neither id.

### B.7 Digest and override

Inbox → Decided for you: decisions answered `by: policy` or `by: precedent` since the owner last opened the Inbox, one line each with the reason; **Override** opens the decision as a new owner decision (`supersedes` the delegated one), which counts as an override for B.4.

Detail as built (bead `bm-autonomy-phase2-t9lm.15`):
- **Last look** (`server/inbox-seen-store.ts`, `<data>/inbox/seen.json` = `{ version: 1, seenAt, since }` on the JSON store factory). `inbox.seen {}` → `{ since, seenAt }`, called on each Inbox read while it is shown. A visit lasts while the Inbox is shown again within `INBOX_VISIT_GAP_MS` (5 min); within a visit `since` stays, and the next visit starts at the previous `seenAt` (never seen → `null`, everything listed). It writes at most every 30 s. No usable data folder → `E_DATA_HOME_UNAVAILABLE`; a newer or unwritable file → `E_INBOX_WRITE_FAILED`.
- **Digest.** `inbox.digest { since?, workspaceId? }` → `{ decisions, truncated }`: decisions answered `by: policy | precedent` after `since`, latest first, at most 100; reads only. Since bead `t9lm.23` it also answers `interventions` (the Orchestrator's intervention log entries after `since`, newest first, at most 100, with `interventionsTruncated`; each entry as stored plus `targetRole` — `manager`, `worker`, `owner` or null — and `reason`, redacted on read, one line, at most 300 characters: a command's `why`, an answer's reason or the advice question's first line). A log that cannot be read counts as empty, with one log line. The Inbox shows "Decided for you · N" (not counted in the tab), one line each — the question's first line → the answer, then the project · "your policy (recommended option)" | "your policy (the Orchestrator)" | "your precedent", the reason and the time — ids under Details. Empty: "Nothing was decided for you since you last looked."; more than 100: "More was decided for you than the Inbox shows; Work has every decision." **Override** sits under the line on a phone and at its end on a wide screen; one press, no confirmation (it answers and sends nothing, and it demotes, the safe direction).
- **Override** (`decisions.override { id }` → `{ decision, overridden, created }`, `server/decision-override.ts`). In one synchronous write it records the reversal `overridden` on the delegated decision (which stays answered and delivered) and opens `r:<uuid>` with the same request, asker, question, subject and options, the answer's class and `supersedes` the delegated id; a second press returns the same override. Only the call that created it demotes (`demoteOnReversal`, §B.4: a `delegate` cell goes to `shadow` with the `autonomy-demoted` alert). An `r:` decision is never answered by a precedent or the policy (`resolveAtOpen`, `recommendedDelegationOf` and `precedentResolutionOf` skip it) and is refused by `bm_decide` and `bm_predict`; its card offers no precedent and reads "You are overriding an answer made for you. Your answer goes to the same agent and replaces it." Refusals: open, owner-answered or a Phase 1 Orchestrator answer → `E_DECISION_NOT_DELEGATED`; superseded, withdrawn or expired → `E_DECISION_SETTLED`. The override keeps the original's recommended prediction for the ledger; when the owner's answer differs from a precedent's, it supersedes that precedent.
- **Delivery** (`server/override-delivery.ts`, the `override` kind of `settledByKind`), by the overridden decision's kind: a `q:` goes to the request's sole Worker as `BM-DELIVERY answers` with a correction line ("The owner changed the answer to Qn …") then `BM-ANSWERS`, queue kind `override:<id>`, with a Worker answer's guarantees (§A.6: `queued` → `sent` when a Worker turn record carries it or the queue no longer holds it; once per plugin run every undelivered one is sent again); an `o:` sends the chosen option's command on `authority: decision:r:…` through `command-send.ts` (counted by the loop guard, never refused), or a `BM-ANSWER` with an `overrides:` line; an `f:` runs `fallback.act` while its incident is still pending. An open override of a `q:` expires with its request's questions at the `finished` report (§A.3).
- **Known limitation:** the fallback handover still lists the delegated answer, not the owner's override.

### G.1 The loop and the ladder

**The loop.**
- Code observes (trace records, reports, decisions, alerts, tokens) and detects (a threshold or an event). Only then is the Orchestrator woken (§A.8's rule: only a judgement wakes it).
- The Orchestrator diagnoses with its bounded read tools and picks the lightest intervention that will do.
- Code records the intervention with its expected outcome (G.3) and checks it after a window.

**The ladder**, lightest first:

| # | Intervention | How |
|---|---|---|
| 1 | Advise the Manager | a note, no command |
| 2 | Correct the Worker | a command, the Manager copied |
| 3 | Change the structure: compaction, handoff, a re-plan | a handoff always goes through the Manager |
| 4 | Stop | `interrupt` on a danger line |
| 5 | The owner | a decision |

**Who deals with the owner.** The Manager stays the owner's contact and the keeper of the request's context (PRD Q-100). The Orchestrator reaches the owner only through decisions and its own chat.

**What the Orchestrator never does:**
- skip or shorten a review or a check;
- waive a blocking finding;
- change what the owner asked;
- create, archive or delete an agent;
- read whole transcripts routinely.

### G.3 The intervention log and outcomes (Phase 2, REQ-127)

**The store** (as built, bead `t9lm.22`: `plugin/server/intervention-store.ts`, shape in `plugin/shared/interventions.ts`). `<data>/orchestrator/interventions.json` = `{ version: 1, entries: [...] }`, oldest first, with the store rules of §A.8: the folder `0700` created only by a write, the file `0600` replaced atomically, symlinks refused, a missing or corrupt file read as empty, an entry that does not validate skipped on its own and dropped by the next write, a file of a newer version read as empty and never written; the newest 2,000 kept. The cleanup deletes it with `orchestrator/`. Ids, times and enums only. Each entry: `{ id, kind, workspaceId, requestId, targetAgentId, trigger, expected, windowMs, at, outcome: pending | met | missed | unknown, checkedAt }`, plus what its check reads when the kind has it: `decisionId` (`answer`, `advice`), `alertKey` (the stall of an `unblock`; the `stuck`, `permission-waiting` or `danger` alert of a `correct`) and `signal` (the Worker signal of a `correct` or `stop`).

- `trigger`: `decision.opened`, `request.stalled`, `worker.signal`, `advice.due` (the event of the wake), `owner` (the owner's word in the Orchestrator's chat), or `orchestrator` (no event of its wake behind it).
- `expected`: `worker-resumes`, `stall-clears`, `signal-clears-or-checks-pass`, `turn-ends`, `tokens-per-turn-down`, `successor-progresses`, `owner-answers` — one per kind.
- Recording never holds back or fails the intervention: a store failure is one log line.

**Kinds**, each with its expected outcome and window:

| Kind | Recorded from | Met when | Window |
|---|---|---|---|
| `answer` | `bm_decide` | the Worker resumes | 10 min |
| `unblock` | a command on a `request.stalled` event | the stall alert clears | 15 min |
| `correct` | a command on a `worker.signal` | the signal clears, or the next report's checks pass | the next report, at most 60 min |
| `stop` | an interrupt | the turn ends | 2 min |
| `compact` | Phase 3 | tokens per turn over the next three turns ≤ 60 % of the three before | three turns, at most 60 min until Phase 3 checks it |
| `handoff` | Phase 3 | the successor's tokens per turn ≤ 50 % of the predecessor's last three, and the successor reports progress | 60 min |
| `advice` | G.4 | the owner answered the advice decision | 7 days |

**Which event a command answers** (as built). The event bus keeps the events of each Orchestrator wake in memory from its `BM-EVENTS` delivery to the end of that turn, beside the wake record (`wakeEventsOf`). A command `bm_send_command` or `bm_direct_worker` delivers in that turn is logged against them, after delivery:

- an `interrupt` is a `stop` (trigger the Worker's `worker.signal` when the wake carried one, else `owner` or `orchestrator`);
- else a `request.stalled` of the command's request is an `unblock` (a Worker's command without a request takes the Worker's);
- else a `worker.signal` of the Worker it went to is a `correct`;
- else, on the owner's word in the chat (authority `owner`), a `correct` with trigger `owner`; otherwise nothing is logged.

Every `bm_decide` answer is an `answer` to the Worker that asked, with trigger `decision.opened` when the wake carried that decision, else `orchestrator`. A reload forgets the events of the running wake: its commands then log only as the owner's. An `unblock`, `correct` or `stop` entry carries the `commandId` of the command it logs — its id in the commands store (`proposals.json`) — as an optional field; the file stays `version: 1`. A prepared command delivered on a decision's answer logs no intervention.

**The check** (as built). A pass on `agent.turn_ended`, throttled like the outdated-agents pass (once a minute), judges each pending entry from the stores. It runs at each turn end the collector records (its `onRecorded`), so it adds no lifecycle hook of its own and finds that turn's record in the store. It reads the decision store, the Inbox alerts and the trace records. It settles `met` as soon as the stores show the expected outcome within the window; `missed` once they show it did not come; `unknown` when the window is over and they cannot tell. An absence of evidence counts only a minute after the window ends, so a turn record written at its edge has landed.

- `answer`: met when the answer was sent to the Worker (`delivery.outcome: sent`), or one of its turns started, within the window. Missed when it was sent or resumed after the window, or the delivery is still `queued` or `failed`. Unknown with no delivery recorded and no turn, or the decision gone.
- `unblock`: met when the alert cleared within the window, or was cleared and raised afresh within it. Missed while it still holds after the window, or when it cleared late. Unknown when the alert is gone, or was raised afresh after the window.
- `correct`: met when the signal's alert cleared within the window, or the request's first report after the command, within the window, says its checks pass (`reportChecksOf` on `buildAndTests`). A signal without an alert (`failing`, `heavy`, `outside`) is settled by that report: missed when its checks fail, unknown when it names none or none came. A signal with an alert waits for the window's end: missed when the alert still holds or cleared late, or the report's checks failed.
- `stop`: met when the Worker's first turn from the interrupt on ended within the window; the turn it replaced does not count. Missed when that turn ended after the window, or none ended by then (a turn is recorded when it ends). Unknown without a Worker.
- `advice`: met when the owner answered the decision within the window. Missed when it is still open after the window, or was superseded, withdrawn or expired. Unknown when the decision is gone.
- `compact`, `handoff`: pending in the window, unknown after it, until Phase 3 checks them.

**Where it shows.**
- **The Inbox's Decided for you** (as built, bead `t9lm.23`, §B.7): the interventions since the owner last looked are merged by time with the delegated decisions, newest first (a decision first on a tie). A line reads the kind and its target ("Unblocked the Worker"), the project · the Orchestrator, the reason — what set it off, then the Orchestrator's words when a store kept them — and the outcome, Pending, Met, Missed or Unknown, each in its own tone with its expectation. No Override; ids (intervention, command, request, agent, decision, alert) only under Details. An Orchestrator answer's outcome joins its decision's line instead of a second line. More than 100: "The Orchestrator intervened more often than the Inbox shows; Insights → Coordination counts every intervention." The heading count includes these lines; the Inbox tab's does not.
- A-12 per kind appears in Insights → Coordination (as built): one card per kind used in the window, met / (met + missed) with pending and unknown apart, against the 80 % target. `insights.summary` carries `interventions`, one row per kind. The replay reports `a12.byKind` and a headline row (evaluation design §4).
- A compaction or handoff kind below A-12's target is switched off until it recovers, with an Inbox alert. Another kind below it becomes an advice finding (G.4).

### G.4 Proactive advice (Phase 2, REQ-128; replaces the workflow assessment, §B.9)

**The trigger.**
- Each `finished` report the collector records counts toward its project.
- When the count since the last advice reaches `advice.everyFinished` (Settings, G.7; default 5; 0 = off), the event bus publishes `advice.due` for that project. It is a judgement wake.
- The owner can also ask in the Orchestrator's chat at any time.
- For the Phase 2 exit ("advice at least once per active project"), an **active project** is one with at least `advice.everyFinished` finished requests in the window (change-007). In the earlier field's 15 days, 3 of 16 projects met that bar, and they held 50 of the 74 requests.

**The tool.** `bm_findings { workspaceId }` is bounded (about 4,000 characters) and returns the project's findings, each with its figures:
- repeated question subjects without a precedent;
- blocked rounds per request;
- review rounds and blocking findings per tier;
- stall reasons;
- the heaviest requests and the compaction or handoff candidates of G.2;
- intervention kinds below target.

**The action.** For each finding worth acting on, the Orchestrator asks with `bm_ask_owner`, and one option carries a **prepared change** the plugin applies on the owner's answer:
- `precedent.save`
- `autonomy.set` (a delegable cell)
- `coordination.set` (a threshold or cadence of G.7)
- `review.budget` (Phase 3): a `coordination.set` on one of the review-budget keys of §G.7 (`review.smallBudget`, `review.mediumBudget`, `review.largeBudget`), not a separate kind (change-008 C6)

With no finding worth acting on, it writes a note; the wake still counts as acted on.

**Never** text appended to an agent's instructions (the retired assessment).

Detail as built (bead `bm-autonomy-phase2-t9lm.25`):

OpenCode's result also depends on the owner's own OpenCode configuration, which Paseo does not isolate, and its next turn lost almost all of its prompt cache.
- **No provider needs the fallback** (a handoff or nothing).
- **Reading the context:** the figure reported right after a compaction understates the real one, so a threshold check reads the context at the **next** turn's end.
- **The message is the owner's to the collector unless the plugin says otherwise:** on all three the `/compact` is a `user_message` carrying `clientMessageId` (on Claude and OpenCode inside the compaction's turn; on Codex with no turn id). A leading `/compact` cannot tell it apart, since the owner may type one too. The plugin therefore keeps a **send log** of what it sent (agent, time, text hash), and the collector classifies a matching message as the plugin's, never as the owner's words (A-6, the owner's texts, the owner's word in chat).

**What wakes the Orchestrator:** a `threshold.crossed` event of kind `compact` (§G.7, change-008 C1).

**The tool.** `bm_compact { agentId, reason }` (Orchestrator), in a tool module registered in `orchestrator-tools.ts`. The target is a Manager or a Worker of a project, never a Reviewer (short-lived) or the Orchestrator (it replaces itself). It is refused, writing nothing, when:
- compaction is off;
- the target is not a Manager or a Worker;
- the target is below its threshold (G.7);
- `compact.maxPerAgent` is reached. For a Worker, a handoff is suggested instead.

**The sequence.**
1. Wait for the target's next idle moment after a safe point: a Worker after a report; a Manager with no notice pending. Never inside a running turn (the notice queue).
2. The plugin sends `/compact` — with a focus from a fixed template on Claude (keep the request and the owner's words, the decisions taken, the plan and bead state, open review findings and files changed; drop tool output), bare on Codex and OpenCode — and records it in the send log.
3. It waits for the `compaction` item to complete.
4. It sends a **state brief** (`BM-STATE`, a plugin notice) built from the stores, so what matters is restored from artifacts rather than from the model's summary alone.

**As built** (bead `7gxw.10`). `bm_compact { agentId, reason }` lives in `server/orchestrator-coordination-tools.ts`; refused, writing nothing, in this order: compaction off; the target the Orchestrator, a Reviewer, not a paseo-bm Manager or Worker, archived or in no project; a compaction of it pending; `compact.maxPerAgent` reached (a Worker's refusal names `bm_handoff`); its provider cannot compact; its last measured turn below the threshold, or none measured since its last compaction. The provider comes from the alias's `extends`, else the turn's model id. Accepted: a `compact` intervention (trigger `threshold.crossed` when the wake carried that agent's event, else `owner` when the owner just spoke, else `orchestrator`), the compaction recorded with its reason masked, and a reply saying whether the `/compact` went now, is queued or waits. The runner (`server/compaction.ts`) sends at a safe point — a Worker's turn that just sent a `BM-REPORT`; a Manager's idle moment with no notice queued — as a one-item batch through the notice queue (Claude `/compact <COMPACT_FOCUS>`, Codex and OpenCode bare); a `/compact` held while the target turned busy is dropped after 60 s and sent again at the next safe point, never doubled; the next recorded turn with a completed `compaction` item (Codex: its own `autonomous-…` turn) triggers the `BM-STATE` brief. States `waiting | compacting | done | failed | dropped`; 60 min to find a safe point, 10 min for the compaction. **The send log** (`server/compaction-store.ts`, `<data>/orchestrator/compactions.json`, deleted with the folder): `{ agentId, at, hash, compactionId }` — the SHA-256 of the trimmed text, never the text — written just before the send; the collector records a would-be owner `user_message` of that agent with that hash, from 60 s before to 30 min after, as `origin: "agent"`, never parsed as a report. **The brief** (`BM-STATE`, now a plugin notice) tells the agent to reply "noted" and end its turn: a Worker's holds its request id and the owner's first words, up to 3 later owner messages, up to 8 decisions with their answers and the report facts (phase, tier, files, beads, open findings, checks, `decided`, blockers); a Manager's its 5 newest requests (phase, Worker, open decisions, written `- req-…`) and the owner's 3 newest messages; masked, at most 6,000 characters. **The outcome** (§G.3): from the `/compact` being sent, at most 60 min, the mean tokens read over the next 3 measured turns against the 3 before — met at 60 % or less, else missed (the compaction's own turn and OpenCode's repeat turns left out; judged on 1–2 turns when the window ends early); unknown when the compaction never went out or no turn compares — so the A-12 guard (§G.7) can fire. The `threshold.crossed` event carries a `cycle` (the `/compact`s sent to that agent), is raised from `turnRecorded` (a turn holding a compaction is never judged), goes to every project and is dropped at delivery when compaction was turned off, the agent compacted, or a compaction was requested meanwhile. Work's live view (`live-timeline.ts`) checks typed messages against the send log with the collector's own matcher (`pluginSentBeside`) and leaves the plugin's `/compact` out of the owner's messages; `BM-STATE` is recognised by its marker and shown in chat as "State restored after compaction". Inbox → Decided for you reads a `compact` line's target role and masked reason from the compaction store (by its `interventionId`). The Manager handover drops what the send log says the plugin sent (bead `7gxw.11`).

### G.6 Handoff (Phase 3, REQ-135)

**What wakes the Orchestrator:** a `threshold.crossed` event of kind `handoff` (§G.7, change-008 C1).

**The tool.** `bm_handoff { workerId, reason }` (Orchestrator). It is refused, writing nothing, when:
- handoff is off;
- the target is not the Worker of an unfinished request;
- `handoff.maxPerRequest` is reached;
- the request is below its threshold.

When the Worker is not at a safe point, the request waits for the next one. Safe points are a bead closed with evidence (`bead-implemented`), `beads-done`, or a review verdict received.

**The sequence.**
1. **The outgoing Worker's note.** At the Worker's idle moment the plugin asks it for a short note: `bm_report` with `handoffNote`, at most 1,500 characters, saying what was tried and what is next. It waits for it within a bound (10 min) and goes on without it after.
2. **The brief.** The plugin builds it, bounded to about 6,000 characters, and keeps it at `<data>/handoffs/<id>.json`, written with the `data-files.ts` rules and masked with `redactText`; the cleanup deletes `handoffs/`. It extends the fallback Worker handover (`workerHandover`, `fallback-handover.ts`), which already gives the latest report, the review calls, the request's questions with their answers and the original request, built from the stores (change-008 C3). It holds:
   - the request and the owner's words;
   - the decisions taken;
   - the plan and doc paths;
   - the bead state (done, ready, blocked);
   - the last report (files, checks);
   - open review findings;
   - the branch and diff stat;
   - the note.
3. **The command to the Manager.** `BM-COMMAND`, carrying the brief's id: `intent: handoff`, `authority: coordination:handoff`, `effects: none`, `approved: none`, `to: manager` (change-008 C3).
   - *The authority* is the owner's Settings switch. None of the authorities Phase 2 kept (a grant, the policy, the owner's word, §B.8) covers a handoff that ADR-021 lets the Orchestrator ask for on its own.
   - *Its checks:* the builder refuses `coordination:handoff` for any other intent, and the send refuses it while handoff is off. It goes through `command-send.ts` (counted by the loop guard), and its card reads "Coordination · handoff".

   The Manager:
   - creates the successor with `create_agent` (provider `bm-worker…`), the rendered brief as its first message and `bm.handoffFrom=<old>` among its labels, beside `bm.role` and `bm.requestId`. The creation hook adds instructions and runtime facts as for every Worker. It cannot set labels: Paseo 0.9.2's `before("agent.create")` sees `{ config, env }` only;
   - tells the outgoing Worker it is replaced. On `agent.created` the plugin checks the successor's label and labels that Worker `bm.replacedBy=<new>` through `paseo-cli.ts`, as the fallback switch does. Delivery, the materialiser and the chat peers already skip a replaced Worker. It stays idle and is never archived.
4. **The request continues.** It keeps its request id: Work's timeline shows the handoff, and the Worker's reports continue.
5. **The successor proves again.** Its brief says to run the checks again before reporting anything done. Phase 3's detected evidence (C.2) holds it to that.

**Role text.**
- The Manager gets one bullet: executing a handoff.
- The Worker gets one bullet: the handoff note and working from a brief.
- Both within their budgets (Manager 118 of 120 lines, Worker 248 of 250 at the Phase 3 start): reword, do not add. The Manager's bullet names the `bm.handoffFrom` label.

**As built** (bead `7gxw.11`; `shared/handoff.ts`, `server/handoff.ts`, `server/handoff-store.ts`). `bm_handoff { workerId, reason }` (in `orchestrator-coordination-tools.ts`) is refused, writing nothing, when handoff is off; the target is not the live Worker of an unfinished request (not a Worker, archived, no project, no `bm.requestId`, already `bm.replacedBy`, or the request finished); the Worker has no live Manager; a handoff of the request is pending; `handoff.maxPerRequest` is reached; the request's tokens since it started (or since its last handoff) are below `handoff.requestTokens`; or the loop guard is full. Accepted: a `handoff` intervention and the runner's entry (states waiting → noting → briefed → commanded → done, or dropped / failed with an ending). **The note:** at the Worker's idle moment after a safe point (a successful `br close`, a `beads-done` / `bead-implemented` report, or a verdict of its own Reviewer) the plugin sends a `BM-HANDOFF` notice; the Worker answers with `bm_report`'s optional last field `handoffNote` (≤ 1,500 characters), which the collector records. With no note, the runner goes on at once when the note turn ends without one, else after 10 minutes at the next recorded turn. **The brief** (first line `BM-HANDOFF-BRIEF <id>`, at most 3,200 characters so it travels inside the 4,000-character command body; the stored file keeps the brief and the full note at `<data>/handoffs/<id>.json`, deleted by the cleanup) is built on `workerHandoverFacts` (extracted from `workerHandover`, whose output is unchanged): the owner's words, questions and decisions, plan and document paths, bead state, the last report and checks, open findings, branch and diff stat (read-only git) and the note, masked. **The command:** `intent: handoff` with `authority: coordination:handoff` only together, from the Orchestrator to the Manager, no copy, no effects, both fixed limits and no backstop (its body is the plugin's brief); refused while handoff is off; through `command-send.ts` (counted by the loop guard); sent when the Manager is idle with nothing queued, waiting up to 30 minutes; the card reads "Coordination · handoff". `bm_send_command`, `bm_direct_worker` and prepared commands cannot declare `handoff` (`DECLARED_COMMAND_INTENTS`). **The successor:** on `agent.created` (through `agent-labels.ts`'s existing hook), a Worker labelled `bm.handoffFrom` created by that Manager, in that workspace, for that request completes the handoff; the old Worker is labelled `bm.replacedBy` through `paseo-cli.ts` and never archived; the request keeps its id and the pairing check passes; a late successor (after 30 minutes) still completes it. **Proves again:** a check counts only if run after the request's last handoff (`evidence.ts`), which Work, the finished card, `request.finished` and the delegation refusal all read. **The event:** `threshold.crossed` kind `handoff`, key `threshold.crossed:handoff:<requestId>#<handoffs so far>` (only handoffs whose successor appeared count; tokens count again from the successor's creation), dropped at delivery when handoff is off, the request was handed over or has one pending, or it finished; its line names `bm_handoff`. **The outcome** (§G.3): from the successor's creation, met when its first three turns read at most 50 % of the old Worker's last three and it reports anything but `blocked` within 60 minutes; missed above 50 % or with no report; unknown with no successor or no turns to compare — so the A-12 guard can switch handoff off. The replacement Manager's handover drops a message the plugin's send log says it sent (`pluginSentBeside`). Work's timeline shows "Handed over to Worker 2 from Worker 1".

*After the Phase 3 live check* ([run note](../archive/operations/paseo-bm-phase3-live-check-20260930.md)): a Manager may pass the brief without its first line, so a successor is recognised by its `bm.handoffFrom` label (read into the agent facts, `handoffSuccessorsOf`), the `BM-HANDOFF-BRIEF` line being a second signal; "proves again" counts only checks run after that Worker's first recorded turn; `traces.get` carries an optional `handoffs: [{ agentId, from }]` that Work's timeline reads. The Manager's own message to the outgoing Worker may not arrive, so on the successor's `agent.created`, after `bm.replacedBy`, the plugin itself queues a `BM-REPLACED` notice to it (change nothing more, send no report, end the turn, stay idle); its chat card reads "Handed over to another Worker". A-7 counts a `compact` or `handoff` intervention recorded within a wake as its action.

*As built* (bead `7gxw.9`): the file is `{ version: 1, advice, compact: { enabled, managerTokensPerTurn, workerTokensPerTurn, contextShare, maxPerAgent }, handoff: { enabled, requestTokens, maxPerRequest }, guard: { compact, handoff } }`, each setting read on its own (a Phase 2 file reads the new ones as their defaults). Bounds (`COORDINATION_BOUNDS`, `coordinationRuleOf`; a value out of bounds → `E_COORDINATION_INVALID` with the key's rule): token thresholds 50,000–100,000,000 (request 10,000,000–1,000,000,000), whole; `contextShare` 0.1–0.9; `maxPerAgent` and `maxPerRequest` 1–5; switches true or false. `compact.enabled` is one switch, on for `COMPACTION_PROVIDERS` (Claude, Codex, OpenCode — all passed G.5; `compactionOnFor`). The crossing rules are pure (`shared/coordination.ts`): `compactCrossingOf(role, { coverage, tokensRead, contextShare })` — tokens read against the role's threshold only when the provider counts the whole turn, the context share on any turn, either crossing counts (reaching it is crossing), an unknown provider by its context share only; `handoffCrossingOf(requestTokensRead)`. Each returns `{ figure, value, threshold }` for `threshold.crossed`.

**Switched off under A-12** (`server/coordination-guard.ts`, wired after the intervention check). A mechanism that is on is judged over its newest 10 met-or-missed entries recorded since the owner last turned it on (`guard.<kind>.countsFrom`); fewer than 10 → no judgement. Below 80 % the store switches it off (`switchOff`, which can only switch off; `guard.<kind>.switchedOff = { at, met, checked }`) and one `coordination-off` Inbox alert is raised for all projects ("Only 6 of its last 10 compactions met their goal (target 8). Compaction stays off until you turn it on in Settings → Coordination."). Only the owner turns it back on — in Settings, or by answering advice that carries `coordination.set` — which sets `countsFrom` to now, clears `switchedOff` and ends the alert. Beads `7gxw.10` and `7gxw.11` check the outcome of `compact` and `handoff` entries, so the guard can fire. Settings → Coordination shows an Advice card and a Compaction and a Handoff card (status; Turn off at once, Turn on… after a confirmation with Cancel first; thresholds with − and + on a 1-1.2-1.5-2-2.5-3-4-5-6-8 ladder, the context share by 5 points; Save and Use the defaults). `coordination.set`, and a prepared `coordination.set`, accept all nine keys.

**The defaults as derived at the Phase 3 start** (bead `bm-autonomy-phase3-7gxw.1`; evaluation baseline report §6).
- **The data:** the replay of the whole store on 2026-09-30, 62 requests (59 finished) from 2026-09-16 and 2,056 turns with usage (Manager 958, Worker 812). Nearly all of it is earlier field data: the Phase 1 build has one request, and the fixed build none.
- **The figures:** the p75 of tokens read per turn is 388,524 for the Manager and 5,713,582 for the Worker, and the request p80 is 150,553,952. The defaults are these, rounded to two significant figures; the earlier field alone gives the same within 1 %.
- **The candidates:** at those thresholds, compaction would have been proposed for 44 of 70 Workers (at a median third turn) and 6 of 15 Managers. Handoff would have been proposed for 13 requests, the heaviest fifth; their estimated saving is at most 34 % of the tokens they read.
- **Every saving is an upper bound.** A 1,500-token re-read is assumed after the crossing, and the call counts are lower bounds, since the field has no `toolCalls` yet.
- **`compact.contextShare`** keeps the design's 0.5: no context is reported in the field until the Phase 2 collector is installed.
- **Re-checked in the combined field period** (beads `t9lm.18`, `i8fc.6`). There, compaction and handoff lower the very distribution they are set from, so the re-check compares that window's figures with these before changing a default.

**Which figure a turn is judged by** (change-008 C2). A turn's tokens read are compared with its role's `compact.*TokensPerTurn` only when its provider counts the whole turn (Claude, `TOKEN_COVERAGE` `turn`). On Codex and OpenCode a turn reports its last call only: its tokens read are about its context, and the p75 of turn sums would never be reached. Such a turn is judged by `compact.contextShare` alone. Either figure crossing counts. `handoff.requestTokens` compares the request's tokens read since it started, or since its last handoff.

**The threshold event** (change-008 C1). Code detects a crossing and wakes the Orchestrator with `threshold.crossed { workspaceId, requestId, agentId, role, kind: compact | handoff, figure: tokensPerTurn | contextShare | requestTokens, value, threshold, at }`. It is raised from the collector's `onRecorded`, for a Manager's or a Worker's turn.
- **When `compact` is published:** while compaction is on for the agent's provider, the agent is below `compact.maxPerAgent` and no compaction of it is pending.
- **When `handoff` is published:** for a Worker's turn of an unfinished request, while handoff is on and the request is below `handoff.maxPerRequest`.
- **Scope:** every project, as `advice.due` is. The owner's Settings are its scope, not the autonomy policy.
- **Dropped at delivery** when the mechanism was turned off, the agent compacted, or the request was handed over or finished meanwhile.
- **One per cycle:** its dedupe key is `threshold.crossed:compact:<agentId>#<its compactions so far>` or `threshold.crossed:handoff:<requestId>#<its handoffs so far>`.
- **Its `BM-EVENTS` line** names `bm_compact` or `bm_handoff`.
- **A judgement wake.** The Orchestrator may leave it with a `bm_note`, which A-7 counts as acted on.
- **Its trigger** in the intervention log is `threshold.crossed`, added to `INTERVENTION_TRIGGERS` (the store stays `version: 1`).

**The review budget** (change-008 C6).
- **What they hold:** the three `review.*Budget` settings are the review calls per request of each tier, `REVIEW_BUDGET`'s numbers until the owner changes them.
- **Who reads them:** `review-budget.ts` (the budget notice and the stall pass's `review.over-budget`). A new Worker gets them in its `## Runtime facts`, and worker.md's budget line points there, within its budget. An existing Worker keeps the budget it started with.
- **Bounds:** never below one review and its re-review (§G.8).
- **Who changes them:** only the owner, in Settings → Coordination or by answering advice whose option carries `coordination.set` on one of these keys. That change is §G.4's `review.budget`; no separate prepared-change kind is built.

*As built* (bead `7gxw.12`): the file adds `review: { smallBudget, mediumBudget, largeBudget }` (whole 2–8, defaults 2 / 2 / 4, `REVIEW_BUDGET_KEYS`, `reviewBudgetOf`); `coordination.set` and a prepared `coordination.set` accept all twelve keys. `readReviewBudget` (`coordination-rpc.ts`, an unreadable store reads 2 / 2 / 4) is read by `review-budget.ts` (the Manager's notice and `review.over-budget`), the stall pass (once per pass) and `fallback-handover.ts`. ### G.8 Guardrails and measures

**Quality comes first.** No review, check or blocking finding is traded for tokens or time. A-8's Phase 3 target on the heaviest requests holds only with no rise in:
- blocking findings per review batch;
- A-5;
- the finished-unverified share.

**Bounded.**
- Each intervention is logged (G.3), shown in the digest and measured (A-12).
- Settings switches compaction and handoff off at once.
- Hard-owner effects keep their grants (§A.3).
- Agents belong to the owner.

**A-7 still holds** (< 20 % of wakes with no action): `advice.due` and the threshold events (`threshold.crossed`, §G.7) are judgement wakes, and the Orchestrator's own tokens are part of A-8.

**The Phase 3 exit's window and references** (change-008 C7; bead `bm-autonomy-phase3-7gxw.7`).
- **Window:** the combined field period's whole window (≥ 14 days from the final build's install, change-006/007), not its first 10 requests.
- **A-8's target** (−20 % on the heaviest 20 %, kept at the Phase 3 start: the replay's upper-bound estimate for the heaviest fifth is 34 %):
  - *The figure:* the p90 of Worker tokens read per request, which is the median of the heaviest fifth.
  - *The reference:* the same figure over the field before the final build's install, read at the combined period's start (`i8fc.6`) and recorded in the baseline report. As of 2026-09-30 it is 298,250,986 over 58 requests (§6.5 there).
  - *Why not the Phase 2 field:* under change-006 no Phase 2 build runs in the field without these mechanisms, so there would be no Phase 2 field figures to compare with.
  - *Minimum:* it needs ≥ 25 finished requests with usage (≥ 5 in the heaviest fifth); below that it is reported and the verdict reasoned, not passed.
- **The quality guardrails:**
  - blocking findings per review batch, against the same pre-install reference (1.46 as of 2026-09-30);
  - A-5, against the owner's own rate;
  - the finished-unverified share, which has no earlier value, so it is compared between the window's requests with a compaction or handoff and those without.
- **A-12** for `compact` and `handoff` is judged over every entry checked in the window. A kind with fewer than 10 checked entries is reported with its count, not called met.
