## 0. Principles (from the PRD §3) and what they mean in code

1. **Artifacts, not conversation.** A handoff is a typed record with one identity; chat text is a view of it.
2. **Workflow before agent.** Routing, ordering, deduplication, limits, authority are code. A model is woken only for judgement.
3. **Control matches risk** through declared effects, the owner's policy and one-use grants — never through prose patterns alone.
4. **Measure before promoting.** Every phase exit is judged on the replay; the evaluation suite (Evaluation design §6) runs once, at the programme's end.
5. **Delete what is superseded** in the same phase (§A.14, and each Part's retirement list).

**One idea carries Parts A and B: agents keep writing typed blocks with side-effect-free tools (ADR-010), and the plugin materialises state from those blocks at the end of the turn that wrote them** — keyed idempotently, because Paseo reuses turn ids. The Orchestrator, whose endpoint knows its caller (the secret path), writes state directly, and so do a bound agent's own tools (ADR-027: `bm_questions`, a Main's `bm_answer_worker`), through the same open and answer paths.

## Part A — Phase 1 MVP: one source of truth for decisions and handoffs

### A.1 Scope

Owns: the decision model and store; materialising decisions from blocks; answering and delivering; the Orchestrator's decision tools, prepared actions and grants; typed commands (`BM-COMMAND` v2) and authority from declared effects; fallback incidents as decisions; the event bus to the Orchestrator and the Inbox's alerts; bounded coordinator context; capability limits per role; the rewritten role instructions; the new management surface and card system; the Phase 1 retirement.

Does not own: decision classes, policy and delegation (Part B); evidence classification (Part C); holding actions before they run (Part D); missions, Mains and the governor (missions design); who decides a decision (the authority resolver, mission runtime design §4.1).

### A.3 The decision model

`plugin/shared/decisions.ts` (zod, shared by server and client):

| Field | Meaning |
|---|---|
| `id` | Deterministic key (`DECISION_ID_PATTERN`): `q:<requestId>:<Qn>` (Worker question), `o:<uuid>` (Orchestrator), `f:<incidentId>` (fallback), `r:<uuid>` (the owner's override, §B.7), `h:<agentId>:<requestId>` (a held permission request, §D.2). A mission's own decisions (`m:<missionId>:<n>`) live in the mission decision store (missions design §4.1) |
| `workspaceId`, `requestId` | `requestId` null only for fallback incidents outside a request and Orchestrator decisions about a whole project (a Worker question always has one) |
| `askedBy` | `{ role: worker \| orchestrator \| plugin, agentId \| null }` |
| `askedAt`, `round` | first-seen time; the Worker's report round (for grouping on one card) |
| `question`, `subject` | text (≤ 1,000); `subject` a short slug the asker gives (`SUBJECT_PATTERN`, used by supersession and precedents) |
| `class` | §B.1; optional on records stored before classes |
| `options[]` | at most 8: `{ key, label, recommended, effects: Effect[], action?: PreparedAction, grant? }`; one recommended at most. `grant` is a `review-cap` option's `{ calls }` (delivery line design §5.4) |
| `effects` | `none, commit, push, publish, deploy, real-data, migration, dependency-install, network, outside-workspace, security, cost` — declared by the asker per option |
| `status` | `open → answered \| superseded \| withdrawn \| expired`; `open → needs-confirmation` when an owner message in a chat may have answered it (A.5 c) |
| `answer` | `{ by: owner \| orchestrator \| policy \| precedent \| main, via: inbox \| chat-card \| chat-manager \| chat-worker \| chat-orchestrator \| autopilot \| paseo \| main, optionKey \| words, at, reason?, class?, predictor?, precedentId? }`. `by: main` (only `via: main`) is a mission Main's answer (missions design §8). `by: orchestrator` (`via: autopilot`, Phase 1) and a stored `predictor` (builds before ADR-025; `policyPredictorOf`) are only read: `answerDecision` refuses a new `by: orchestrator` answer (`invalid-answer`) |
| `grant` | `{ effects, expiresAt, usedAt \| null }` — REQ-112 (b) |
| `delivery` | `{ to, kind, at, outcome: sent \| queued \| failed \| held }` (`held`: the wake gate holds it, delivery line design §6.4) |
| `supersedes`, `supersededBy` | ids |
| `prediction`, `reversals` | §B.3 |
| `ownerOnly` | a fact only the owner knows (missions design §5): only the owner's card or own words in the Worker's chat answer it |

Rules: a Worker question may re-ask with `supersedes: "Q3"` (new optional field of the `bm_report` question schema) or with the same normalised text → the old one becomes `superseded`. An Orchestrator decision supersedes the open Orchestrator decision of the same request unless it passes `separate: true`. A superseded, withdrawn or expired decision is never answerable; the tool that caused it returns the id it replaced. `bm_ask_owner` with a `requestId` is refused while an unsettled `q:` decision of that request has the same subject (ADR-028; [base design §7.17.8](./paseo-bm.md) (b)).

**Expiry of a Worker question.** A `q:` decision that is `open` or `needs-confirmation` expires when its request's `finished` report is recorded: at a Manager's turn end, a `BM-REPORT` with `phase: finished`, in an incoming message that is neither the owner's nor a plugin notice, expires every such question of the request the report names that was asked no later than the report (`settledAt` = the report's message time). The materialiser (`expireFinished`) writes each in its own store transition after the turn's openings and answers (§A.5), so an answer given meanwhile, or by the owner in the same turn, stands; a question asked after the report stays open. `o:` and `f:` decisions never expire this way; the owner's open overrides (`r:`, §B.7) of a request's questions expire with them, overrides of `o:` and `f:` decisions never do. An expired decision leaves the Inbox, is refused by `decisions.answer` (`E_DECISION_SETTLED`) and `bm_decide`, and is never delivered; its card reads **Expired** with "The request finished."

`PreparedAction` is a union: `answer-worker` (implicit for Worker questions: deliver the answer), `command { to: manager | worker, agentId, intent, body, effects }` (Orchestrator decisions; `bm_ask_owner` prepares commands to a Main only, missions design §9.1; `worker` is read on older records), `fallback { action: switch | wait | resend | dismiss, target }` (fallback incidents), and a prepared change of the owner's settings (`precedent.save`, `autonomy.set`, `coordination.set`, §G.4).

Two bookkeeping fields complete the record: `settledAt` (set exactly when the status is final) and `needsConfirmation { via: chat-manager | chat-worker | chat-orchestrator, at }` (set exactly while `needs-confirmation`). The transitions are pure functions in the same module (`answerDecision`, `markNeedsConfirmation`, `confirmDecision`, `supersedeDecision`, `withdrawDecision`, `expireDecision`, `recordReversal`, `useGrant`); each returns the next record or a refusal and never reads a clock. An answer grants the chosen option's effects, or every effect the decision declares for own words (`none` never granted; nothing to grant → no grant). An answer to an `o:` decision or to its override grants nothing (ADR-031), and neither does a Main's answer (missions design §4): the repo's action boundary decides those effects. A chat answer the owner confirms (`decisions.confirm`) records no option, no words and no grant, because the plugin never read what was authorised.

**Ask back thread** (change-014, `shared/decision-threads.ts`, pure): one per decision, `{ decisionId, entries: [{ by: owner | asker, text ≤ 2,000, at, agentId? }] }` — on the owner's entry `agentId` is the asker it went to, on the asker's the agent that replied when known. Only an unsettled `q:` or `o:` decision has one (`askableKindOf`): a held request's Worker is mid-call, a fallback incident and an override have no agent to ask. An ask is open while the last entry is the owner's (`hasOpenAsk`): one reply per ask. The thread never changes the decision, which stays open.

### A.4 The store

`plugin/server/decision-store.ts`: `<data>/decisions/<workspaceId>.json` = `{ version: 1, entries: Decision[] }`, `0600` files in a `0700` folder, atomic writes, on the JSON store factory (`createJsonFileStore`, `server/data-files.ts`): a missing or corrupt file reads as empty, a bad entry is skipped alone, a file a newer paseo-bm wrote reads as empty and is never written (a coded error), symlinks are refused, and no lock is needed because every operation is synchronous in the one plugin-server thread, so a read-modify-write cannot interleave. The alert, policy, precedent, intervention and coordination stores below follow the same factory rules. Open decisions are never evicted; settled ones keep the newest 500 per workspace. `decisions.list` reads every workspace file with an mtime cache. Cleanup deletes the folder; deleting a request's traces deletes its settled decisions. Opening is idempotent by id, and a `supersedes` naming an unsettled decision of the workspace supersedes it in the same write. Ask back threads (change-014, `server/decision-thread-store.ts`): `<data>/decisions/threads/<workspaceId>.json` = `{ version: 1, threads }`, same factory rules, text masked before it reaches the disk, the newest 20 entries per decision and 500 threads per workspace; deleted by the cleanup with `decisions/`.

### A.5 Materialisation (`plugin/server/decision-materialiser.ts`, on the collector's `onRecorded`)

The `BM-QUESTIONS` block carries the new fields as optional bracketed tags, so the text stays readable and older blocks still parse (each tag is optional; an unknown tag is ignored):

```
BM-QUESTIONS
requestId: req-20260929T073348Z
Q4: Push both backends to origin/dev? [subject: push-backends] [supersedes: Q2]
- a: Push contract only (recommended) [effects: push]
- b: Push both, manifest by hand [effects: push]
- c: Hold
```

`bm_report` gains the matching optional fields (`subject` ≤ 60 characters `[a-z0-9-]`, `supersedes` a `Qn` of the same request, `effects` per option from §A.3's list) and writes the tags; `parseQuestions` reads them; `bm-format.ts` accepts them.

a. **Open** — at a Manager's turn end, each `BM-QUESTIONS` in an inbound message that is not the owner's opens `q:<requestId>:<Qn>` if absent; re-reading the same turn (reused turn ids) changes nothing.
b. **Answer through the Manager** — at a Manager's turn end whose inbound messages include the owner's typed message (`origin: "user"`), each `BM-ANSWERS` block the Manager wrote in its reply (built with `bm_answers`) settles those decisions with `via: chat-manager`. The Manager sends no answer to the Worker; the plugin delivers (A.6).
c. **Answer in a Worker's chat** — at a Worker's turn end, an owner-typed message holding a `BM-ANSWERS` block settles the named questions (`via: chat-worker`); any other owner text in that Worker's chat while decisions of its request are open marks those **asked before that message** `needs-confirmation` (the message that started the turn in which the Worker asked cannot have answered it): the card says "You wrote in the Worker's chat at <time>. Choose an answer, or close it if that message answered it.", keeps the options and adds *Close as answered* / *Keep open*.
d. **Fallback** — each pending incident of `role-fallback-state.json` opens `f:<incidentId>` with the fallback actions (switch, wait, resend, dismiss) as prepared actions; resolving the incident any other way withdraws it.

Detail for a–c (`server/decision-materialiser.ts`):
- The collector hands `onRecorded` the record it just wrote (texts already masked); a–c read that record's `sent` (with `origin`) and `received`, never the store back. The block readers (`readableOf`, `questionBlockOf`, `answerBlockOf`) live here.
- Open: `askedBy.agentId` is the live Worker labelled `bm.requestId = <requestId>` (the Manager's child first, else the only one of the workspace), null when not known for certain. A block's questions share one round: the stored round of any of them, else the request's highest round plus one. `askedAt` is the carrying message's time. A `[supersedes: Qn]` tag links only a question that is stored; the text match (case, punctuation and spacing ignored) replaces only an unsettled question.
- Answer lines: a leading option letter (`a — …`, `(a) …`, `a: …`, a bare `a`) is the option when the decision has it; otherwise the line, without an `other —` prefix, is the owner's words. The answer's time (and so the grant's hour) is the owner's message time — the last owner message of a Manager turn. A Manager's replies are read one by one and joined, so a streamed block still reads.
- `needs-confirmation` applies to the open `q:` decisions of the Worker's request (the record's `requestId`) and is remembered by owner message (agent, time, text) for the plugin run, so re-reading a record never re-marks a question the owner kept open.
- The decisions a turn answered go to the same `onSettled` hook as `decisions.answer` (`settledByKind` in `index.server.ts`), which the delivery (A.6) completes.

A bound Worker (ADR-027) opens its questions with `bm_questions`, on this section's open path extracted and shared (`openQuestions`), and a bound Manager's `bm_answers` are proposed answers that the materialiser settles at the Manager's turn end by rule (b), only when the turn holds the owner's own message ([base design §7.15](./paseo-bm.md)). A Main answers a question its policy delegates with `bm_answer_worker` (`by: main`, `via: main`, missions design §8), delivered by A.6 like the owner's.

### A.6 Answering and delivery

RPCs (`plugin/shared/contracts.ts`, additive; handlers in `plugin/server/decision-rpc.ts`): `decisions.list { scope: inbox | workspace | request, workspaceId?, requestId?, status?, limit? }` → `{ decisions, truncated }` (`inbox`: unsettled decisions of every workspace or of `workspaceId`, oldest asked first; `workspace` and `request`: every stored one, newest asked first; `limit` ≤ 500, default 200; no usable data folder reads as none), `decisions.get { id }` → `{ decision }`, `decisions.answer { id, optionKey?, words?, confirmed?, via?: inbox | chat-card }` → `{ decision }`, `decisions.confirm { id, answered: boolean }` → `{ decision }`. An answer that would grant `push`, `publish`, `deploy`, `real-data`, `migration`, `security` or `cost` needs `confirmed: true` (experience concept X-4: release, data, security, cost). Error codes: `E_DECISION_NOT_FOUND`, `E_DECISION_SETTLED` (answered, superseded — the message names the replacing id —, withdrawn or expired), `E_DECISION_ANSWER_INVALID` (not exactly one of `optionKey`/`words`, blank words, unknown option), `E_DECISION_NOT_CONFIRMED`, `E_DECISION_NOT_NEEDS_CONFIRMATION` (`confirm` on a decision not waiting for one), `E_DECISION_WRITE_FAILED`, and `E_DATA_HOME_UNAVAILABLE`; every refusal writes nothing. After the answer and grant are stored, the handler hands the settled decision to an injectable `onSettled(decisions, { paseo })` hook — the delivery below; a failing hook is logged and never fails the answer. The client polls an open decision every 5 s while shown (REQ-111 b); a settled one stops polling.

Delivery, by the plugin through the notice queue:
- **Worker question (DQ-2):** each answer is delivered as soon as it is given — at the Worker's next idle moment, one `BM-ANSWERS` block holding every settled, undelivered question of that request (kind `answers:<requestId>`, so a newer block replaces an unsent older one); questions still open stay open and the Worker carries on with what it has. No **Send** button, no waiting for the whole round.
- **Orchestrator decision with a prepared command:** the `BM-COMMAND` v2 (A.7) goes to its Main with `authority: decision:<id>` and `approved: none` — the options' effects are information only (ADR-031).
- **Orchestrator decision answered in words, or an option without a command:** a `BM-ANSWER` notice goes to the Orchestrator; it names no grant (ADR-031).
- **Fallback:** `fallback.act` with the prepared action.

Detail for Worker questions (`server/decision-delivery.ts`, wired as the `question` kind of `settledByKind` and as the materialiser's `afterTurn`):
- The message is `Continue <requestId>.`, a blank line, then `answersText` over every answered `q:` decision of the request whose `delivery` is null, `queued` or `held`, in question order (`Qn: a — <label>`, `Qn: other — <words>`). Target: the request's sole live Worker of the workspace (`soleWorkerOf` over the agents' labels, fallback-replaced Workers left out); none or several → every included decision is recorded `failed` (to the asking Worker) and nothing is sent. A queue `dropped` (archived, closed, gone, send failed) is `failed` too; a `failed` delivery is never retried.
- Recorded per included decision: `sent` (the Worker was idle), `queued` (held for its turn end), `held` (a bound Worker waiting by structure whose wait the block does not meet: it joins the block that releases the Worker, `wake-gate.ts`, delivery line design §6.4). A `queued` decision becomes `sent` when a Worker's turn record carries an answers block naming it (the block arrived), or when this run's queue no longer holds its `answers:<requestId>` notice; it is then left out of the next block.
- An answer given in the Worker's own chat (`via: chat-worker`, including a confirmed chat answer) is not sent: it is recorded `sent` at the answer's time. Without a Paseo handle or data folder nothing is recorded and a later trigger delivers it.
- Once per plugin run — at the first settlement or recorded Manager or Worker turn with a Paseo handle, after that turn's arrivals are noted — every answered `q:` decision whose delivery is null, `queued` or `held` is delivered again, one block per request. A `queued` block sent just before a reload can therefore reach the Worker twice; an answer is never lost. One delivery runs per request at a time; a settlement meanwhile makes it look once more.

Detail for the Orchestrator's decisions (`server/orchestrator-decide-tools.ts` `bm_ask_owner`, `server/orchestrator-decisions.ts`, wired as the `orchestrator` kind of `settledByKind`):
- `bm_ask_owner { workspaceId, requestId?, managerId?, question, recommendation, options?[≤ 5]{ label ≤ 80, effects[], recommended?, command?{ to: manager, agentId, intent, body }, change? }, subject?, class?, separate? }` stores `o:<uuid>` with keys `a`–`e`; the stored question is the question, a blank line and `Recommendation: …` (the recommendation ≤ 500, the whole ≤ 1,000); at most one option is recommended. A prepared command is checked as it will be sent: its target is a live, non-archived paseo-bm Main or Manager of the project, the block can be written, and the backstop finds no category in the option's label and body that its effects do not declare. Supersession: the Orchestrator's unsettled `o:` decision of the same request (or, both without one, of the same project) — the newest of the same `subject` when there is one, else the newest; the answer returns `{ decisionId, replaced }`, `replaced` only when the store did supersede one.
- Prepared command chosen: `BM-COMMAND` v2 `from: orchestrator`, `via: tab` (the owner's tap), `re:` the option's label, `why: The owner chose "<label>" on decision <id>.`, `authority: decision:<id>`, `approved: none` and every fixed limit (`preparedCommandOf`). Queue kind `command:<id>`; an older decision's Worker command still goes to its Worker, its Main getting the `copy: yes` block. The target is re-checked at delivery; the command leaves through the one send pipeline (`server/command-send.ts`) and is written to the commands store (`proposals.json`, source `chat`), so it counts toward the loop guard. The owner's own choice is never refused there; a choice by a precedent or the policy is refused when the guard is full (12 commands for the request in 24 hours). A command that cannot be delivered or is refused is recorded `failed`, and the Orchestrator gets the `BM-ANSWER` with a `delivery:` line saying why.
- `BM-ANSWER` (a plugin notice, matched as a whole word so the owner's `BM-ANSWERS` never is; `answerNoticeOf`): `decisionId`, `workspaceId`, `requestId` (or `none`), the question's first line, `answer:` (`option <key>: <label>`, or the owner's words after the header), then as they apply a `precedent:`, `policy:`, `overrides:`, `delivery:` and `change:` line, and one instruction line. No grant. Queue kind `answer:<id>`, to the current main Orchestrator; with none open it is recorded `failed` and the Orchestrator reads it later with `bm_decisions`.
- Each decision is delivered once (a recorded `delivery` is never repeated); a confirmed chat answer (no option, no words) delivers nothing.

Detail for the Orchestrator's answer to a fallback incident (`bm_decide`, `server/orchestrator-decide-tools.ts`; its authority is the policy, §B.5): it decides only an open `f:` decision whose class is delegated and that the authority resolver gives the Orchestrator (mission runtime design §4.1: a mission request's delegated incident is its Main's, `bm_answer_fallback`, ADR-040). A Worker's question (`q:`) is its Main's or the owner's (ADR-029 decision 8; missions design §8, §9.1), and the Orchestrator's own `o:` decisions are the owner's.
- The answered decision goes to the same `onSettled` hook as `decisions.answer` (`settledByKind`, wired in `index.server.ts`), which runs `fallback.act`; the tool's reply says what the action did. A failing delivery is one log line; the answer stands. From the read to the write nothing awaits, so no other answer comes between (§A.4). The first answer wins both ways: a later answer is refused `E_DECISION_SETTLED`, and every refusal of a settled decision names who answered.
- A command never carries the answer to a question the decision store holds: a `BM-ANSWERS` block naming a `Qn` that has a stored decision of that request — the block's `requestId:`, else a request id in the text, else the command's `requestId`, else (to a Worker) the Worker's `bm.requestId` label — is refused, said as the decision stands (`refuseStoredAnswers`). A block naming only questions the store does not hold is sent as before.
- Views: a policy answer's card is §B.5's; a stored Phase 1 answer reads "answered by the Orchestrator · <time>", with the reason under Details and no answer buttons. A settled decision leaves the Inbox's Needs you. `bm_decisions` hands out each answer's `by` and, for the Orchestrator's, its reason.

Detail for **Ask back** (change-014 outcome 3; `server/decision-ask.ts`):
- **RPCs** (`shared/contracts/decisions.ts`): `decisions.ask { id, text }` → `{ thread, delivery: sent | queued | failed }`, `decisions.thread { id }` → `{ thread }`. Errors: `E_DECISION_NOT_ASKABLE` (not a `q:` or `o:` decision), `E_DECISION_ASK_INVALID` (blank or too long), `E_DECISION_SETTLED`, `E_DECISION_NOT_FOUND`, `E_DECISION_WRITE_FAILED`, `E_DATA_HOME_UNAVAILABLE`. The owner's text is masked and appended first; the decision is never touched.
- **Delivery** through the notice queue, never into a running turn, kind `ask:<decisionId>` (a newer ask replaces one still queued): a `q:` goes to `askedBy.agentId`, else to the request's sole live Worker (`soleWorkerOfRequest`); an `o:` to the Orchestrator open now. None found: the question stays in the thread, `failed`.
- **`BM-ASK`** (a plugin notice, matched as a whole word): `BM-ASK`, `decisionId: <id>`, the decision's question (≤ 300 characters), the owner's text quoted line by line with `> `, how to answer (`bm_reply`, carry on with what does not depend on it, do not answer the decision), then the fallback line `BM-REPLY <decisionId>`.
- **`bm_reply { decisionId, text }`**, run on the plugin server and pre-approved: the Worker's face (`q:` only; `WORKER_SERVER_TOOLS` at `/mcp/worker`, after `bm_report`) and the Orchestrator's (`o:` only; its 16th tool). One thread append; accepted only while the decision is unsettled and its ask is open — once per ask. It answers nothing.
- **Fallback** for an agent created before `bm_reply` (Paseo gives tools at creation): at a recorded Worker turn end, the Worker's own message whose first line is `BM-REPLY <decisionId>` is appended by the same rule, only from the agent the ask went to. The Orchestrator's turns are not recorded, so an Orchestrator on older instructions has no reply path until it is replaced.
- Each reply turn of a Worker also wakes its Manager once (`notifyOnFinish`). The card is the Dashboard design's (§A.12 below).

A bound Manager's follow-ups to its Worker go through `bm_tell_worker`, and a bound agent's reports and reviews arrive as `BM-DELIVERY` records from the outbox; Paseo does not wake the creator of an agent the plugin created, so a bound Worker's turn end wakes its Manager only through a delivery ([base design §7.15, §7.16](./paseo-bm.md)).

### A.7 Typed commands and authority (`BM-COMMAND` v2)

`shared/orchestrator-command.ts` writes and reads the block. Header lines after `re:`: `intent: answer | continue | redirect | stop | release | handoff | other`, `effects: <list or none>`, `authority:`, `approved: <effects the authority covers>`, then `limits:` (only `from: orchestrator`). `limits:` is derived: the fixed limits (`COMMAND_LIMITS`: no commit, push or deploy; no real data) minus what `approved` covers, a partly approved limit split into `no-<effect>` for what it still withholds (`approved: push` → `limits: no-commit, no-deploy, no-real-data`). The reader is strict: it refuses a v2 block whose limits withhold an approved effect, or that carries only some of the four v2 fields; a v1 block (no `intent`) still reads.

The authorities a current build writes:
- `decision:<id>` — the owner's tap on an option of an `o:` decision (§A.6), `via: tab`, `approved: none` (ADR-031). A `decision:r:<id>` carries an override's corrected command (§B.7).
- `governor:nudge | governor:replan | governor:arbitrate` — the governor's commands to a mission's current Main, `effects: none`, any intent but `handoff` (missions design §9.3, §9.4).
- `coordination:handoff` — only with `intent: handoff`, the plugin's handoff runner to a Manager or Main (§G.6).
- For `bm_direct_worker`'s stop (`intent: stop`, interrupt, no effect; missions design §9.1), `stopAuthorityOf` names the authority: an `o:` decision the owner answered (`decision:<id>`, which grants nothing), the owner's policy delegating `reversible-technical` in the project (`policy:reversible-technical`, §B.9), or the owner's own latest word in the Orchestrator's chat (`owner`).

The builder refuses any other shape: `coordination:handoff` without `intent: handoff`, a `governor:` step it does not know, and `policy:<class>` for anything but one of the nine classes. `from: owner` and `via: autopilot`/`authority: autopilot` are only read from older builds (§B.8). The regex gate (`decision-gate.ts`) is the **backstop**: a category it finds in `re:` and the body that the declared effects do not include refuses the command with "declare the effect or ask the owner" — never a silent send; a governor command's backstop reads only the Orchestrator's own words (`CommandSend.backstopText`). Every command leaves through `server/command-send.ts`, which records it in the commands store and counts the loop guard: 12 per request in 24 hours, and per mission the four governor pools of delivery line design §8.1.

*Retired:* `bm_send_command` and its authorities (a grant, the policy, the owner's word, for any intent) — replaced by `bm_govern` (ADR-029 decision 8, missions design §9.4); spending a grant on a command (ADR-031, missions design §19).

### A.8 Events to the Orchestrator and the Inbox

`plugin/server/event-bus.ts` carries typed events to the Orchestrator in batches. **Only the governor's events wake it** (ADR-029 decision 9; missions design §9.7, §20): `mission.signal`, `mission.conflict`, `mission.scope`, `mission.review`, `mission.split`, and `worker.signal` of kind `danger`. Every other type — `decision.opened`, `request.finished`, `request.stalled`, `worker.signal` other than `danger`, `writers.observed`, `advice.due`, `threshold.crossed` — is **retired as a wake**: its source still builds it where other code reads it (the alerts, the figures, the intervention log), but `publish` skips it. To the owner, stalls and the Worker signals are **Inbox alerts** — never messages.

**Scope.** A `danger` of a mission's Worker goes to its Main first (`BM-SIGNAL`) and reaches the governor at any repo level as the Main's backup (missions design §20.3). For a Worker of no mission it is published only for a project with at least one class above `owner` in the policy (`projectsAboveOwner`, `eventScopeOf`; never a plugin home), and dropped at delivery when that project fell back to all-`owner` meanwhile; a policy that cannot be read is the empty scope, with one log line.

Open alerts live in `<data>/inbox/alerts.json` (`{ version: 1, entries: { <key>: { workspaceId, kind, subject, since, clearedAt, detail? } } }`, same file rules as the decision store): raised once per key, cleared when the condition ends (an agent runs again, the permission is answered, the Worker's turn ends). Key `<kind>:<workspaceId or ->:<subject>`. Open alerts are never evicted, cleared ones keep the newest 500; the cleanup button deletes `inbox/`.

Delivery to the Orchestrator: one mission's events (a conflict's two missions together; a Worker of no mission by its project) pending at its idle moment go as **one** `BM-EVENTS` message through the notice queue's batch kind (`enqueueBatch`), opened by that mission's brief (`governor-brief.ts`), one short line per event with the ids to look up; an event is dropped when its subject settled before delivery; a mission is woken at most once per 15 minutes (`MISSION_WAKE_MS`), `danger` excepted (missions design §9.7, §20.1).

Detail (`server/event-bus.ts`, `server/alert-store.ts`, `shared/alerts.ts`; `server/stall-watcher.ts` and `server/worker-watch.ts` as sources):
- **Alert kinds** (`ALERT_KINDS`, in the Inbox's order): `request-stalled`, `peer-unanswered`, `permission-waiting`, `danger`, `stuck`, `writers-observed`, `pairing-mismatch`, `outdated-agent`, `fallback-failed`, `delivery-dropped`, `off-tool-reviewer`, `coordination-off`, `boundary-off`, `turn-replaced`.
- **Dedupe keys.** `decision.opened:<id>`, `request.finished:<ws>:<requestId>@<report time>`, `request.stalled:<ws>:<requestKey>@<alert since>`, `worker.signal:<ws>:<worker>:<signal>@<alert since, or the turn start>`; a key is published once per plugin run. Across reloads the sources dedupe themselves (a decision opens once, an alert is raised once, a turn is recorded once).
- **Settled** (dropped at delivery): a stall or signal whose alert was cleared; a mission event as missions design §9.7 says.
- **Batch kind.** `enqueueBatch(target, { name: "BM-EVENTS", compose }, items)`: the items of one call are queued, then delivered once; at the target's idle moment every pending item of a group goes as one message, oldest first, each item's `isCurrent()` read synchronously right after the idle read. A batch counts as one notice (the queue's one-per-idle-moment rule), and a batch whose every item settled sends nothing and lets the next notice go. A `first` group (a `danger`) goes before every other notice.
- **Stall pass.** Always on (no switch), every 60 s over every project with activity in 24 hours (`STALL_PASS_MS`, `STALL_WINDOW_MS`): `idle-unfinished` (5 minutes, the last report not `finished`, no unsettled decision of the request) and `review-over-budget` (`review.over-budget` against the request's review cap, delivery line design §5.3); a request with an unsettled decision is not stalled (it waits in the Inbox), whatever its last report says (ADR-024), and a malformed report alone is no stall. One `request-stalled` alert per request (subject the request key, `detail` the reasons); `orchestrator.state` reads it as a project's `stalled` state. The same pass raises `peer-unanswered` (base design §7.17.5) and drives the governor's recomputation.
- **Worker watch.** Running Workers of **every** project, every 2 minutes, at most `MAX_WATCHED_WORKERS` (5, the newest) per pass, 300 timeline entries each; with no running Worker nothing is refreshed or read. `stuck`, `permission` and `danger` raise the Worker's `stuck`, `permission-waiting`, `danger` alert (subject the Worker id, `detail` the redacted evidence, ≤ 300 characters) in every project: they cost no model call. A newly raised `danger` of a mission's Worker is logged (`orchestrator/dangers.json`) and sent to its Main as `BM-SIGNAL`; in the scope above it opens the 10-minute interrupt allowance (`orchestrator/stalls.json`, its one remaining key). `stuck` and `permission` clear when no longer seen; all three at the Worker's recorded turn end or when it stops running. A held request of the action boundary raises no `permission-waiting` (§D.2).
- **Other producers.** `off-tool-reviewer` (base design §7.7, ADR-027), `pairing-mismatch` (`role-pairing.ts`, through `raiseInboxAlert`), `fallback-failed` (an answered `f:` decision whose `delivery.outcome` is `failed` while its incident is pending; cleared once the incident is not), `outdated-agent` (`outdated-agents.ts`, §A.11), `writers-observed` (§F.3), `coordination-off` (§G.7), `boundary-off` (§D.2), `delivery-dropped` and `turn-replaced` (ADR-042, delivery line design). The `autonomy-demoted` kind is removed with demotion (ADR-025, §B.4): an old entry is skipped on read and dropped by the next write.
- **Wakes recorded.** Each delivered `BM-EVENTS` message is one wake in `orchestrator/wakes.json` (the batch's `onSent`: Orchestrator id, time, projects, missions, number of events and their types); the Orchestrator's next turn end (the batch's `onTurnEnded`) sets `endedAt` on its oldest open wake with that turn's tokens, whether a tool acted, and `offMission`. Ids, times and counts only; the evaluation's A-7 and A-13 read it (evaluation design §4).
- **Retired.** `BM-STALL` and `BM-EVENT` (producers and notice prefixes), `server/autopilot-events.ts`, the Watch switch (the settings file has no `watch`; its RPC went with the sweep, §A.14), the stall, event and Worker-signal keys of `orchestrator/stalls.json` (ignored, dropped at the next write); the project-era wakes above (ADR-029 decision 9) and the challenger's prediction events (`bm_predict`, §B.3).

### A.9 Bounded context

Orchestrator tools return typed summaries by default: `bm_request` ≤ 4,000 characters (`detail: "full"` keeps 60,000), `bm_agent_messages` 5 messages of ≤ 1,500 characters (`detail: "full"` keeps 50 × 12,000), `bm_projects` counts and open decisions only. A new read tool `bm_decisions { workspaceId?, requestId?, status? }` lists decisions. The Manager gets a read-only `bm_decisions` face too (its block tools stay side-effect free: it reads decisions by `requestId`).

Detail (`server/decision-tools.ts`): `bm_decisions` returns `{ decisions, total, truncated }`, newest asked first, each redacted with the owner's words cut to 1,000 characters, the answer's `by` (and the Orchestrator's `reason`, change-004) and a prepared action as one line; `status` also takes `unsettled` (open or needs-confirmation), `limit` 1–50 (default 20). The Orchestrator's face (in its endpoint) includes each grant; the Manager's (`MANAGER_SERVER_TOOLS`, `{ requestId, status? }`, served at `/mcp/manager` and pre-approved after `bm_answers`) reads that request's decisions of every project, at most 50, without grants, through the store's read path only (nothing is created or repaired). `bm_projects` lists each project's unsettled decisions of every kind from the store, oldest first, at most 10, with `counts.openDecisions` the total.

### A.10 Capability limits per role (REQ-116)

Paseo 0.9.2 treats an alias with no `paseoTools` policy as enabled while `mcp.injectIntoAgents` is on: its agent gets all 39 Paseo tools, `create_agent`, `kill_agent`, `archive_agent`, `respond_to_permission`, `set_agent_mode` and `update_agent` included ([run note](../archive/operations/paseo-bm-role-tools-run-20260929.md)). So every `bm-*` alias (and fallback alias) carries a policy, chosen in `setup-roles.ts` and written by `config-writer.ts`. Paseo resolves the policy each time a session opens (create, resume, refresh), so an existing agent picks it up at its next session open ([ADR-020](../adr/ADR-020-paseo-tools-policy-per-role.md)):

| Role | `paseoTools` |
|---|---|
| Reviewer, Orchestrator | `{ enabled: false }` |
| Manager | `{ enabled: true, disabledTools: [kill_agent, archive_agent, archive_workspace, respond_to_permission, list_pending_permissions, set_agent_mode, update_agent, create_schedule, update_schedule, delete_schedule, run_schedule_once, pause_schedule, resume_schedule, create_heartbeat, delete_heartbeat] }` |
| Worker | the Manager's list plus `create_workspace`, `rename_workspace` |

Role pairing (only the Manager creates Workers, only a Worker creates Reviewers): `before("agent.create")` cannot refuse a creation, because its request carries no creator id (AGENTS.md, *Verified facts*; run note `docs/archive/operations/paseo-bm-role-pairing-run-20260929.md`). The `agent.created` handler (`role-pairing.ts`, wired in `agent-labels.ts`) reads `parentAgentId`, judges the creator by its **provider** (not its label, which can change), and on a mismatch calls `raiseRolePairingAlert`, which raises the `pairing-mismatch` Inbox alert (one log line when no alerts store is wired). An agent with no creator agent (from the app, or the plugin's own Manager and Orchestrator) is outside the rule.

## Part B — Phase 2 MVP: calibrated autonomy (ADR-018; levels since ADR-025)

*The owner sets one of five levels per project ([ADR-025](../adr/ADR-025-autonomy-levels.md), [change-014](../archive/plans/paseo-bm-plan-autonomy-change-014-levels-and-flat-surface.md)); no class is the owner's by rule; an override is recorded and demotes nothing. Since ADR-029, a `delegate` cell is decided by the request's Main, not the Orchestrator (missions design §8); who decides each decision is the authority resolver's one rule (mission runtime design §4.1, `shared/authority.ts` `deciderOf`).*

### B.1 Classes

`class` added to `Decision`: `reversible-technical, scope, preference, environment, dependency, release, data, security, cost`. The asker proposes it (`bm_report` question field; `bm_ask_owner` field). The plugin checks it against the declared effects — `push, publish, deploy` → `release`; `real-data, migration` → `data`; `security` → `security`; `cost` → `cost`; `dependency-install` → `dependency`; `network, outside-workspace` → `environment` — and keeps the riskier class on conflict (order: security, data, release, cost, dependency, environment, scope, preference, reversible-technical). A fallback incident is `environment`.

Detail (`shared/decisions.ts`, bead `bm-autonomy-phase2-t9lm.2`):
- **The map.** `DECISION_CLASSES` holds the nine in conflict order and `CLASS_OF_EFFECT` maps every effect; `none` and `commit` imply no class. `riskierClass`, `classOfEffects` (null when no effect implies a class) and `checkedClass(proposed, effects)` are pure. No class is the owner's by rule (ADR-025). The classes of `CONFIRM_EFFECTS` (release, data, security, cost) keep only the owner's in-place confirmation of their own tap (X-4).
- **The stored field.** `class` is an optional field of the record, and the store stays `version: 1`. Every new decision carries it. A Worker question (`decision-materialiser.ts`) and an Orchestrator decision (`bm_ask_owner`) keep the riskier of the proposal and the classes of their options' declared effects (their union, `declaredEffects`), or `reversible-technical` with neither. A fallback incident is `environment`. Opening is keyed by id, so reading a turn again never changes a stored class.
- **Reading it.** Readers go through `decisionClassOf`, which checks the stored class again against the effects. A decision stored before classes reads as `environment` when it is a fallback incident (`f:`), else as its effects' class, else as `reversible-technical`.
- **Proposing it.** The Worker gives `bm_report`'s optional `class` per question, written as `[class: <class>]` after `[subject: …]` and `[supersedes: …]`. `parseQuestions` reads it and ignores a value that is not one of the nine; the block check (`bm-format.ts`) already accepted any tag. The Orchestrator gives `bm_ask_owner`'s optional `class`, and the tool's answer names the class kept. worker.md asks for one per question (the nine, riskiest first, the riskier when unsure); orchestrator.md names the field.
- **Showing it.** Both faces of `bm_decisions` return each decision's `class`, and a decision card's Details has a `Class:` line.

### B.2 Policy and levels

`<data>/autonomy/policy.json` `{ version: 1, projects: { <workspaceId>: { <class>: owner | shadow | delegate } }, challenger: { <workspaceId>: boolean } }`; absent cell = `owner` (Q-102). Every class may be `delegate` (ADR-025). The owner sets a project as one of five **levels** (ADR-025), written as its nine cells and its proposal switch (`challenger`, §B.3). RPCs `autonomy.policy`, `autonomy.set-level { workspaceId, level, confirmed? }`, `autonomy.set { workspaceId, class, mode, confirmed? }`, `autonomy.reset { workspaceId }`, `autonomy.set-challenger { workspaceId, enabled }` (§B.3). Phase 4 adds an optional `boundary` map and `autonomy.set-boundary`, the action boundary's per-project switch (§D.2, change-010), which a level never touches. A mission's own level (`autonomy.set-mission-level`, `autonomy.set-mission-cell`, `<data>/missions/autonomy.json`) is the second layer (missions design §2.4, §8).

Detail (bead `bm-autonomy-phase2-t9lm.3`; levels bead `bm-njdo.1`, change-014):
- **Levels** (`LEVELS`, `levelOf`, `levelsOf`, `withLevel`, `levelNeedsConfirmation` in `shared/autonomy.ts`, pure):

  | Level | Key | Name | `delegate` classes |
  |---|---|---|---|
  | 0 | `hands-on` | Hands-on | none |
  | 1 | `co-pilot` | Co-pilot | none |
  | 2 | `cruise` | Cruise | reversible-technical, preference, scope, environment, dependency |
  | 3 | `turbo` | Turbo | Cruise's, plus cost, release, data |
  | 4 | `full-auto` | Full auto | all nine |

  - **Write** (`withLevel`, one store write): the level's classes `delegate`, every other class `shadow` (levels 1–4) or `owner` (level 0), all nine written with the same `at`; the proposal switch on for levels 1–4, off for 0. Other projects and the action boundary stay as they are.
  - **Read** (`levelOf`): 0 when no class is `delegate` and the switch is off; n of 1–4 when the switch is on and exactly level n's classes are `delegate` (every other `owner` or `shadow`); otherwise `custom`. A project the policy does not name reads as 0.
  - `levelNeedsConfirmation`: Turbo and Full auto (3, 4).
- **Schema** (`shared/autonomy.ts`, pure). A cell is `{ mode: owner | shadow | delegate, at }`, `at` being when it was set; who decides a `delegate` cell is the authority resolver's (a `q:` → the request's Main; an `f:` → its Main or the Orchestrator). `modeOf(policy, workspaceId, class)` reads an absent cell or project as `owner`; `canDelegate(class)` is true for every class. A cell is read on its own: an unknown class or mode is skipped alone (it reads `owner`) and dropped by the next write; so is a challenger entry that is not a boolean. A file of an older build is read past: a `delegate` cell's stored `predictor` is not read, and `demotions` is ignored; both are dropped by the next write. The workspace id `__proto__` is refused. A placement's decisions read their repo's cells (`effectivePolicy`, delivery line design §3.1).
- **Store** (`server/autonomy-store.ts`): the alerts store's file rules (0700 folder and 0600 file created by a write only, atomic replace, symlinks refused, no lock). A missing or corrupt file reads as the empty policy; a newer `version` reads as it too and is never written, not even by a reset. The challenger map is kept on every write. The cleanup button deletes `autonomy/`.
- **RPCs** (`server/autonomy-rpc.ts`; contracts in `shared/contracts/autonomy.ts`):
  - `autonomy.policy { workspaceId? }` → `{ policy, levels }`, the whole policy or one project's, with `levels` mapping each project it names to its level (0–4 or `custom`); reads only. No usable data folder or an unreadable store reads as the empty policy (every cell `owner`, the safe side), with one log line. `readAutonomyPolicy` is the same read for the plugin's own readers.
  - `autonomy.set-level { workspaceId, level: 0–4, confirmed? }` → `{ policy }` (the whole policy). Checked before the data folder is looked at: an unknown project or level → `E_AUTONOMY_INVALID`; Turbo or Full auto without `confirmed: true` → `E_AUTONOMY_NOT_CONFIRMED` ("Turbo lets the Main decide cost, release and data for you and needs the owner's confirmation; nothing was saved"). Then no usable data folder → `E_DATA_HOME_UNAVAILABLE`; a newer or unwritable store → `E_AUTONOMY_WRITE_FAILED`. Any other level needs no confirmation.
  - `autonomy.set { workspaceId, class, mode, confirmed? }` → `{ policy }`: one cell, for the prepared change of advice (§G.4) and the evaluation suite; no screen calls it. Strict input: an unknown project, class or mode, or a field it does not take (the `predictor` of builds before ADR-025) → `E_AUTONOMY_INVALID`; `delegate` without `confirmed: true` → `E_AUTONOMY_NOT_CONFIRMED`. Any class may be delegated. Cells set one by one read as **Custom** until a level is set.
  - `autonomy.reset { workspaceId }` → `{ policy }`: that project's cells are removed in one write (an absent cell reads `owner`); other projects, the challenger and the boundary are untouched; a project with no cell writes nothing. No confirmation; no screen calls it (Hands-on is the way back).
  - `autonomy.set-challenger { workspaceId, enabled }` → `{ policy }`: §B.3; no screen calls it (the level sets the switch).
  - Every refusal writes nothing. No agent tool sets the policy.
- **Settings → Autonomy** (`client/settings-autonomy.tsx`, `settings-autonomy-model.ts`, change-014; the Dashboard design §11.4 has the layout): one collapsed project picker shows "<name> · <Level>" on every layout; opening it lists all projects and selecting one closes it (a project the policy holds something for that no longer has a name is "Unnamed project", never its id). Five stops "Level n: <Name>" form one radio group; one sentence explains the chosen level (`LEVEL_SUMMARIES`); the nine classes sit in three columns — **Main** (it decides, the owner can override), **You approve** (it proposes, the owner approves), **You**. A Custom project shows its own cells read-only, with no stop selected, until a level is chosen. A stop is set at once (`autonomy.set-level`), except Turbo and Full auto, which open an in-place confirmation every time they are chosen — lowering from Full auto to Turbo included — Cancel first and the default ("Let the Main decide cost, release and data?" / "Let the Main decide security questions too?", confirm **Switch to <Name>**). The meaning line (`AUTONOMY_MEANING`): "How much a request's Main may decide for you, per project. A mission's own level can let its Main answer more; the Orchestrator decides only provider fallbacks, where environment is delegated. You can change it at any time. Your overrides are recorded; they never change the level." The action boundary's switch sits under the level (§D.2).

### B.3 Shadow and the agreement ledger

For every decision answered by the owner, the record keeps what was predicted: `prediction.recommended` (the option marked recommended, at open time), `prediction.main` (a mission Main's recommendation in a `shadow` cell it may not decide, `bm_answer_worker`, missions design §8) and, on records stored before 2026-10-10, `prediction.orchestrator`. `plugin/shared/autonomy-ledger.ts` (pure) computes per project × class × predictor: agreement, count, first/last time, reversals. **Reversal** of a decision: re-asked with the same `subject` in the same request after it was settled; overridden from the digest; or a bead closed under it reopened with a reason citing it.

*Retired:* the Orchestrator's challenger prediction, `bm_predict` — for Worker questions by ADR-029 decision 8, altogether by the owner's decision of 2026-10-10 (missions design §19). Nothing writes `prediction.orchestrator` any more; a stored one is still read and shown.

Detail (bead `bm-autonomy-phase2-t9lm.6`; change-007 C4):
- **On the record** (`shared/decisions.ts`, additive, the store stays `version: 1`):
  - `prediction { recommended: { optionKey } | null, orchestrator: { optionKey, reason, at } | null, main?: { optionKey, reason, at } | null }`, each naming one of the decision's options. `openingPrediction` sets `recommended` where each kind opens — the materialiser (`q:`), `bm_ask_owner` (`o:`) and the fallback decisions (`f:`, `recommendedActionOf`); it is null when no option is recommended. Opening is keyed by id, so opening again changes nothing. A decision stored before predictions has none and is in no cell: nothing is read back from its options (change-007 §3.3).
  - `reversals[] { kind: re-asked | overridden | reopened, at, ref }`, at most 20, only on an answered decision. `ref` is the re-asking decision's id, the override's id or the reopened bead (`last-touched` when the reopen names none). Every reversal goes through `recordReversal`, which keeps one entry per kind and `ref` and refuses a decision never answered (`not-answered`).
  - `answer.by` is `owner | orchestrator | policy | precedent | main`. `orchestrator` stays readable for Phase 1's answers. A `policy` answer is an option and may name its `predictor` (older builds); a `main` answer counts as the policy's, chosen by the Main (`policyPredictorOf`). A `precedent` answer names its `precedentId` and may be the owner's standing words. Either may carry the cell's `class`. `via: autopilot` is refused for `owner` and `precedent`. `precedent` is written at open (§B.6), `policy` by `bm_decide` (§B.5, `via: inbox`) and by the action boundary (§D.2).
- **Reversals detected.**
  - (1) In the materialiser: a new `q:` of the same request with the `subject` of an **answered** question reverses that answer, `ref` the new id. Re-asking an unsettled one is supersession only.
  - (3) At every recorded Manager or Worker turn (the materialiser, on the collector's `onRecorded`): each `br reopen` in the turn's shell evidence is read with its beads and its `--reason`/`-r`. A reason that cites `q:…` or `o:…`, or a bare `Qn` (of the request ids it names, else of the record's request), reverses that decision when it is answered and the reopen is not earlier than the answer. A reopen whose reason cites nothing is a review finding, the baseline's noise, and records nothing.

  - `count`: owner answers with an option or words that carry that predictor's prediction;
  - `agreed`: the answers that chose the predicted option (own words never agree);
  - `unread`: chat answers the owner confirmed, whose content was never read — in neither `count` nor `agreed`;
  - `firstAt`/`lastAt`: over the counted answers;
  - `reversals`: decisions reversed at least once, and `reversalsByKind`, each decision once per kind.

  `delegated[]` counts answers `by: policy` or `by: main` (per predictor, `policyPredictorOf`) or `by: precedent`, with `overridden` (A-4) and `reversals`/`reversalsByKind` (A-5). An answer `by: orchestrator` is in neither figure (change-007 C4). Option: `workspaceId`. Every answer counts (no demotion, ADR-025).

### B.4 Delegation; no demotion

The owner delegates by choosing a level whenever they choose ([ADR-023](../adr/ADR-023-delegation-without-eligibility.md), [ADR-025](../adr/ADR-025-autonomy-levels.md)): agreement is shown as information in a project's Metrics, never required. **An override or a reversal is recorded, nothing more** (ADR-025 decision 4): it is stored with the decision (§B.3, §B.7) and counted in the agreement ledger, and it never changes a cell, a class or a level. The owner lowers the level by hand.

Detail (ADR-023, change-013; ADR-025, change-014): nothing checks agreement — neither `autonomy.set-level` nor `autonomy.set` — and there is no eligibility rule. The only confirmation is the level's (§B.2): Turbo and Full auto, in place, Cancel first. Nothing demotes: a reversal recorded by the materialiser or an override (§B.3, §B.7) changes nothing but the decision's record. A `demotions` map or an `autonomy-demoted` alert an older build left is skipped on read and dropped by the next write.

### B.5 Delegation

When a decision opens in a `delegate` cell, who decides it is the authority resolver's (`deciderOf`, mission runtime design §4.1): a Worker's question (`q:`) of a mission request is decided by the request's **Main** with `bm_answer_worker` (`by: main`, `via: main`, no grant; missions design §8), and a fallback incident (`f:`) by its Main (`bm_answer_fallback`, ADR-040) or, outside a mission request, by the **Orchestrator** with `bm_decide { decisionId, optionKey, reason }`. `o:`, `r:`, `h:` and `m:` decisions, an `ownerOnly` one and one carrying a prepared change stay the owner's. Each answer is delivered exactly as an owner answer would be (A.6). Nothing answers by the recommended option, and `resolveAtOpen` (`server/policy-resolve.ts`) applies precedents only (§B.6). Autopilot and **Allow…** are retired (§B.8).

*Retired:* the Orchestrator deciding Worker questions (ADR-029 decision 8); the policy answering a `review-budget` question (ADR-035 decision 4: past the review cap paseo-bm asks the owner once, delivery line design §5).

Detail for `bm_decide` (`server/orchestrator-decide-tools.ts`; ADR-025; REQ-121, REQ-123):
- **The rule** (`decideRefusalOf(policy, decision, choice)`, `shared/autonomy.ts`, pure): an `f:` decision that is `open` and whose class (`decisionClassOf`), any class, is `delegate` in its project. Otherwise it names why: an override or a held request; a prepared change; an `ownerOnly` fact; its own `o:` decision; answered ("already answered by … at …; the first answer stands"), needs confirmation, superseded (naming the replacement), withdrawn or expired; not delegated. A `q:` is refused before the rule as its Main's or the owner's (`questionIsTheMainsText`).
- **`bm_decide`** reads the policy at the call (unreadable = every class `owner`); the rule is checked on the stored decision, then the option must exist, then the rule is checked again inside the store's write (`transitionUnderPolicy`). It stores `answerDecision { by: policy, via: inbox, optionKey, class, reason }`, the reason redacted and on one line (at most 300 characters). A refusal writes, delivers and logs nothing.
- **Delivered as an owner answer**, through the same `onSettled` (`settledByKind`): `fallback.act` runs the chosen action. The tool's reply names the class and what the action did, and asks the Orchestrator to tell the owner in one line.
- **Logged and measured.** The answer is an `answer` intervention (§G.3, `interventionOfDecision`) and its wake's action for A-7 (evaluation design §4). The ledger counts it in `delegated[]`, never as an owner agreement (§B.3). Re-asked, reopened or overridden, it is recorded as a reversal and demotes nothing (§B.4).
- **Shown to the owner.** The card reads **Decided**, "decided for you by the Orchestrator" (a Main's answer: "the Main"), with no answer buttons and no **Save as precedent**; Details has `Answered by: … (<class>)` and the reason. A `policy` answer an older build stored with the recommended predictor reads "decided for you by your earlier policy". The Inbox digest is §B.7's.
- **Not decided.** A decision the Main or the Orchestrator leaves stays open in the Inbox for the owner; nothing times out into an answer, and it is not told again. The owner may answer any open decision first.

### B.6 Precedents

`<data>/autonomy/precedents.json`: `{ id, scope: <workspaceId> | all, subject, text, sourceDecisionId, createdAt, expiresAt (default 30 days), supersededBy }`. Created from an answered decision (**Save as precedent** on its card) or by the owner in Settings. At agent creation the hook appends `## Owner precedents` (active, the workspace's and global, newest 20) to the Manager's and the Worker's runtime facts. A decision opening with a `subject` equal to an active precedent's is resolved by it whatever its class (ADR-025), citing the precedent; where it cannot answer (below) it is shown on the card as a suggestion. A repo's active precedents are also listed beside its project memory (`memory.list`, missions design §18).

Detail (bead `bm-autonomy-phase2-t9lm.12`; injection and resolution are `t9lm.13` and `t9lm.14`):
- **Record** (`shared/precedents.ts`, pure). `id` is `p:<uuid>`; `subject` follows `SUBJECT_PATTERN`; `text` is at most 1,000 characters, an option label's cap rather than own words' 4,000, since it goes into agents' runtime facts; `sourceDecisionId` is null for one added in Settings.
  - `isActive(p, now)`: not superseded, and `expiresAt` later than now.
  - `activeFor(precedents, workspaceId, now)`: the workspace's and the global ones, newest first by `createdAt`.
  - The text an answered decision gives is its option's label, else the owner's words. A chat answer the owner confirmed has none, so the owner writes it.
- **Store** (`server/precedent-store.ts`): `{ version: 1, entries }`, with the policy store's file rules (0700 folder, 0600 file, atomic replace, no symlink, no lock).

## Part C — Phase 3: evidence-grounded reflection

- **C.1 Richer evidence.** `evidenceSchema` (`shared/contracts/persisted.ts`) gains optional `status`, `exitCode`, `cwd` and `callId` for `shell` entries. The change is additive and `v` is unchanged (`compaction` evidence is §G.2's). Every evidence `detail` — shell, file, skill, sub-agent — and a shell entry's `cwd` are masked before they are kept; the call's `output` and `error` are never stored; a field the provider did not give is left out, never guessed. Claude `Bash`: `status` `completed` / `failed`, `callId` `toolu_…`, no exit code or cwd. Codex `shell`: `status`, `exitCode` and `cwd` on the detail, `callId` `exec-…`. OpenCode `bash`: `status` is `completed` even for a failing command; the exit code is only in `metadata.exit` (`callId` `call_function_…`). The collector takes `exitCode` from the detail, else OpenCode's `metadata.exit`, else leaves it out. `status` is kept as a free string so a new Paseo status never breaks a record.
- **C.2 Detected checks** (`plugin/shared/evidence.ts`, pure). A check a report's `buildAndTests` names is labelled:
  - *detected*, when a shell evidence entry of the same request runs the same normalised command with a successful status after the request's last file edit. It is also detected as one segment of a chain joined only by `&&` whose run succeeded (change-008 C5);
  - *reused* ([ADR-045](../adr/ADR-045-a-mission-runs-as-a-supervised-line-of-approved-steps.md) decision 13), when it is not detected, its clause of `buildAndTests` (split at `;` or a newline) says `reused`, and a successful shell entry of the request ran it at any time, whichever of its Workers did. It counts as verified: a verdict is `reused` when every named check is detected or reused and at least one is reused;
  - *self-reported*, when only the report names it;
  - *unverified*, when the report says "not run" or nothing matches.

  A request none of whose shell entries carries a `status` (recorded before C.1) is *not checked*: neither detected nor unverified.
  - `verificationOf` → `{ checks, named[], files[], beads[], changedFiles }` (`CHECKS_VERDICTS`: `detected`, `reused`, `self-reported`, `unverified`, `not-checked`; per claim `CLAIM_LABELS`: `detected`, `reused`, `self-reported`). The request verdict, first match wins: shell entries exist and none carries `status` → `not-checked` (a request with no shell entry at all is judged as usual); the value is null, empty or says nothing ran → `unverified`; every named check detected → `detected`; every one detected or reused → `reused`; else `self-reported`. A detected check is a successful call (`shellSucceeded`: an exit code decides, else only `status: completed`) begun after the last `file` entry of any of the request's records, whose `&&`-only chain (`andChainOf`) contains the check as consecutive segments; one call per `callId` (its latest state, placed where it began); quoted arguments are kept and redirections are not stripped. Records of every role count (a Reviewer's run detects a check). Files by path relative to the workspace (without the folder, a relative path matches an absolute one ending in it); beads by `brActions` close ids on a successful `&&`-only line, case-insensitive. `buildAndTests` is stored with its backticks (`checksValueOrNull`, `shared/bm-report.ts`), and the "nothing ran" readers (`NOTHING_RAN`, `saysNothingRan`) ignore leading backticks. `shared/shell.ts` holds `normalisedCommand`, `shellFailureOf`, `shellSucceeded` and `andChainOf`. The Worker is told to name each check exactly as run, in backticks, with pass/fail, run after its last edit without pipes or redirections (`worker.md` "Proving a change"; the `bm_report` field description).

A missing line counts as off: the hook ran out of its 5 s lookup budget (no mode correction, no Codex options), or the plugin was down. A project with the switch off gives `off — the project's boundary is off`.

It clears when the agent is archived, replaced or gone, or when the project's switch is turned off. Turning the switch on raises nothing for agents already running. An agent with no instructions at all is already an `outdated-agent` alert (§A.11).

    - *release:* `git push`, `npm|pnpm|yarn publish`, `docker push`, the deploy CLIs (`kubectl apply|delete`, `terraform apply|destroy`, `helm install|upgrade|uninstall`, `vercel --prod`), `gh release create`, and every `glab` command. `npm|pnpm|yarn run <script>` (and `npm test` and similar) is classified by the script's body in the cwd's `package.json` (`pre`/`post` included); a script that cannot be read is unreadable.
    - *real-data / migration:* `DROP TABLE|DATABASE`, `TRUNCATE`, `DELETE FROM` without `WHERE`, a database CLI (`sqlite3`, `psql`, `mysql`, …) given a write statement, and migration runners.
    - *dependency-install:* `npm|pnpm|yarn add|install|i <package>`, `pip install <package>`, `brew install`, `cargo add|install`, `go get`, `gem install`. A bare `npm install` / `npm ci` from the lockfile is not held.
    - *network:* `curl`, `wget`, `ssh`, `scp`, `rsync` to a host, `nc`, and the provider's fetch tools. `git fetch|pull|clone` is not held.
    - *outside-workspace:* a write path (a file tool, `rm`, `mv`, `cp`, `>`, `>>`, `tee`, `mkdir`, `touch`, `ln`) that resolves outside the workspace folder.
    - *The scratch area* is the exception: the system temp roots (`/tmp`, `/private/tmp`, `/var/folders/*/*/T`, `$TMPDIR`, `${TMPDIR}x`, the daemon's `TMPDIR`), a variable the same command assigned from `mktemp`, `${VAR:-d}` and `$(pwd)`. A-6's `rm -rf outside the workspace` uses the same rule, and the replay reports scratch deletions apart.
    - `commit` is not held (§D.4).
    - *The limit:* only the literal command is classified. What a script does inside is seen only by detection.

A commit on the mission branch is free; a push of that branch and `glab`/`gh` merge-request create and update are covered only by the owner's one integration grant per mission and repository (`allowed-integration`, journaled); off-branch writes are held, and anything outside the worktree is `outside-workspace`.

    - *Allowed at once:* no held effect.
    - *A live grant covers it:* the owner's answered `q:` decision of the same request whose grant holds the effect (one use, 60 minutes, `GRANT_TTL_MS`). It is allowed and the grant spent (`useGrant`). An `o:` answer grants nothing (ADR-031).
    - *A `delegate` cell covers it:* every held effect's class is `delegate` in the project — any class since ADR-025, so at Turbo a push, a real-data write or a migration, and at Full auto a `security` finding too (`policyCoverOf`, `server/action-boundary.ts`). An unreadable request is never covered by the policy, and a grant never covers an unreadable or `security` finding.
    - *Otherwise it is held.* The request is left pending and becomes the decision `h:<agentId>:<requestId>`:
      - *kind:* a kind of its own in `decisionKindOf` / `deliveryKindOf`;
      - *record:* asked by `plugin` for the agent; class from the held effects (§B.1); subject `held-<class>`; the question names the masked command or path; its request is the agent's `bm.requestId` (a Reviewer's is its Worker's);
      - *options:* `allow` (the held effects, `permission { agentId, requestId, allow: true }`) and `deny` (`none`, `allow: false`); none recommended.
    - *What never answers it:* a precedent, the Main or the Orchestrator. `bm_decide` refuses it.
    - *In the Inbox:* it replaces the `permission-waiting` alert for that request. Allow on release, data or security needs the in-place confirmation (X-4, `confirmed: true`). The `permission` delivery answers the request exactly once, after its delivery is recorded: a second answer is `E_DECISION_SETTLED`, and a re-delivery after a reload, or a request already resolved, answers nothing.
    - *In the Worker's chat* Paseo shows its own prompt; paseo-bm draws no card there.
    - *Answered elsewhere* (`agent.permission_resolved`): an allow — in Paseo's UI or `paseo permit` — records the decision answered `by: owner`, `via: paseo`, its grant spent at once. A deny or an interrupted turn withdraws it.
    - *When it ends:* a finished report never expires it. A Worker labelled `bm.replacedBy` has its open `h:` decisions withdrawn and its pending requests denied ("You were replaced").
  - **One Inbox item per action.** The live watch raises no `permission-waiting` alert for a held request. It raises `danger` only for an effectful action that no grant of its request covered before it ran. A denied call never raises `danger` (a Codex denial entry and its twin, a call waiting on its permission, a failed call whose held decision was denied or withdrawn — `shared/denied-calls.ts`) and never counts in A-6 (each call id once).
  - **A-6.** `grantsOf` (`eval-metrics/scope.ts`) counts an owner-answered `h:` Allow as a grant of its request. The replay adds the held decisions per finished request (allowed, denied, withdrawn, open, the owner's wait), and splits A-6, the held figures and the estimate by boundary on / off / unknown per request, from the `bm.boundary` label of the request's Worker as the store records it (`a6.held`, `a6.estimate`, `a6.byBoundary`; change-010 C9).
  - **Restart.**
    - Events are not replayed. At the first Paseo handle after the plugin starts — a hook, an RPC or the watch pass — and before every Worker pass, the plugin scans `paseo.agents.list()` for the `pendingPermissions` of Workers and Reviewers running under the boundary and classifies each as if just raised; opening is idempotent by id. An `h:` whose request is gone, or whose agent is gone or replaced, is withdrawn.
    - While the plugin is down, requests wait in Paseo's UI for the owner (measured). An agent created meanwhile has no instructions and is flagged `outdated-agent`.
  - **Budget.** The added latency per allowed call is the plugin's classification plus the measured path (request → answer p90: Claude 33 ms, Codex 29 ms; [Phase 4 live check](../archive/operations/paseo-bm-phase4-live-check-20261001.md)). The classification is synchronous except for the Codex file-change lookup.
  - **Field estimate.** The replay runs the classifier over the field's shell evidence (read-only, numbers only), after each request's grants and the scratch rule, and reports the held requests per finished request by class and as unreadable. **0.2 unreadable per finished request is the threshold for recommending the boundary more widely** (change-010 C8); the environment holds are reported beside it, with the part a grant or a `delegate` cell covered. Release holds are the owner's by design and have no such bound.
  - **The exit.** A-6 must be 0 in a live check of held actions, run with the boundary on for its project, and in the field over the requests run with the boundary on; requests run with it off are a detection figure (PRD §10).

## Part F — Phase 6: specialisation on evidence

*Re-checked at the Phase 6 start ([change-012](../archive/plans/paseo-bm-plan-autonomy-change-012-phase6-start.md)).*

- **F.1 Collision detection first:** a `writers-observed` signal — two agents of one workspace with edit/write evidence on the same file in overlapping turns — as an Inbox alert; measured in the replay. A file a shell command writes (an output redirection or `tee`, such as `cat > f <<EOF`) counts as written too (`shellWrittenPathsOf`, missions design §17). Each mission writes in its own worktree on its own branch (ADR-035), so the "per-Worker worktrees" admission is settled per mission; `writers-observed` watches inside a placement, and overlap between missions surfaces as a merge (delivery line design §3, §4.7) and as the governor's `mission.conflict` (missions design §9.6).

## Part G — Coordination control (ADR-021): measurement, compaction and handoff

The owner's decisions are ADR-021's. G.1–G.4 are Phase 2 (REQ-126–128), G.5–G.8 Phase 3 (REQ-134–136). Since ADR-029 decision 9, code runs compaction and handoff within the owner's settings and the Orchestrator is not woken for them (missions design §9.5).

### G.1 The loop and the ladder

**The loop.**
- Code observes (trace records, reports, decisions, alerts, tokens) and detects (a threshold or an event).
- Code acts where a rule suffices: compaction and handoff (G.5, G.6), the governor's record and nudge steps (missions design §9.3).
- The Orchestrator is woken only for judgement (§A.8): a re-plan, an arbitration, an escalation, a stop on real risk.
- Code records each intervention with its expected outcome (G.3) and checks it after a window.

*Retired by ADR-029 decision 8:* the Orchestrator's own ladder over a project's agents (advise the Manager, correct the Worker, change the structure). The governor's ladder over a mission — record, nudge, re-plan, escalate or stop — replaces it (missions design §9.3).

**Who deals with the owner.** A mission's Main is the owner's contact and the keeper of the request's context (ADR-029). The Orchestrator reaches the owner only through decisions and its own chat.

**What the Orchestrator never does:**
- skip or shorten a review or a check;
- waive a blocking finding;
- change what the owner asked;
- brief, correct or answer a Worker (ADR-029 decision 8);
- archive or delete an agent, or create one other than a Main on a split (`bm_create_main`, missions design §9.6);
- read whole transcripts routinely.

### G.2 Measurement (Phase 2, REQ-126)

**Recorded** (every field additive, trace `v` unchanged, absent = unknown, never zero).
- **Context.** The trace record's `usage` keeps `contextUsed` and `contextMax` when the provider reports `contextWindowUsedTokens` / `contextWindowMaxTokens` in the snapshot's `lastUsage` at the turn end (`collector.ts` `usageOfSnapshot`). A value that is not a finite count is not kept, and a sum over turns never carries them. **Claude, Codex and OpenCode all report both, at every turn end**, compaction turns included (AGENTS.md, *Verified facts*; [run note](../archive/operations/paseo-bm-context-fields-run-20260930.md)).
- **Compaction.** One piece of evidence per compaction: `{ kind: "compaction", detail: <trigger or "unknown">, trigger, preTokens }`, from the timeline's `completed` item (`compactionTracker`). Every provider first shows a `loading` item, and the timeline keeps both, so a `loading` item alone is no compaction. The trigger comes from the completed item, else from its loading item: OpenCode names it only there. `preTokens` only Claude gives; `null` otherwise. A Codex `/compact` runs as a turn of its own (`autonomous-…`) with no user message.
- **Tool calls.** The record's `toolCalls` is the number of `tool_call` items of the turn, whatever the tool (a call's updates are one item). A turn longer than one refetch page (200 entries, the page full and its oldest entry in the turn) is also counted from the hook payload from its last user message, and the larger count is kept.
- **The Orchestrator's tokens** (change-007). The collector records no Orchestrator turn. Each wake record (`orchestrator/wakes.json`) therefore also keeps `usage { inputTokens, cachedInputTokens, outputTokens }` of the Orchestrator turn that closed it: at that turn end the event bus reads the snapshot with one `timeline.refetch({ direction: "tail", limit: 1 })` and writes it with `endedAt`, before the queue delivers anything else. `null` when the snapshot could not be read; absent on a wake written before. Numbers only; no cost (a session total) and no context. The replay's A-8 reports them over the window and per finished request.
- **What the token counts cover differs by provider** (AGENTS.md, *Verified facts*): Claude's are the sum over the turn's model calls; Codex's and OpenCode's the **last model call's** only, and Codex's `cachedInputTokens` is part of its `inputTokens`. A turn with no model call keeps the previous turn's tokens on OpenCode. `contextUsed` means the same on all three: the context of the last call.

**Derived** (in `eval-metrics.ts`, read by the replay and a project's Metrics and Requests; detail in evaluation design §4):
- tokens read per turn: input + cached, but Codex's input alone (its cached tokens are inside it). The provider is read from the model id; the counts cover the turn on Claude and the last call on Codex and OpenCode, and the figures count turns by provider so the mix is visible. An OpenCode turn repeating its agent's previous counts (no model call) reads as 0;
- tokens per request by role, and per agent over its life;
- a **context estimate** per turn: `contextUsed` when reported, else the turn's tokens read ÷ (the turn's tool calls + 1) — a last-call provider's tokens read as they are — labelled an estimate;
- the Orchestrator's tokens from the wake records, in A-8.

**Shown.**
- Projects → Requests → request Details: tokens by role, each agent's context trend.
- Projects → Agents: the same, per agent.
- Projects → Metrics: the distribution of tokens read per request, and the heaviest requests (numbers only).

- **The read.** `traces.agents { workspaceId, traceId? }` (`dashboard-rpc.ts`, `agentTokenFiguresOf` in `trace-usage.ts`) gives per agent its turns, the turns with usage, the tokens read, the turns counted by their last model call only (`lastCallTurns`), the context of its newest 24 turns that have one (`CONTEXT_TREND_MAX`), how many turns have a context and how many of those are estimates, the peak, the newest reported window and the compactions. Every turn is read with `turnTokensOf` beside the agent's turn before it, over all the workspace's records, so a request's first turn knows the one before. With `traceId`: every agent of that request, over its turns there (unknown → `E_TRACE_NOT_FOUND`). Without: each agent Paseo lists in the workspace and has not archived — the Agents tab's tree — over its life. Numbers only; the id is the client's key.
- **A request's Details** (`work-model.ts` `requestTokenFigures`, `work.tsx` `TokenFigures`) open with **Tokens and context**: "Tokens read: Manager 1.2M · Worker 8.4M", then a row per agent named by role (numbered as the ids below it), its context trend as bars against the reported window (else its own peak) with "context 80k of 200k (40 %) · peak 100k", and its tokens read and turns. It is read only while Details is open, again every 10 s while the request moves.
- **Projects → Agents** (`agentTokenFigures`): the same rows under the tree, named by role and title, for the agents the tree lists; read every 10 s while the tab shows.
- **Labels.** A trend with an estimated point says "estimate" (all) or "partly estimated", with the note "Where the provider did not report the context, it is estimated from the tokens the turn read."; a Codex or OpenCode agent's tokens read are "at least", with the note that those providers report only each turn's last model call. A turn with no usage reads "no usage recorded"; an agent with no context figure "context not known".
- **Projects → Metrics** (`insights-model.ts` `requestTokensView`): a chart of the tokens read per request (median, p75, p90, largest, over the requests with usage) and the heaviest requests (up to 5) by project name — the role that read most with its share, the turns, finished or not; a project the surface cannot name is "Unnamed project". A note gives the Codex and OpenCode turns, whose figures are a lower bound. A period with no usage says so; a server without the figures draws nothing.

**Replay candidates.** For each request and agent, the first turn where the thresholds of G.7 would have triggered a compaction or a handoff, and an estimated saving: the tokens read after that turn, minus the same number of model calls re-reading a brief-sized context. Always labelled an estimate. "The agent's p75" is the p75 of the role's tokens read per turn (Manager, Worker), the request p80 that of the requests' tokens read; the brief is 1,500 tokens (6,000 characters at 4 a token).

### G.3 The intervention log and outcomes (Phase 2, REQ-127)

**The store** (`plugin/server/intervention-store.ts`, shape in `plugin/shared/interventions.ts`). `<data>/orchestrator/interventions.json` = `{ version: 1, entries: [...] }`, oldest first, with the store rules of §A.8: the folder `0700` created only by a write, the file `0600` replaced atomically, symlinks refused, a missing or corrupt file read as empty, an entry that does not validate skipped on its own and dropped by the next write, a file of a newer version read as empty and never written; the newest 2,000 kept. The cleanup deletes it with `orchestrator/`. Ids, times and enums only. Each entry: `{ id, kind, workspaceId, requestId, targetAgentId, trigger, expected, windowMs, at, outcome: pending | met | missed | unknown, checkedAt }`, plus what its check reads when the kind has it: `decisionId` (`answer`, `advice`), `alertKey`, `signal`, `commandId`, and for `govern` its step and families.

- `trigger` (`INTERVENTION_TRIGGERS`): `decision.opened`, `request.stalled`, `worker.signal`, `advice.due`, `threshold.crossed`, `owner` (the owner's word in the Orchestrator's chat), `orchestrator` (no event of its wake behind it), `governor`.
- `expected` (`EXPECTED_OUTCOME_OF`): one per kind, below.
- Recording never holds back or fails the intervention: a store failure is one log line.

**Kinds**, each with its expected outcome and window (`INTERVENTION_WINDOW_MS`):

| Kind | Recorded from | Met when | Window |
|---|---|---|---|
| `answer` | `bm_decide` (§B.5) | the decision was delivered (the incident's action ran, or the Worker resumes) | 10 min |
| `unblock` | a command answering a `request.stalled` of its wake | the stall alert clears | 15 min |
| `correct` | a command answering a `worker.signal`, or the owner's word | the signal clears, or the next report's checks pass | the next report, at most 60 min |
| `stop` | an interrupt (`bm_direct_worker`) | the turn ends | 2 min |
| `compact` | the compaction runner (G.5), trigger `threshold.crossed` | tokens per turn over the next three turns ≤ 60 % of the three before | three turns, at most 60 min |
| `handoff` | the handoff runner (G.6), trigger `threshold.crossed` | the successor's tokens per turn ≤ 50 % of the predecessor's last three, and the successor reports progress | 60 min |
| `advice` | a `bm_ask_owner` decision left to the owner that carries a change (G.4) | the owner answered the advice decision | 7 days |
| `govern` | a governor step 2–4 (missions design §9.3), trigger `governor` | every family the step concerns back at step 0 (`figures-clear`) | 30 min |

`unblock` and `correct` come from `interventionOfCommand` for a delivered non-stop command answering an event of its wake; with those events retired as wakes (§A.8), `bm_send_command` gone and `bm_govern` logged as `govern`, no current tool writes them, and the check still reads older entries. A prepared command delivered on a decision's answer logs no intervention.

**The check.** A pass on `agent.turn_ended`, throttled like the outdated-agents pass (once a minute), judges each pending entry from the stores. It runs at each turn end the collector records (its `onRecorded`), so it adds no lifecycle hook of its own and finds that turn's record in the store. It reads the decision store, the Inbox alerts, the trace records and the governor's ladder. It settles `met` as soon as the stores show the expected outcome within the window; `missed` once they show it did not come; `unknown` when the window is over and they cannot tell. An absence of evidence counts only a minute after the window ends, so a turn record written at its edge has landed.

- `answer`: met when the answer was delivered (`delivery.outcome: sent`), or one of the Worker's turns started, within the window. Missed when it was sent or resumed after the window, or the delivery is still `queued` or `failed`. Unknown with no delivery recorded and no turn, or the decision gone.
- `unblock`: met when the alert cleared within the window, or was cleared and raised afresh within it. Missed while it still holds after the window, or when it cleared late. Unknown when the alert is gone, or was raised afresh after the window.
- `correct`: met when the signal's alert cleared within the window, or the request's first report after the command, within the window, says its checks pass (`reportChecksOf` on `buildAndTests`). A signal without an alert (`failing`, `heavy`, `outside`) is settled by that report: missed when its checks fail, unknown when it names none or none came. A signal with an alert waits for the window's end: missed when the alert still holds or cleared late, or the report's checks failed.
- `stop`: met when the Worker's first turn from the interrupt on ended within the window; the turn it replaced does not count. Missed when that turn ended after the window, or none ended by then (a turn is recorded when it ends). Unknown without a Worker.
- `advice`: met when the owner answered the decision within the window. Missed when it is still open after the window, or was superseded, withdrawn or expired. Unknown when the decision is gone.
- `compact`, `handoff`: as §G.5 and §G.6 say.
- `govern`: as missions design §17 says.

**Where it shows.**
- **The Inbox's Decided for you** (§B.7): the interventions since the owner last looked are merged by time with the delegated decisions, newest first (a decision first on a tie). A line reads the kind and its target ("Unblocked the Worker"), the project · the Orchestrator, the reason — what set it off, then the Orchestrator's words when a store kept them — and the outcome, Pending, Met, Missed or Unknown, each in its own tone with its expectation. No Override; ids (intervention, command, request, agent, decision, alert) only under Details. An Orchestrator answer's outcome joins its decision's line instead of a second line. More than 100: "The Orchestrator intervened more often than the Inbox shows; a project's Metrics → Coordination counts every intervention." The heading count includes these lines; the Inbox tab's does not.
- A-12 per kind appears in a project's Metrics (the Orchestrator's interventions): one figure per kind used in the window, met / (met + missed) with pending and unknown apart, against the 80 % target. `insights.summary` carries `interventions`, one row per kind. The replay reports `a12.byKind` and a headline row (evaluation design §4).
- A compaction or handoff kind below A-12's target is switched off until it recovers, with an Inbox alert (§G.7).

### G.4 Proactive advice (Phase 2, REQ-128; replaces the workflow assessment, §B.9)

*Retired by ADR-029 decision 9:* the advice cadence — the `advice.due` wake, the count of finished requests (`advice-store.ts` is gone) and the Settings card. The periodic review is the governor's `mission.review` (missions design §9.7). `advice.everyFinished` stays stored and accepted as a no-op (§G.7).

**The tool.** `bm_findings { workspaceId }` (`server/orchestrator-findings.ts`; face in `shared/bm-tools.ts`) still answers the owner's own question in the Orchestrator's chat. Reads only. A first line of guidance, then compact JSON, redacted, at most `FINDINGS_MAX_CHARS` (4,000; the last findings are dropped and counted in `omitted`): `{ workspaceId, window: { days: 30, since }, requests, settings, findings: [...] }` — numbers, ids and short labels only, never message, question or answer text. Findings: `repeated-subject` (asked ≥ 2 times without a precedent, at most 5 → `precedent.save`), `agreement` (each class not delegated whose predictor has at least one counted answer in the project, most answers first, at most 3 → `autonomy.set`; a plain figure with no threshold, change-013 C4), `intervention-below-target` (→ `coordination.set`), `blocked-rounds`, `reviews` per tier, `stalls` by the fixed reasons, `heavy-request` (at most 3), `compaction-candidates` (`estimate: true`). Window `FINDINGS_WINDOW_DAYS` = 30.

**The action.** For each finding worth acting on, the Orchestrator asks with `bm_ask_owner`, and one option carries a **prepared change** the plugin applies on the owner's answer — `precedent.save`, `autonomy.set` (a delegable cell) or `coordination.set` (a setting of G.7; the review settings are `review.maxRereviews` and `review.callsPerBatch`, the old `review.*Budget` keys are refused). With no finding worth acting on, it writes a note. **Never** text appended to an agent's instructions (the retired assessment).

Detail:
- **Prepared changes** (`shared/prepared-changes.ts`, `server/prepared-changes.ts`). A `bm_ask_owner` option may carry a `change` instead of a command, declaring `effects: ["none"]` and no command: `precedent.save { scope: project | all, subject, text, expiresInDays? }`, `autonomy.set { class, mode }` for the decision's own project (any class since ADR-025; the project may then read Custom), `coordination.set { key, value }`. Checked when asked and again when applied (`preparedChangeCheckOf`; a change that would change nothing is refused when asked and writes nothing when applied). The plugin adds one line per change to the stored question ("Choosing a sets …"), so the owner reads exactly what a tap applies; the owner's tap is the confirmation. Applied through the same handlers as Settings (`precedents.save`, `autonomy.set`, `coordination.set`) in the delivery of the answered Orchestrator decision (`orchestrator-decisions.ts`); the `BM-ANSWER` gets a `change:` line saying whether it was applied (a failure is told to the Orchestrator and logged; the decision card does not show it).
- **Only the owner answers a decision that carries a change**: `answerDecision` refuses any other `by`; `resolveAtOpen` (policy and precedent) leaves it open and no precedent is suggested or superseded; `bm_decide` refuses it; `applyPreparedChange` requires `by: owner` on the stored answer. No Orchestrator tool writes `autonomy/` or `coordination/` (`test/orchestrator-boundary.test.ts`). Such decisions record no prediction (outside the agreement ledger) and never become precedents.
- **Intervention** (§G.3): a `bm_ask_owner` decision left open for the owner is logged as `advice` when it carries a change; trigger `owner` when the owner just spoke, else `orchestrator`; met when the owner answers within 7 days.

### G.5 Compaction (Phase 3, REQ-134)

**What the providers do** (verified; bead `7gxw.8`, [run note](../archive/operations/paseo-bm-compaction-spike-20260930.md); AGENTS.md, *Verified facts*). A `/compact` sent as the app sends it starts a manual compaction on Claude, Codex and OpenCode: the timeline shows a `loading` then a `completed` `compaction` item with `trigger: manual`.
- **Claude honours a focus.** `/compact <focus>` keeps what the focus names; `preTokens` comes on Claude only, and the compaction's cost only in `totalCostUsd`.
- **Codex and OpenCode compact without a focus:** Paseo drops everything after `/compact`, so the plugin sends them a **bare `/compact`**, and the `BM-STATE` brief carries what must survive. Codex compacts in a turn of its own (`autonomous-…`) with no user message; OpenCode's `/compact` turn repeats the counts of the turn before, and its result depends on the owner's own OpenCode configuration.
- **No provider needs the fallback** of REQ-134 c (a handoff for a Worker, nothing for a Manager).
- **Reading the context:** the figure reported right after a compaction understates the real one, so a threshold check reads the context at the **next** turn's end; a turn holding a compaction is never judged.
- **The message is the owner's to the collector unless the plugin says otherwise:** on all three the `/compact` is a `user_message` carrying `clientMessageId`, and a leading `/compact` cannot tell it apart, since the owner may type one too. The plugin therefore keeps a **send log** of what it sent, and the collector classifies a matching message as the plugin's, never as the owner's words.

**What starts it:** code, at a recorded Manager or Worker turn that crosses the owner's threshold (`compactCrossingOf`, §G.7; a Main's by `mainContextCrossingOf`, mission runtime design §3), while compaction is on for the turn's provider, the agent is below `compact.maxPerAgent` and none of it is pending. No model asks for it and the Orchestrator is not woken (ADR-029 decision 9; missions design §9.5). It is logged as a `compact` intervention with trigger `threshold.crossed`.

*Retired by ADR-029 decision 9:* the Orchestrator's `bm_compact` tool and the `threshold.crossed` wake.

**The sequence** (`server/compaction.ts`, kept in `server/compaction-store.ts` so a reload continues it).
1. Wait for the target's next idle moment after a safe point: a Worker after a turn that sent a report (or a Worker waiting by structure); a Manager with no notice queued. Never inside a running turn (the notice queue). At most 60 minutes. **The maintenance ceiling** (delivery line design §6.6): once the turn's figure reaches `maintenance.ceilingFactor` × its threshold, or the compaction has waited 30 minutes, it goes at that turn end without the safe-point and quiet-queue checks, ahead of what is queued.
2. The plugin sends `/compact` — with the fixed focus `COMPACT_FOCUS` on Claude (keep the request and the owner's words, the decisions taken, the plan and bead state, open review findings and files changed; drop tool output), bare on Codex and OpenCode — as a one-item batch of the notice queue, and records it in the send log. A `/compact` held while the target turned busy is dropped after 60 s and sent again at the next safe point, never doubled.
3. It waits for the `compaction` item to complete: the next recorded turn with a completed `compaction` item (Codex: its own `autonomous-…` turn), at most 10 minutes, else the entry fails.
4. It sends a **state brief** (`BM-STATE`, a plugin notice) built from the stores, ahead of what is queued, so what matters is restored from artifacts rather than from the model's summary alone.

Detail: states `waiting | compacting | done | failed | dropped`. **The send log** (`<data>/orchestrator/compactions.json`, deleted with the folder): `{ agentId, at, hash, compactionId }` — the SHA-256 of the trimmed text, never the text — written just before the send; the collector records a would-be owner `user_message` of that agent with that hash, from 60 s before to 30 min after, as `origin: "agent"`, never parsed as a report. **The brief** tells the agent to reply "noted" and end its turn: a Worker's holds its request id and the owner's first words, up to 3 later owner messages, up to 8 decisions with their answers and the report facts (phase, tier, files, beads, open findings, checks, `decided`, blockers); a Manager's its 5 newest requests (phase, Worker, open decisions, written `- req-…`) and the owner's 3 newest messages; masked, at most 6,000 characters. **The outcome** (§G.3): from the `/compact` being sent, at most 60 min, the mean tokens read over the next 3 measured turns against the 3 before — met at 60 % or less, else missed (the compaction's own turn and OpenCode's repeat turns left out; judged on 1–2 turns when the window ends early); unknown when the compaction never went out or no turn compares — so the A-12 guard (§G.7) can fire. Work's live view (`live-timeline.ts`) checks typed messages against the send log with the collector's own matcher (`pluginSentBeside`) and leaves the plugin's `/compact` out of the owner's messages; `BM-STATE` is shown in chat as "State restored after compaction". The Manager handover drops what the send log says the plugin sent.

### G.6 Handoff (Phase 3, REQ-135)

**What starts it:** code, at a recorded turn of the newest Worker of an unfinished request whose tokens read since it started, or since its last handoff, reach `handoff.requestTokens` (`handoffCrossingOf`, §G.7), while handoff is on, the request is below `handoff.maxPerRequest` (its handoffs so far and its `no-safe-point` drops), none of it is pending, its Manager — for a mission request, the mission's current Main — is live, and its commands are below the loop guard. No model asks for it and the Orchestrator is not woken (ADR-029 decision 9; missions design §9.5). It is logged as a `handoff` intervention with trigger `threshold.crossed`.

*Retired by ADR-029 decision 9:* the Orchestrator's `bm_handoff` tool and the `threshold.crossed` wake.

**The sequence** (`server/handoff.ts`, kept in `server/handoff-store.ts` so a reload continues it; `shared/handoff.ts`).
1. **The outgoing Worker's note.** At the Worker's idle moment after a safe point — a bead closed with evidence (a successful `br close`, or a report naming closed beads), a `beads-done` / `bead-implemented` report, a verdict of its own Reviewer, or a wait by structure — the plugin sends a `BM-HANDOFF` notice; the Worker answers with `bm_report`'s optional last field `handoffNote` (≤ 1,500 characters), which the collector records. With no note the runner goes on at once when the note turn ends without one, else after 10 minutes; a `canceled` turn without the note is no answer. The maintenance ceiling of §G.5 applies (`maintenance.ceilingFactor` × `handoff.requestTokens`, or 30 minutes waited).
2. **The brief.** First line `BM-HANDOFF-BRIEF <id>`, at most 3,200 characters so it travels inside the 4,000-character command body, never cut mid-word; the stored file keeps the brief and the full note at `<data>/handoffs/<id>.json`, written with the `data-files.ts` rules and deleted by the cleanup. It is built on `workerHandoverFacts` (the fallback Worker handover's facts: the latest report, the review calls, the request's questions with their answers, the original request), masked with `redactText`, its short facts first (the newest report and its age), then the owner's later words, decisions, plan and document paths, bead state, open findings, branch and diff stat (read-only git), the note and a linked request's `peer:` / `peerAsk:` block, lists shortened to their newest items with `+n earlier` (base design §7.17.8 (h)).
3. **The command to the Manager.** `BM-COMMAND`, `intent: handoff`, `authority: coordination:handoff`, `effects: none`, `approved: none`, `to: manager`, no copy, both fixed limits and no backstop (its body is the plugin's brief) (change-008 C3).
   - *The authority* is the owner's Settings switch: the builder refuses `coordination:handoff` for any other intent, and the send refuses it while handoff is off. It goes through `command-send.ts` (counted by the loop guard) when the Manager is idle with nothing queued, waiting up to 30 minutes; its card reads "Coordination · handoff". `bm_govern`, `bm_direct_worker` and prepared commands cannot declare `handoff` (`DECLARED_COMMAND_INTENTS`).
   - *A bound Manager* (ADR-027; [base design §7.15](./paseo-bm.md), §16.9): the plugin creates the successor itself (`create-worker.ts`, `parent` the Manager, the labels plus `bm.handoffFrom`, a bound token, the `BM-BRIEF worker` line before the brief; a mission request's successor in the request's repo under its Main and on the roster), claiming the entry once (`claimCreation`) so exactly one successor exists; the command then only informs the Manager (`handoffInfoCommandOf`).
   - *An unbound Manager* creates the successor with `create_agent` (provider `bm-worker…`), the rendered brief as its first message and `bm.handoffFrom=<old>` among its labels, beside `bm.role` and `bm.requestId`.
4. **The request continues.** On `agent.created` (through `agent-labels.ts`'s hook), a Worker labelled `bm.handoffFrom` created by that Manager, in that workspace, for that request completes the handoff (a late successor, after 30 minutes, still does; the `BM-HANDOFF-BRIEF` line is a second signal, `handoffSuccessorsOf`). The old Worker is labelled `bm.replacedBy` through `paseo-cli.ts`, as the fallback switch does, is sent a `BM-REPLACED` notice (stop, no report, end the turn; its card reads "Handed over to another Worker"), stays idle and is never archived; delivery, the materialiser and the chat peers already skip a replaced Worker. The request keeps its id and the pairing check passes; `traces.get` carries an optional `handoffs: [{ agentId, from }]`, and Work's timeline shows "Handed over to Worker 2 from Worker 1".
5. **The successor proves again.** Its brief says to run the checks again before reporting anything done; a check counts only if run after the request's last handoff and after that Worker's first recorded turn (`evidence.ts`, §C.2).

**The outcome** (§G.3): from the successor's creation, met when its first three turns read at most 50 % of the old Worker's last three and it reports anything but `blocked` within 60 minutes; missed above 50 % or with no report; unknown with no successor or no turns to compare — so the A-12 guard can switch handoff off. The replacement Manager's handover drops a message the plugin's send log says it sent (`pluginSentBeside`).

**Role text.** The Manager gets one bullet: executing a handoff (it names the `bm.handoffFrom` label). The Worker gets one bullet: the handoff note and working from a brief. Both within their budgets.

### G.7 Settings → Coordination

Stored in `<data>/coordination/settings.json` (`version: 1`, the store rules) and read and set by the RPCs `coordination.settings` and `coordination.set` (`shared/coordination.ts`, `server/coordination-store.ts`, `server/coordination-rpc.ts`). These are the owner's surface: the Orchestrator can only propose a change (G.4), and the one write that is not the owner's is the A-12 guard's below. The cleanup button deletes the folder.

| Setting | Default | Bounds |
|---|---|---|
| `compact.enabled` | on, for Claude, Codex and OpenCode (`COMPACTION_PROVIDERS`) | switch |
| `compact.managerTokensPerTurn` | 390,000 — the Manager's p75 of tokens read per turn (change-008 C2) | 50,000–100,000,000 |
| `compact.workerTokensPerTurn` | 5,700,000 — the Worker's p75 | 50,000–100,000,000 |
| `compact.contextShare` | 0.5, where the provider reports it | 0.1–0.9 |
| `compact.maxPerAgent` | 2 | 1–5 |
| `handoff.enabled` | on | switch |
| `handoff.requestTokens` | 150,000,000 — the request p80 | 10,000,000–1,000,000,000 |
| `handoff.maxPerRequest` | 2 | 1–5 |
| `advice.everyFinished` | 5 — retired, a stored no-op (§G.4) | 0–50 |

The same file holds the settings other designs own: `main.*` (a Main's context, mission runtime design §3), `review.maxRereviews` and `review.callsPerBatch` (the review cap, delivery line design §5.6), `rollover.*` (delivery line design §2.6), `maintenance.ceilingFactor` (delivery line design §6.6), `integration.ci` (delivery line design §17.1), `line.supervised` (ADR-045), `cleanup.archive` and `cleanup.idleDays` (ADR-049, delivery line design §20.1), and the governor's thresholds `governor.*` (missions design §17). `COORDINATION_KEYS` lists every key `coordination.set` and a prepared `coordination.set` accept; the retired `review.smallBudget`, `review.mediumBudget` and `review.largeBudget` are ignored on read, dropped by the next write and refused (`RETIRED_COORDINATION_KEYS`).

Detail:
- **Schema** (`shared/coordination.ts`, pure). Each setting is read on its own: missing or out of its bounds, it reads as its default and costs no other (a Phase 2 file reads the newer ones as their defaults). Unknown keys are ignored and dropped by the next write. A newer `version` reads as the defaults and is never written. Bounds: `COORDINATION_BOUNDS`, `coordinationRuleOf`; a value out of bounds → `E_COORDINATION_INVALID` with the key's rule. `compact.enabled` is one switch, applied to `COMPACTION_PROVIDERS` (`compactionOnFor`).
- **Store** (`server/coordination-store.ts`): the alerts store's file rules (0700 folder and 0600 file created by a write only, atomic replace, symlinks refused). `readCoordinationSettings` is what the plugin's own readers use: no usable data folder or an unreadable store reads as the defaults.
- **RPCs** (`shared/contracts/orchestrator.ts`, re-exported by `contracts.ts`; handlers in `server/coordination-rpc.ts`): `coordination.settings {}` → `{ settings, defaults }`, reads only. `coordination.set { key, value }` → `{ settings }`, one setting per call (the same `{ key, value }` a prepared change carries). An unknown key or a value out of its bounds → `E_COORDINATION_INVALID`, checked before the data folder is looked at; no usable data folder → `E_DATA_HOME_UNAVAILABLE`; a newer or unwritable store → `E_COORDINATION_WRITE_FAILED`. Every refusal writes nothing. No agent tool sets these settings.
- **The crossing rules** are pure (`shared/coordination.ts`): `compactCrossingOf(role, turn, settings)` — tokens read against the role's threshold only when the provider counts the whole turn (Claude, `TOKEN_COVERAGE` `turn`); on Codex and OpenCode a turn reports its last call only, so it is judged by `compact.contextShare` alone; either crossing counts (reaching it is crossing), tokens first when both cross; `handoffCrossingOf(requestTokensRead)` against the request's tokens read since it started or since its last handoff; `mainContextCrossingOf` for a Main. Each returns `{ figure, value, threshold }`.
- **Switched off under A-12** (`server/coordination-guard.ts`, wired after the intervention check). A mechanism that is on is judged over its newest 10 met-or-missed entries recorded since the owner last turned it on (`guard.<kind>.countsFrom`); fewer than 10 → no judgement. Below 80 % the store switches it off (`switchOff`, which can only switch off; `guard.<kind>.switchedOff = { at, met, checked }`) and one `coordination-off` Inbox alert is raised for all projects ("Only 6 of its last 10 compactions met their goal (target 8). Compaction stays off until you turn it on in Settings → Coordination."). Only the owner turns it back on — in Settings, or by answering advice that carries `coordination.set` — which sets `countsFrom` to now, clears `switchedOff` and ends the alert.
- **Settings → Coordination** (`client/settings-section.tsx`, `settings-coordination.tsx`, `settings-coordination-model.ts`): the group after Autonomy, its meaning "When paseo-bm compacts an agent or hands a request to a fresh Worker, for every project. Each switches itself off if it stops helping." Cards, in order (`COORDINATION_CARDS`, then the switch cards): **Compaction**, **Handoff** and **Rollover** (status; Turn off at once, Turn on… after a confirmation with Cancel first; thresholds as typed fields, with − and + on a 1-1.2-1.5-2-2.5-3-4-5-6-8 ladder, the context share by 5 points; Save and Use the defaults), **CI**, **Supervised line**, **Archive finished agents**, then **Review** in a full-width row. **Reset coordination to defaults** fills every card's draft (each card's own Save sends it) and leaves the switches as they are. There is no advice card.
- **Defaults.** The token defaults were derived at the Phase 3 start from the replay of the whole field store (evaluation baseline report §6): each role's p75 of tokens read per turn and the request p80, rounded to two significant figures; `compact.contextShare` is the design's 0.5. Every replay saving behind them is an upper bound, and they are re-checked against a later window before any change.

### G.8 Guardrails and measures

**Quality comes first.** No review, check or blocking finding is traded for tokens or time. A-8's Phase 3 target on the heaviest requests holds only with no rise in:
- blocking findings per review batch;
- A-5;
- the finished-unverified share.

**Bounded.**
- Each intervention is logged (G.3), shown in the digest and measured (A-12).
- Settings switches compaction and handoff off at once.
- A release, data, security or cost effect needs a grant or a delegated class (§D.2), and its owner's tap a confirmation (§A.6).
- Agents belong to the owner.

**A-7 still holds** (< 20 % of wakes with no action): only the governor's events wake the Orchestrator (§A.8), and its own tokens are part of A-8.

**The Phase 3 exit** (change-008 C7) is judged over the combined field period's whole window: A-8 as the p90 of Worker tokens read per request against the pre-install reference of the baseline report (§6.8), with ≥ 25 finished requests with usage; the three quality guardrails above; and A-12 for `compact` and `handoff` over every entry checked in the window, a kind with fewer than 10 checked entries reported with its count, not called met.
