## 0. Principles (from the PRD §3) and what they mean in code

1. **Artifacts, not conversation.** A handoff is a typed record with one identity; chat text is a view of it.
2. **Workflow before agent.** Routing, ordering, deduplication, limits, authority are code. A model is woken only for judgement.
3. **Control matches risk** through declared effects, the owner's policy and one-use grants — never through prose patterns alone.
4. **Measure before promoting.** Every phase exit is judged on the replay; the evaluation suite (Evaluation design §6) runs once, at the programme's end.
5. **Delete what is superseded** in the same phase (§A.14, and each Part's retirement list).

**One idea carries Parts A and B: agents keep writing typed blocks with side-effect-free tools (ADR-010), and the plugin materialises state from those blocks at the end of the turn that wrote them** — keyed idempotently, because Paseo reuses turn ids. The Orchestrator, whose endpoint knows its caller (the secret path), writes state directly. This keeps caller identity out of the Worker, Manager and Reviewer tools.

## Part A — Phase 1 MVP: one source of truth for decisions and handoffs

### A.1 Scope

Owns: the decision model and store; materialising decisions from blocks; answering and delivering; the Orchestrator's decision tools, prepared actions and grants; typed commands (`BM-COMMAND` v2) and authority from declared effects; fallback incidents as decisions; the event bus to the Orchestrator and the Inbox's alerts; bounded coordinator context; capability limits per role; the rewritten role instructions; the new management surface and card system; the Phase 1 retirement.

Does not own: decision classes, policy and delegation (Part B); evidence classification (Part C); holding actions before they run (Part D).

### A.2 Architecture

```
 Worker ── bm_report(blocked, questions+effects) ──► BM-REPORT + BM-QUESTIONS ── send_agent_prompt ──► Manager
                                                             │ Manager turn_ended
 Manager ── bm_answers after the owner's typed message ──────┤ (collector → decision materialiser)
 Owner types in a Worker's chat ─────────────────────────────┤ Worker turn_ended
 Fallback incident (usage limit, login, …) ──────────────────┤
 Orchestrator ── bm_ask_owner / bm_decisions (secret endpoint)┤ direct write
                                                             ▼
                              decisions store  <data>/decisions/<workspaceId>.json
                  ▲ decisions.answer (Inbox, chat cards)     │ delivery by the plugin (notice queue):
                  │                                          │   answers → Worker · prepared action → Manager/Worker/fallback
 Inbox · Projects · cards (renderer) ◄─ decisions.list/get ┘   · owner's words → Orchestrator (with a grant)
                                                             │
 events: decision.opened · request.finished · request.stalled · worker.signal
        └─► event bus ──► Orchestrator (one batched message per idle moment) · Inbox alerts
```

### A.3 The decision model

`plugin/shared/decisions.ts` (zod, shared by server and client):

| Field | Meaning |
|---|---|
| `id` | Deterministic key: `q:<requestId>:<Qn>` (Worker question), `o:<uuid>` (Orchestrator), `f:<incidentId>` (fallback) |
| `workspaceId`, `requestId` | `requestId` null only for fallback incidents outside a request and Orchestrator decisions about a whole project (a Worker question always has one) |
| `askedBy` | `{ role: worker \| orchestrator \| plugin, agentId \| null }` |
| `askedAt`, `round` | first-seen time; the Worker's report round (for grouping on one card) |
| `question`, `subject` | text (≤ 1,000); `subject` a short slug the asker gives (used by supersession now, by precedents in Part B) |
| `options[]` | `{ key, label, recommended, effects: Effect[], action?: PreparedAction }`; one recommended at most |
| `effects` | `none, commit, push, publish, deploy, real-data, migration, dependency-install, network, outside-workspace, security, cost` — declared by the asker per option |
| `status` | `open → answered \| superseded \| withdrawn \| expired`; `open → needs-confirmation` when an owner message in a chat may have answered it (A.5 c) |
| `answer` | `{ by: owner \| orchestrator \| policy \| precedent, via: inbox \| chat-card \| chat-manager \| chat-worker \| chat-orchestrator \| autopilot, optionKey \| words, at, reason?, class?, predictor?, precedentId? }` — the Orchestrator answers `by: policy` (§B.5). `by: orchestrator` (`via: autopilot`, Phase 1's Autopilot answers, change-004) and a stored `predictor` (builds before ADR-025; `policyPredictorOf`: a `policy` answer without one is the Orchestrator's, a held request's none) are only read: `answerDecision` refuses a new `by: orchestrator` answer (`invalid-answer`) |
| `grant` | `{ effects, expiresAt, usedAt \| null }` — REQ-112 (b) |
| `delivery` | `{ to, kind, at, outcome: sent \| queued \| failed }` |
| `supersedes`, `supersededBy` | ids |

Rules: a Worker question may re-ask with `supersedes: "Q3"` (new optional field of the `bm_report` question schema) or with the same normalised text → the old one becomes `superseded`. An Orchestrator decision supersedes the open Orchestrator decision of the same request unless it passes `separate: true`. A superseded, withdrawn or expired decision is never answerable; the tool that caused it returns the id it replaced.

**Expiry of a Worker question.** A `q:` decision that is `open` or `needs-confirmation` expires when its request's `finished` report is recorded: at a Manager's turn end, a `BM-REPORT` with `phase: finished`, in an incoming message that is neither the owner's nor a plugin notice, expires every such question of the request the report names that was asked no later than the report (`settledAt` = the report's message time). The materialiser (`expireFinished`) writes each in its own store transition after the turn's openings and answers (§A.5), so an answer given meanwhile, or by the owner in the same turn, stands; a question asked after the report stays open. `o:` and `f:` decisions never expire this way; the owner's open overrides (`r:`, §B.7) of a request's questions expire with them, overrides of `o:` and `f:` decisions never do. An expired decision leaves the Inbox, is refused by `decisions.answer` (`E_DECISION_SETTLED`), `bm_decide` and `bm_predict`, and is never delivered; its card reads **Expired** with "The request finished."

`PreparedAction` is a union: `answer-worker` (implicit for Worker questions: deliver the answer), `command { to: manager | worker, agentId, intent, body, effects }` (Orchestrator decisions; P5), `fallback { action: switch | wait | resend | dismiss, target }` (fallback incidents).

Two bookkeeping fields complete the record: `settledAt` (set exactly when the status is final) and `needsConfirmation { via: chat-manager | chat-worker | chat-orchestrator, at }` (set exactly while `needs-confirmation`). The transitions are pure functions in the same module (`answerDecision`, `markNeedsConfirmation`, `confirmDecision`, `supersedeDecision`, `withdrawDecision`, `expireDecision`, `useGrant`); each returns the next record or a refusal and never reads a clock. An answer grants the chosen option's effects, or every effect the decision declares for own words (`none` never granted; nothing to grant → no grant). A chat answer the owner confirms (`decisions.confirm`) records no option, no words and no grant, because the plugin never read what was authorised.

**Ask back thread** (change-014, `shared/decision-threads.ts`, pure): one per decision, `{ decisionId, entries: [{ by: owner | asker, text ≤ 2,000, at, agentId? }] }` — on the owner's entry `agentId` is the asker it went to, on the asker's the agent that replied when known. Only an unsettled `q:` or `o:` decision has one (`askableKindOf`): a held request's Worker is mid-call, a fallback incident and an override have no agent to ask. An ask is open while the last entry is the owner's (`hasOpenAsk`): one reply per ask. The thread never changes the decision, which stays open.

### A.4 The store

`plugin/server/decision-store.ts`: `<data>/decisions/<workspaceId>.json` = `{ version: 1, entries: Decision[] }`, `0600` files in a `0700` folder, atomic writes, on the JSON store factory (`createJsonFileStore`, `server/data-files.ts`): a missing or corrupt file reads as empty, a bad entry is skipped alone, a file a newer paseo-bm wrote reads as empty and is never written (a coded error), symlinks are refused, and no lock is needed because every operation is synchronous in the one plugin-server thread, so a read-modify-write cannot interleave. The alert, policy, precedent, intervention and coordination stores below follow the same factory rules. Open decisions are never evicted; settled ones keep the newest 500 per workspace. `decisions.list` reads every workspace file with an mtime cache. Cleanup deletes the folder; deleting a request's traces deletes its settled decisions. Opening is idempotent by id, and a `supersedes` naming an unsettled decision of the workspace supersedes it in the same write. Ask back threads (change-014, `server/decision-thread-store.ts`): `<data>/decisions/threads/<workspaceId>.json` = `{ version: 1, threads }`, same factory rules, text masked before it reaches the disk, the newest 20 entries per decision and 500 threads per workspace; deleted by the cleanup with `decisions/`.

### A.5 Materialisation (`plugin/server/decision-materialiser.ts`, on the collector's `onRecorded`)

The `BM-QUESTIONS` block carries the new fields as optional bracketed tags, so the text stays readable and older blocks still parse (each tag is optional; an unknown tag is ignored):

```
BM-QUESTIONS
requestId: req-20260929T073348Z
Q4: Push both backends to origin/dev? [subject: push-backends] [supersedes: Q2]
- a: Push contract only (recommended) [effects: push]
- b: Push both, manifest by hand [effects: push]
- c: Hold
```

`bm_report` gains the matching optional fields (`subject` ≤ 60 characters `[a-z0-9-]`, `supersedes` a `Qn` of the same request, `effects` per option from §A.3's list) and writes the tags; `parseQuestions` reads them; `bm-format.ts` accepts them.

a. **Open** — at a Manager's turn end, each `BM-QUESTIONS` in an inbound message that is not the owner's opens `q:<requestId>:<Qn>` if absent; re-reading the same turn (reused turn ids) changes nothing.
b. **Answer through the Manager** — at a Manager's turn end whose inbound messages include the owner's typed message (`origin: "user"`), each `BM-ANSWERS` block the Manager wrote in its reply (built with `bm_answers`) settles those decisions with `via: chat-manager`. The Manager sends no answer to the Worker; the plugin delivers (A.6).
c. **Answer in a Worker's chat** — at a Worker's turn end, an owner-typed message holding a `BM-ANSWERS` block settles the named questions (`via: chat-worker`); any other owner text in that Worker's chat while decisions of its request are open marks those **asked before that message** `needs-confirmation` (the message that started the turn in which the Worker asked cannot have answered it): the card says "You wrote in the Worker's chat at <time>. Choose an answer, or close it if that message answered it.", keeps the options and adds *Close as answered* / *Keep open*.
d. **Fallback** — each pending incident of `role-fallback-state.json` opens `f:<incidentId>` with the fallback actions (switch, wait, resend, dismiss) as prepared actions; resolving the incident any other way withdraws it.

Detail for a–c (`server/decision-materialiser.ts`):
- The collector hands `onRecorded` the record it just wrote (texts already masked); a–c read that record's `sent` (with `origin`) and `received`, never the store back. The block readers (`readableOf`, `questionBlockOf`, `answerBlockOf`) live here.
- Open: `askedBy.agentId` is the live Worker labelled `bm.requestId = <requestId>` (the Manager's child first, else the only one of the workspace), null when not known for certain. A block's questions share one round: the stored round of any of them, else the request's highest round plus one. `askedAt` is the carrying message's time. A `[supersedes: Qn]` tag links only a question that is stored; the text match (case, punctuation and spacing ignored) replaces only an unsettled question.
- Answer lines: a leading option letter (`a — …`, `(a) …`, `a: …`, a bare `a`) is the option when the decision has it; otherwise the line, without an `other —` prefix, is the owner's words. The answer's time (and so the grant's hour) is the owner's message time — the last owner message of a Manager turn. A Manager's replies are read one by one and joined, so a streamed block still reads.
- `needs-confirmation` applies to the open `q:` decisions of the Worker's request (the record's `requestId`) and is remembered by owner message (agent, time, text) for the plugin run, so re-reading a record never re-marks a question the owner kept open.
- The decisions a turn answered go to the same `onSettled` hook as `decisions.answer` (`settledByKind` in `index.server.ts`), which the delivery (A.6) completes.

A bound Worker (ADR-027) opens its questions with `bm_questions`, on this section's open path extracted and shared (`openQuestions`), and a bound Manager's `bm_answers` are proposed answers that the materialiser settles at the Manager's turn end by rule (b), only when the turn holds the owner's own message ([base design §7.15](./paseo-bm.md)).

### A.6 Answering and delivery

RPCs (`plugin/shared/contracts.ts`, additive; handlers in `plugin/server/decision-rpc.ts`): `decisions.list { scope: inbox | workspace | request, workspaceId?, requestId?, status?, limit? }` → `{ decisions, truncated }` (`inbox`: unsettled decisions of every workspace or of `workspaceId`, oldest asked first; `workspace` and `request`: every stored one, newest asked first; `limit` ≤ 500, default 200; no usable data folder reads as none), `decisions.get { id }` → `{ decision }`, `decisions.answer { id, optionKey?, words?, confirmed?, via?: inbox | chat-card }` → `{ decision }`, `decisions.confirm { id, answered: boolean }` → `{ decision }`. An answer that would grant `push`, `publish`, `deploy`, `real-data`, `migration`, `security` or `cost` needs `confirmed: true` (experience concept X-4: release, data, security, cost). Error codes: `E_DECISION_NOT_FOUND`, `E_DECISION_SETTLED` (answered, superseded — the message names the replacing id —, withdrawn or expired), `E_DECISION_ANSWER_INVALID` (not exactly one of `optionKey`/`words`, blank words, unknown option), `E_DECISION_NOT_CONFIRMED`, `E_DECISION_NOT_NEEDS_CONFIRMATION` (`confirm` on a decision not waiting for one), `E_DECISION_WRITE_FAILED`, and `E_DATA_HOME_UNAVAILABLE`; every refusal writes nothing. After the answer and grant are stored, the handler hands the settled decision to an injectable `onSettled(decisions, { paseo })` hook — the delivery below; a failing hook is logged and never fails the answer. The client polls an open decision every 5 s while shown (REQ-111 b); a settled one stops polling.

Delivery, by the plugin through the notice queue:
- **Worker question (DQ-2):** each answer is delivered as soon as it is given — at the Worker's next idle moment, one `BM-ANSWERS` block holding every settled, undelivered question of that request (kind `answers:<requestId>`, so a newer block replaces an unsent older one); questions still open stay open and the Worker carries on with what it has. No **Send** button, no waiting for the whole round.
- **Orchestrator decision with a prepared command:** the `BM-COMMAND` v2 (A.7) goes to its target with `authority: owner (decision <id>)` and `approved: <the option's effects>` — the owner's choice needs no further gate.
- **Orchestrator decision answered in words:** a `BM-ANSWER` block (`decisionId`, the words, the grant) goes to the Orchestrator; the grant allows exactly the decision's declared effects for one command within 60 minutes.
- **Fallback:** `fallback.act` with the prepared action.

Detail for Worker questions (`server/decision-delivery.ts`, wired as the `question` kind of `settledByKind` and as the materialiser's `afterTurn`):
- The message is `Continue <requestId>.`, a blank line, then `answersText` over every answered `q:` decision of the request whose `delivery` is null or `queued`, in question order (`Qn: a — <label>`, `Qn: other — <words>`). Target: the request's sole live Worker of the workspace (`soleWorkerOf` over the agents' labels, fallback-replaced Workers left out); none or several → every included decision is recorded `failed` (to the asking Worker) and nothing is sent. A queue `dropped` (archived, closed, gone, send failed) is `failed` too; a `failed` delivery is never retried.
- Recorded per included decision: `sent` (the Worker was idle), `queued` (held for its turn end). A `queued` decision becomes `sent` when a Worker's turn record carries an answers block naming it (the block arrived), or when this run's queue no longer holds its `answers:<requestId>` notice; it is then left out of the next block.
- An answer given in the Worker's own chat (`via: chat-worker`, including a confirmed chat answer) is not sent: it is recorded `sent` at the answer's time. Without a Paseo handle or data folder nothing is recorded and a later trigger delivers it.
- Once per plugin run — at the first settlement or recorded Manager or Worker turn with a Paseo handle, after that turn's arrivals are noted — every answered `q:` decision whose delivery is null or `queued` is delivered again, one block per request. A `queued` block sent just before a reload can therefore reach the Worker twice; an answer is never lost. One delivery runs per request at a time; a settlement meanwhile makes it look once more.

Detail for the Orchestrator's decisions (`server/orchestrator-decide-tools.ts` `bm_ask_owner`, `server/orchestrator-decisions.ts`, wired as the `orchestrator` kind of `settledByKind`):
- `bm_ask_owner { workspaceId, requestId?, managerId?, question, recommendation, options?[≤ 5]{ label, effects[], recommended?, command?{ to: manager | worker, agentId, intent, body } }, subject?, separate? }` stores `o:<uuid>` with keys `a`–`e`; the stored question is the question, a blank line and `Recommendation: …` (≤ 1,000 in all); at most one option is recommended; an option's `effects` are also its command's. A prepared command is checked as it will be sent: its target is a live, non-archived paseo-bm agent of that role in the project (never a Reviewer), the block can be written, and the backstop finds no category in the option's label and body that its effects do not declare. Supersession: the Orchestrator's unsettled `o:` decision of the same request (or, both without one, of the same project) — the newest of the same `subject` when there is one, else the newest; the answer returns `{ decisionId, replaced }`, `replaced` only when the store did supersede one.
- Prepared command chosen: `BM-COMMAND` v2 `from: orchestrator` (it prepared it), `via: tab` (the owner's tap), `re:` the option's label, `why: The owner chose "<label>" on decision <id>.`, `authority: decision:<id>`, `approved:` the option's effects the answer granted, `limits:` derived. Queue kind `command:<id>`; a Worker's Manager gets the `copy: yes` block. The target is re-checked at delivery; the command then leaves through the one send pipeline of `bm_send_command` and `bm_direct_worker` (`server/command-send.ts`, Orchestrator design §7): the grant is claimed and spent only once delivered, the command is written to the commands store (`proposals.json`, source `chat`) and so counts toward the loop guard. The owner's own choice is counted and never refused there; a choice by the policy or a precedent is refused when the guard is full. A command that cannot be delivered or is refused spends nothing, is recorded `failed`, and the Orchestrator gets the `BM-ANSWER` with a `delivery:` line saying why, so it can act on the unused grant.
- `BM-ANSWER` (a plugin notice, matched as a whole word so the owner's `BM-ANSWERS` never is): `decisionId`, `workspaceId`, `requestId` (or `none`), the question's first line, `answer:` (`option <key>: <label>`, or the owner's words after the header), `grant: <effects>, for one command with decisionId <id>, until <expiresAt>` (or `none`), then one instruction line. Queue kind `answer:<id>`, to the current main Orchestrator; with none open it is recorded `failed` and the Orchestrator reads it later with `bm_decisions`. An option without a command gets the same notice.
- Each decision is delivered once (a recorded `delivery` is never repeated); a confirmed chat answer (no option, no words) delivers nothing.

Detail for the Orchestrator's answer to a Worker's question (`bm_decide`, `server/orchestrator-decide-tools.ts`; its authority is the policy, §B.5 — Phase 1's Autopilot authority, change-004, is retired, §B.8, and its stored answers `by: orchestrator, via: autopilot` stay readable):
- The answered decision goes to the same `onSettled` hook as `decisions.answer` (`settledByKind`, wired in `index.server.ts`), so the Worker gets it as `BM-DELIVERY answers` at its next idle moment, in one block with the request's other undelivered answers; the tool's reply says whether it was sent, queued or could not be delivered. A failing delivery is one log line; the answer stands. From the read to the write nothing awaits, so no other answer comes between (§A.4). The first answer wins both ways: a later answer is refused `E_DECISION_SETTLED`, and every refusal of a settled decision names who answered.
- `bm_direct_worker` and `bm_send_command` refuse a command whose `BM-ANSWERS` block names a `Qn` that has a stored decision of that request — the block's `requestId:`, else a request id in the text, else the command's `requestId`, else (to a Worker) the Worker's `bm.requestId` label: open → "answer it with bm_decide, not in a BM-ANSWERS block"; answered → "already answered by the owner / the Orchestrator"; needs confirmation, superseded, withdrawn or expired → said as such (`refuseStoredAnswers`). A block naming only questions the store does not hold is sent as before.
- Views: a policy answer's card is §B.5's; a stored Phase 1 answer reads "answered by the Orchestrator · <time>", with the reason under Details and no answer buttons. A settled decision leaves the Inbox's Needs you. `bm_decisions` hands out each answer's `by` and, for the Orchestrator's, its reason.

Detail for **Ask back** (change-014 outcome 3, bead `bm-njdo.3`; `server/decision-ask.ts`):
- **RPCs** (`shared/contracts/decisions.ts`): `decisions.ask { id, text }` → `{ thread, delivery: sent | queued | failed }`, `decisions.thread { id }` → `{ thread }`. Errors: `E_DECISION_NOT_ASKABLE` (not a `q:` or `o:` decision), `E_DECISION_ASK_INVALID` (blank or too long), `E_DECISION_SETTLED`, `E_DECISION_NOT_FOUND`, `E_DECISION_WRITE_FAILED`, `E_DATA_HOME_UNAVAILABLE`. The owner's text is masked and appended first; the decision is never touched.
- **Delivery** through the notice queue, never into a running turn, kind `ask:<decisionId>` (a newer ask replaces one still queued): a `q:` goes to `askedBy.agentId`, else to the request's sole live Worker (`soleWorkerOfRequest`); an `o:` to the Orchestrator open now. None found: the question stays in the thread, `failed`.
- **`BM-ASK`** (a plugin notice, matched as a whole word): `BM-ASK`, `decisionId: <id>`, the decision's question (≤ 300 characters), the owner's text quoted line by line with `> `, how to answer (`bm_reply`, carry on with what does not depend on it, do not answer the decision), then the fallback line `BM-REPLY <decisionId>`.
- **`bm_reply { decisionId, text }`**, run on the plugin server and pre-approved: the Worker's face (`q:` only; `WORKER_SERVER_TOOLS` at `/mcp/worker`, after `bm_report`) and the Orchestrator's (`o:` only; its 16th tool). One thread append; accepted only while the decision is unsettled and its ask is open — once per ask. It answers nothing.
- **Fallback** for an agent created before `bm_reply` (Paseo gives tools at creation): at a recorded Worker turn end, the Worker's own message whose first line is `BM-REPLY <decisionId>` is appended by the same rule, only from the agent the ask went to. The Orchestrator's turns are not recorded, so an Orchestrator on older instructions has no reply path until it is replaced.
- Each reply turn of a Worker also wakes its Manager once (`notifyOnFinish`). The card is the Dashboard design's (§A.12 below).

A bound Manager's follow-ups to its Worker go through `bm_tell_worker`, and a bound agent's reports and reviews arrive as `BM-DELIVERY` records from the outbox; Paseo does not wake the creator of an agent the plugin created, so a bound Worker's turn end wakes its Manager only through a delivery ([base design §7.15, §7.16](./paseo-bm.md)).

### A.7 Typed commands and authority (`BM-COMMAND` v2)

Header lines added: `intent: answer | continue | redirect | stop | release | other`, `effects: <list or none>`, `authority: owner | decision:<id> | policy:<class>` (§B.9; Phase 1's `autopilot` is retired, §B.8, and only read in stored history), `approved: <effects the authority covers>`. `limits:` is derived: the fixed limits (no commit/push/deploy, no real data) minus what `approved` covers — a delivered command never carries a limit that contradicts its approval. The parser reads v1 blocks (no `intent`) as before.

Authority check for `bm_send_command` / `bm_direct_worker` (replaces the gate as the authority): every declared effect must be covered by a live grant (`decisionId` input), by the owner's policy where every class of the effects is delegated (§B.9; since ADR-025 any class, push, publish, deploy, real data, migration, security and cost included), or — for effects outside `release, real-data, migration, security, cost` — by the owner's own word in the Orchestrator's chat. The regex gate (`decision-gate.ts`) stays as a **backstop**: a category it finds that the declared effects do not include refuses the command with "declare the effect or ask the owner" — never a silent send.

Detail (`shared/orchestrator-command.ts`, `server/command-authority.ts`):
- Header order after `re:`: `intent`, `effects`, `authority`, `approved`, then `limits` (only `from: orchestrator`). `effects`/`approved` list real effects in `EFFECTS` order, or `none`. A fixed limit that is partly approved is split into `no-<effect>` for what it still withholds (`approved: push` → `limits: no-commit, no-deploy, no-real-data`); the parser refuses a v2 block whose limits withhold an approved effect, or that carries only some of the four v2 fields.
- Both tools require `intent` and `effects` (`["none"]` for none). The decision-only effects are `CONFIRM_EFFECTS` (push, publish, deploy, real-data, migration, security, cost). Without `decisionId`: the owner's policy first (`authority: policy:<class>`, §B.9), which covers any effect whose classes are all delegated (ADR-025); else a command declaring one of them is refused ("needs the owner's decision"); else the owner's own latest word in the Orchestrator's chat (`authority: owner`), which covers every effect except those. Every command the Orchestrator sends itself leaves `via: chat` and is recorded with source `chat` (§B.8 as built).
- The policy authority: the policy is read at each send (`autonomy-store.ts` `currentPolicy`, the one read every reader uses; a store that cannot be read reads as every class `owner`). The command's classes are its declared effects' (`commandClassesOf`: §B.1's map, `commit` — and a command that declares no effect — counting as `reversible-technical`). When every one is `delegate` for the project (`modeOf`), the command goes with `authority: policy:<riskiest>` and `approved` its declared effects, without reading the Orchestrator's chat, `via: chat`. It comes before the owner's word, so a command both cover names the policy. Otherwise the refusal names the classes not delegated, riskiest first, then the owner's missing word ("reversible-technical is not delegated in this project and the owner has not just told you to send; ask the owner with bm_ask_owner, with this command prepared on an option"). The parser and the builder take `policy:<class>` for each of the nine classes and refuse any other; the owner's own command still carries only `owner`. The command card's authority reads "Policy · <class>". A `policy:<class>` authority approves what the delegated classes cover — push, publish, deploy, real-data, migration, security and cost included where their classes are delegated (ADR-025). While its request stands finished-unverified, a policy command that commits or releases still needs the owner's word, and one declaring a release, data, security or cost effect is refused (§C.6). The policy answers no `o:` decision (§B.5), so this authority comes only from a command of the Orchestrator's own. With `decisionId`: it must name an `o:` decision of the project that the owner answered and, when it has a request, the same request; the grant (`grantRefusal`) must cover every declared effect; a grant the owner's policy gave holds what its delegated class allowed (ADR-025). It needs no word in the chat (`via: chat`). A decision that granted nothing authorises only a command that declares no effect.
- The grant is spent (`useGrant` through the store's `transition`) only after the command is delivered; an in-memory claim keeps two concurrent calls from spending one grant. A delivery that fails spends nothing.
- No tab sends commands (§A.14): an option the owner picks on an `o:` decision delivers its prepared command as v2 `via: tab` with `authority: decision:<id>`; `from: owner` is only read from older builds. Nothing silences the backstop (§B.8). The fixed limits stay only as the base the `limits:` line is derived from.

### A.8 Events to the Orchestrator and the Inbox

`plugin/server/event-bus.ts` replaces `BM-STALL`, `BM-EVENT` and the `autopilot-on` prompt with typed events: `decision.opened` (by §B.9's per-cell rule), `request.finished`, `request.stalled` (no Worker or Reviewer of an unfinished request running for 5 min; a review over budget), `worker.signal` (the live watch's signals) — the last three only for the projects in the owner's policy scope (Scope below). There is no `waiting-user` or `manager-turn` event: a question waits in the Inbox, and the Manager relays nothing.

Open alerts live in `<data>/inbox/alerts.json` (`{ version: 1, entries: { <key>: { workspaceId, kind, subject, since, clearedAt } } }`, same file rules as the decision store): raised once per key, cleared when the condition ends (an agent runs again, the permission is answered, the Worker's turn ends); this replaces the stall and signal keys of `orchestrator/stalls.json`.

Delivery: to the Orchestrator, all events pending at its idle moment go as **one** `BM-EVENTS` message (the notice queue gains a batch kind), each event one short line with the ids to look up; an event is dropped when its subject settled before delivery. To the owner: `request.stalled` and the `permission`, `danger`, `stuck` signals are **Inbox alerts** — never messages.

Detail (`server/event-bus.ts`, `server/alert-store.ts`, `shared/alerts.ts`; `server/stall-watcher.ts` and `server/worker-watch.ts` as its sources):
- **Scope** (change-007 C1). `request.finished`, `request.stalled` and `worker.signal` are published only for a project with at least one class above `owner` in the policy (§B.2: a `shadow` or `delegate` cell; `projectsAboveOwner` in `shared/autonomy.ts`), and dropped at delivery when that project fell back to all-`owner` meanwhile (a reset, or its cells set back to `owner`) — elsewhere the Orchestrator acts only when the owner talks to it, and what needs the owner is in the Inbox. The scope is read from `autonomy/policy.json` at each publish and at delivery (`eventScopeOf`); a policy that cannot be read is the empty scope, with one log line. The challenger switch alone does not put a project in the scope. `decision.opened` is not scoped by it: it follows the per-cell rule of §B.9 alone (the next two bullets). The Orchestrator's instructions say: "a decision only to decide or predict it, the rest only where the owner's policy shadows or delegates a class". `decision.opened` comes from the `q:` decisions the materialiser opened in the recorded turn and from the `f:` decision a new fallback incident's listener opened (`registerFallbackRpcs`' `onDecisionsOpened` → the bus's `decisionsOpened`, as stored after a precedent or the policy answered it); an `o:` decision is the Orchestrator's own and never raises one. `request.finished` comes from each `finished` report of a recorded Manager turn, in the same `onRecorded` call as the turn's questions, so they reach the Orchestrator together.
- **The challenger's prediction** (change-007 C1). A decision the Orchestrator did not ask, still `open`, of any class (ADR-025) in an `owner` or `shadow` cell of a project whose challenger is on (a level of 1 or more), opened with its predictions recorded and not predicted yet (`predictionRefusalOf` in `shared/autonomy.ts`), raises a `decision.opened` with `asks: "prediction"`. Its line ends "A prediction is asked: read it with bm_decisions and give the option you expect the owner to choose with bm_predict, with your reason in one line. The owner sees it as your proposal and decides: answer nothing." Same type and dedupe key as every `decision.opened`, and at most one event per decision. It is published whatever the policy scope — a project whose cells are all `owner`, every new project, included — and never for a `delegate` cell. The policy is read at the turn's publish and again at delivery (`eventPolicyOf`; unreadable = no challenger on), and the event is dropped when the decision may no longer be predicted: settled or waiting for a confirmation, the challenger turned off, its cell delegated, or predicted already. A fallback incident (`f:`) raises it from its listener (Scope above); the start-up pass and the pass after an action raise none, and `bm_predict` accepts such an incident all the same (§B.3).
- **The delegation to the Orchestrator** (§B.5). A decision the Orchestrator did not ask (`q:`, `f:`), still `open`, of any class that is `delegate` in its project (`decideRefusalOf` in `shared/autonomy.ts`; ADR-025) raises a `decision.opened` with `asks: "decision"`, whose line ends "A decision is asked: the owner's policy delegates its class to you. Read it with bm_decisions and choose the option the owner would, with bm_decide and your reason in one line." The two rules never both hold (a `delegate` cell is not predicted). The policy is read at the publish and again at delivery, and the event is dropped when the decision may no longer be decided: settled or confirming, its cell set back, reset or changed by a new level. An `owner` or `shadow` cell with the challenger off raises nothing. A decision that waits for `bm_decide` and gets none stays open in the Inbox for the owner: nothing times out into an answer, and it is not told again.
- **Only a judgement wakes** (REQ-115 b): a decision raises `decision.opened` only when the policy asks the Orchestrator to decide or predict it (the two bullets above). No class is excluded (ADR-025): a release, data, security or cost decision is predicted or decided by the same rule, at the project's level; a `finished` report raises `request.finished` only when it shows work left — ready beads, open review findings, blockers, or failing checks (`workLeftOf`); a finished-unverified finish counts as work left too (§C.3).
- **Dedupe keys.** `decision.opened:<id>`, `request.finished:<ws>:<requestId>@<report time>`, `request.stalled:<ws>:<requestKey>@<alert since>`, `worker.signal:<ws>:<worker>:<signal>@<alert since, or the turn start>`; a key is published once per plugin run. Across reloads the sources dedupe themselves (a decision opens once, an alert is raised once, a turn is recorded once); only `failing`, `heavy` and `outside` may be told once more after a reload mid-turn.
- **Settled** (dropped at delivery): a decision no longer open or needs-confirmation; a stall or signal whose alert was cleared; a `failing`/`heavy`/`outside` signal whose Worker's turn ended.
- **Batch kind.** `enqueueBatch(target, { name: "BM-EVENTS", compose }, items)`: the items of one call are queued, then delivered once; at the target's idle moment every pending item of that batch goes as one message, oldest first, each item's `isCurrent()` read synchronously right after the idle read. A batch counts as one notice (the queue's one-per-idle-moment rule), and a batch whose every item settled sends nothing and lets the next notice go.
- **Stall pass.** Always on (no switch), every project with activity in 24 hours: `idle-unfinished` (5 minutes, the last report not `finished`, no unsettled decision of the request) and `review-over-budget`; a request with an unsettled decision is not stalled (it waits in the Inbox), whatever its last report says (ADR-024), and a malformed report alone is no stall. One `request-stalled` alert per request (subject the request key, `detail` the reasons); `orchestrator.state` reads it as a project's `stalled` state.
- **Worker watch.** Running Workers of **every** project, every 2 minutes, at most `MAX_WATCHED_WORKERS` (5, the newest) per pass, 300 timeline entries each; with no running Worker nothing is refreshed or read. `stuck`, `permission` and `danger` raise the Worker's `stuck`, `permission-waiting`, `danger` alert (subject the Worker id, `detail` the redacted evidence, ≤ 300 characters) in every project: they cost no model call. Only in the policy scope does the pass that raises an alert publish its `worker.signal` event, a newly raised `danger` open the interrupt allowance (still in `orchestrator/stalls.json`, its one remaining key), and `failing`, `heavy` and `outside` become events; an alert raised while its project was outside the scope is not told when the project enters it. `stuck` and `permission` clear when no longer seen; all three at the Worker's recorded turn end or when it stops running. A project that leaves the scope keeps its alerts; its pending events are dropped at delivery.
- **Alerts file.** `<data>/inbox/alerts.json`, key `<kind>:<workspaceId or ->:<subject>`, optional `detail`; the cleanup button deletes `inbox/`. Open alerts are never evicted, cleared ones keep the newest 500. Other producers: `off-tool-reviewer` and its `worker.signal` kind `off-tool-review` (base design §7.7, ADR-027), `pairing-mismatch` (`role-pairing.ts`, through `raiseInboxAlert`), `fallback-failed` (an answered `f:` decision whose `delivery.outcome` is `failed` while its incident is pending; cleared once the incident is not). `outdated-agent` (`outdated-agents.ts`, §A.11): one per live Manager, Worker or Reviewer on older instructions, cleared once it is current, replaced, archived, closed or gone. The `autonomy-demoted` kind is removed with demotion (ADR-025, §B.4): an old entry is skipped on read and dropped by the next write.
- **Wakes recorded.** Each delivered `BM-EVENTS` message is one wake in `orchestrator/wakes.json` (the notice queue's batch `onSent`: Orchestrator id, time, projects, number of events); the Orchestrator's next turn end (the batch's `onTurnEnded`, called by the queue at that turn end before it delivers anything else) sets `endedAt` on its oldest open wake. Ids, times and a count only; the evaluation's A-7 reads it (evaluation design §4).
- **Retired.** `BM-STALL` and `BM-EVENT` (producers and notice prefixes), `server/autopilot-events.ts` (`question`, `finished`, `manager-turn`, `autopilot-on`), the Watch switch (the settings file has no `watch`; its RPC went with the sweep, §A.14), the stall, event and Worker-signal keys of `orchestrator/stalls.json` (ignored, dropped at the next write).

### A.9 Bounded context

Orchestrator tools return typed summaries by default: `bm_request` ≤ 4,000 characters (`detail: "full"` keeps 60,000), `bm_agent_messages` 5 messages of ≤ 1,500 characters (`detail: "full"` keeps 50 × 12,000), `bm_projects` counts and open decisions only. A new read tool `bm_decisions { workspaceId?, requestId?, status? }` lists decisions. The Manager gets a read-only `bm_decisions` face too (its block tools stay side-effect free: it reads decisions by `requestId`).

Detail (`server/decision-tools.ts`): `bm_decisions` returns `{ decisions, total, truncated }`, newest asked first, each redacted with the owner's words cut to 1,000 characters, the answer's `by` (and the Orchestrator's `reason`, change-004) and a prepared action as one line; `status` also takes `unsettled` (open or needs-confirmation), `limit` 1–50 (default 20). The Orchestrator's face (in its endpoint) includes each grant; the Manager's (`MANAGER_SERVER_TOOLS`, `{ requestId, status? }`, served at `/mcp/manager` and pre-approved after `bm_answers`) reads that request's decisions of every project, at most 50, without grants, through the store's read path only (nothing is created or repaired). `bm_projects` lists each project's unsettled decisions of every kind from the store, oldest first, at most 10, with `counts.openDecisions` the total.

### A.10 Capability limits per role (REQ-116)

Paseo 0.9.2 treats an alias with no `paseoTools` policy as enabled while `mcp.injectIntoAgents` is on: its agent gets all 39 Paseo tools, `create_agent`, `kill_agent`, `archive_agent`, `respond_to_permission`, `set_agent_mode` and `update_agent` included ([run note](../archive/operations/paseo-bm-role-tools-run-20260929.md)). So every `bm-*` alias (and fallback alias) carries a policy, chosen in `setup-roles.ts` and written by `config-writer.ts`. Paseo resolves the policy each time a session opens (create, resume, refresh), so an existing agent picks it up at its next session open ([ADR-020](../adr/ADR-020-paseo-tools-policy-per-role.md)):

| Role | `paseoTools` |
|---|---|
| Reviewer, Orchestrator | `{ enabled: false }` |
| Manager | `{ enabled: true, disabledTools: [kill_agent, archive_agent, archive_workspace, respond_to_permission, list_pending_permissions, set_agent_mode, update_agent, create_schedule, update_schedule, delete_schedule, run_schedule_once, pause_schedule, resume_schedule, create_heartbeat, delete_heartbeat] }` |
| Worker | the Manager's list plus `create_workspace`, `rename_workspace` |

Role pairing (only the Manager creates Workers, only a Worker creates Reviewers): `before("agent.create")` cannot refuse a creation, because its request carries no creator id (AGENTS.md, *Verified facts*; run note `docs/archive/operations/paseo-bm-role-pairing-run-20260929.md`). The `agent.created` handler (`role-pairing.ts`, wired in `agent-labels.ts`) reads `parentAgentId`, judges the creator by its **provider** (not its label, which can change), and on a mismatch calls `raiseRolePairingAlert`, which raises the `pairing-mismatch` Inbox alert (one log line when no alerts store is wired). An agent with no creator agent (from the app, or the plugin's own Manager and Orchestrator) is outside the rule.

Detail (WP-107): each file stays within its budget, with 5 / 5 / 4 / 3 limits in `## RULES`, and says only what the plugin does not already say. The Worker **keeps its class list**: a Worker without the plugin's tools (Pi, Copilot) writes `BM-QUESTIONS` by hand, and an unknown `[class: …]` would file a security or scope question as `reversible-technical`. The Orchestrator reads `BM-EVENTS` and `BM-ANSWER` and points at its tools' own descriptions, plus four behaviour lines: `detail: "full"` only when a summary does not answer, check with `bm_repo` before acting, one note per owner decision or standing instruction, `bm_direct_worker` only for a correction. The fallback `BM-REPORT`, `BM-QUESTIONS` (with tags), `BM-ANSWERS` and `BM-REVIEW` blocks stay as the degraded mode (REQ-113 c). Where each rule of the old files went: [run note](../archive/operations/paseo-bm-roles-rewrite-20260929.md). `test/roles-content.test.ts` pins the budgets, each duty on the plugin text that carries it, the absence of the retired mechanisms, and that every `bm_…` name in `orchestrator.md` is a served tool.

Older agents (PRD §11 rule 3): every agent carries `bm.instructions=<first 12 hex of the SHA-256 of its role text>` (`instructions-label.ts`; the role file only, so Runtime facts and precedents never make an agent outdated) — the Manager from `createManager`, every other agent from `agent.created` through `paseo agent update --label` (skipped when the snapshot's system prompt lacks the role text; the load-time label scan never adds it). An agent whose label is missing or different is **outdated**: a throttled pass (at most once a minute, started by `inbox.alerts` and `agent.turn_started`, neither waiting for it) lists every agent and raises one `outdated-agent` alert per live outdated Manager, Worker or Reviewer — not the Orchestrator, which replaces itself (Orchestrator design §3.3), not an agent marked `bm.replacedBy`, and not one created in the last 5 minutes still without the label — and clears the rest; `agent.archived` clears that agent's alert at once. Workers and Reviewers are only flagged: they end with their request.

The role files teach paseo-bm's tools; the hand-written templates live in the Runtime facts of unbound agents only (`### Without paseo-bm's tools`), within this section's budgets ([base design §10](./paseo-bm.md)).

## Part B — Phase 2 MVP: calibrated autonomy (ADR-018; levels since ADR-025)

*The owner sets one of five levels per project ([ADR-025](../adr/ADR-025-autonomy-levels.md), [change-014](../archive/plans/paseo-bm-plan-autonomy-change-014-levels-and-flat-surface.md)); no class is the owner's by rule; the Orchestrator is the only predictor; an override is recorded and demotes nothing. [Change-007](../archive/plans/paseo-bm-plan-autonomy-change-007-phase2-start.md) records the re-check at the Phase 2 start.*

### B.1 Classes

`class` added to `Decision`: `reversible-technical, scope, preference, environment, dependency, release, data, security, cost`. The asker proposes it (`bm_report` question field; `bm_ask_owner` field). The plugin checks it against the declared effects — `push, publish, deploy` → `release`; `real-data, migration` → `data`; `security` → `security`; `cost` → `cost`; `dependency-install` → `dependency`; `network, outside-workspace` → `environment` — and keeps the riskier class on conflict (order: security, data, release, cost, dependency, environment, scope, preference, reversible-technical). A fallback incident is `environment`.

Detail (`shared/decisions.ts`, bead `bm-autonomy-phase2-t9lm.2`):
- **The map.** `DECISION_CLASSES` holds the nine in conflict order and `CLASS_OF_EFFECT` maps every effect; `none` and `commit` imply no class. `riskierClass`, `classOfEffects` (null when no effect implies a class) and `checkedClass(proposed, effects)` are pure. No class is the owner's by rule (ADR-025). The classes of `CONFIRM_EFFECTS` (release, data, security, cost) keep only the owner's in-place confirmation of their own tap (X-4).
- **The stored field.** `class` is an optional field of the record, and the store stays `version: 1`. Every new decision carries it. A Worker question (`decision-materialiser.ts`) and an Orchestrator decision (`bm_ask_owner`) keep the riskier of the proposal and the classes of their options' declared effects (their union, `declaredEffects`), or `reversible-technical` with neither. A fallback incident is `environment`. Opening is keyed by id, so reading a turn again never changes a stored class.
- **Reading it.** Readers go through `decisionClassOf`, which checks the stored class again against the effects. A decision stored before classes reads as `environment` when it is a fallback incident (`f:`), else as its effects' class, else as `reversible-technical`.
- **Proposing it.** The Worker gives `bm_report`'s optional `class` per question, written as `[class: <class>]` after `[subject: …]` and `[supersedes: …]`. `parseQuestions` reads it and ignores a value that is not one of the nine; the block check (`bm-format.ts`) already accepted any tag. The Orchestrator gives `bm_ask_owner`'s optional `class`, and the tool's answer names the class kept. worker.md asks for one per question (the nine, riskiest first, the riskier when unsure); orchestrator.md names the field.
- **Showing it.** Both faces of `bm_decisions` return each decision's `class`, and a decision card's Details has a `Class:` line.

### B.2 Policy and levels

`<data>/autonomy/policy.json` `{ version: 1, projects: { <workspaceId>: { <class>: owner | shadow | delegate } }, challenger: { <workspaceId>: boolean } }`; absent cell = `owner` (Q-102). Every class may be `delegate` (ADR-025). The owner sets a project as one of five **levels** (ADR-025), written as its nine cells and its prediction switch (`challenger`, §B.3). RPCs `autonomy.policy`, `autonomy.set-level { workspaceId, level, confirmed? }`, `autonomy.set { workspaceId, class, mode, confirmed? }`, `autonomy.reset { workspaceId }`, `autonomy.set-challenger { workspaceId, enabled }` (§B.3). Phase 4 adds an optional `boundary` map and `autonomy.set-boundary`, the action boundary's per-project switch (§D.2, change-010), which a level never touches.

Detail (bead `bm-autonomy-phase2-t9lm.3`; levels bead `bm-njdo.1`, change-014):
- **Levels** (`LEVELS`, `levelOf`, `levelsOf`, `withLevel`, `levelNeedsConfirmation` in `shared/autonomy.ts`, pure):

  | Level | Key | Name | `delegate` classes |
  |---|---|---|---|
  | 0 | `hands-on` | Hands-on | none |
  | 1 | `co-pilot` | Co-pilot | none |
  | 2 | `cruise` | Cruise | reversible-technical, preference, scope, environment, dependency |
  | 3 | `turbo` | Turbo | Cruise's, plus cost, release, data |
  | 4 | `full-auto` | Full auto | all nine |

  - **Write** (`withLevel`, one store write): the level's classes `delegate`, every other class `shadow` (levels 1–4) or `owner` (level 0), all nine written with the same `at`; the prediction switch on for levels 1–4, off for 0. Other projects and the action boundary stay as they are.
  - **Read** (`levelOf`): 0 when no class is `delegate` and the switch is off; n of 1–4 when the switch is on and exactly level n's classes are `delegate` (every other `owner` or `shadow`); otherwise `custom`. A project the policy does not name reads as 0.
  - `levelNeedsConfirmation`: Turbo and Full auto (3, 4).
- **Schema** (`shared/autonomy.ts`, pure). A cell is `{ mode: owner | shadow | delegate, at }`, `at` being when it was set; a `delegate` cell is the Orchestrator's (ADR-025 decision 5). `modeOf(policy, workspaceId, class)` reads an absent cell or project as `owner`; `canDelegate(class)` is true for every class. A cell is read on its own: an unknown class or mode is skipped alone (it reads `owner`) and dropped by the next write; so is a challenger entry that is not a boolean. A file of an older build is read past: a `delegate` cell's stored `predictor` is not read (a `recommended` one reads as the Orchestrator's), and `demotions` is ignored; both are dropped by the next write. The workspace id `__proto__` is refused.
- **Store** (`server/autonomy-store.ts`): the alerts store's file rules (0700 folder and 0600 file created by a write only, atomic replace, symlinks refused, no lock). A missing or corrupt file reads as the empty policy; a newer `version` reads as it too and is never written, not even by a reset. The challenger map is kept on every write. The cleanup button deletes `autonomy/`.
- **RPCs** (`server/autonomy-rpc.ts`; contracts in `shared/contracts/autonomy.ts`):
  - `autonomy.policy { workspaceId? }` → `{ policy, levels }`, the whole policy or one project's, with `levels` mapping each project it names to its level (0–4 or `custom`); reads only. No usable data folder or an unreadable store reads as the empty policy (every cell `owner`, the safe side), with one log line. `readAutonomyPolicy` is the same read for the plugin's own readers.
  - `autonomy.set-level { workspaceId, level: 0–4, confirmed? }` → `{ policy }` (the whole policy). Checked before the data folder is looked at: an unknown project or level → `E_AUTONOMY_INVALID`; Turbo or Full auto without `confirmed: true` → `E_AUTONOMY_NOT_CONFIRMED` ("Turbo lets the Orchestrator decide cost, release and data for you and needs the owner's confirmation; nothing was saved"). Then no usable data folder → `E_DATA_HOME_UNAVAILABLE`; a newer or unwritable store → `E_AUTONOMY_WRITE_FAILED`. Any other level needs no confirmation.
  - `autonomy.set { workspaceId, class, mode, confirmed? }` → `{ policy }`: one cell, for the prepared change of advice (§G.4) and the evaluation suite; no screen calls it. Strict input: an unknown project, class or mode, or a field it does not take (the `predictor` of builds before ADR-025) → `E_AUTONOMY_INVALID`; `delegate` without `confirmed: true` → `E_AUTONOMY_NOT_CONFIRMED`. Any class may be delegated. Cells set one by one read as **Custom** until a level is set. `E_AUTONOMY_OWNER_ONLY` is removed.
  - `autonomy.reset { workspaceId }` → `{ policy }`: that project's cells are removed in one write (an absent cell reads `owner`); other projects, the challenger and the boundary are untouched; a project with no cell writes nothing. No confirmation; no screen calls it (Hands-on is the way back).

### B.3 Shadow and the agreement ledger

For every decision answered by the owner: `prediction.recommended` (the option marked recommended, at open time) and, when the project's challenger is on (a level of 1 or more), `prediction.orchestrator` (the Orchestrator is sent the decision in a `BM-EVENTS` line and answers with `bm_predict { decisionId, optionKey, reason }`; since ADR-025 the owner sees it on the card as the Orchestrator's proposal). `plugin/shared/autonomy-ledger.ts` (pure) computes per project × class × predictor: agreement, count, first/last time, reversals. **Reversal** of a decision: re-asked with the same `subject` in the same request after it was settled; overridden from the digest; or a bead closed under it reopened with a reason citing it.

Detail (bead `bm-autonomy-phase2-t9lm.6`; change-007 C4):
- **On the record** (`shared/decisions.ts`, additive, the store stays `version: 1`):
  - `prediction { recommended: { optionKey } | null, orchestrator: { optionKey, reason, at } | null }`, each naming one of the decision's options. `openingPrediction` sets it where each kind opens — the materialiser (`q:`), `bm_ask_owner` (`o:`) and the fallback decisions (`f:`, `recommendedActionOf`). It is `recommended: null` when no option is recommended and `orchestrator: null` until `bm_predict` (the challenger's bead) writes it. Opening is keyed by id, so opening again changes nothing. A decision stored before predictions has none and is in no cell: nothing is read back from its options (change-007 §3.3).
  - `reversals[] { kind: re-asked | overridden | reopened, at, ref }`, at most 20, only on an answered decision. `ref` is the re-asking decision's id, the override's id or the reopened bead (`last-touched` when the reopen names none). Every reversal goes through `recordReversal`, which keeps one entry per kind and `ref` and refuses a decision never answered (`not-answered`).
  - `answer.by` is `owner | orchestrator | policy | precedent`. `orchestrator` stays readable for Phase 1's `bm_decide` answers. A `policy` answer is an option and names its `predictor`; a `precedent` answer names its `precedentId` and may be the owner's standing words. Either may carry the cell's `class`. `via: autopilot` is refused for `owner` and `precedent`. `precedent` is written at open (§B.6), `policy` by `bm_decide` (§B.5, `via: inbox`) and by the action boundary (§D.2).
- **Reversals detected.**
  - (1) In the materialiser: a new `q:` of the same request with the `subject` of an **answered** question reverses that answer, `ref` the new id. Re-asking an unsettled one is supersession only.
  - (3) At every recorded Manager or Worker turn (the materialiser, on the collector's `onRecorded`): each `br reopen` in the turn's shell evidence is read with its beads and its `--reason`/`-r`. A reason that cites `q:…` or `o:…`, or a bare `Qn` (of the request ids it names, else of the record's request), reverses that decision when it is answered and the reopen is not earlier than the answer. A reopen whose reason cites nothing is a review finding, the baseline's noise, and records nothing.
  - (2) The digest's Override records `overridden` through the same `recordReversal` (bead `t9lm.15`).
- **The ledger** (`shared/autonomy-ledger.ts`, pure, derived on demand) reads answered decisions only. Per `(workspaceId, class, predictor)` a cell holds:
  - `count`: owner answers with an option or words that carry that predictor's prediction;
  - `agreed`: the answers that chose the predicted option (own words never agree);
  - `unread`: chat answers the owner confirmed, whose content was never read — in neither `count` nor `agreed`;
  - `firstAt`/`lastAt`: over the counted answers;
  - `reversals`: decisions reversed at least once, and `reversalsByKind`, each decision once per kind.

  `delegated[]` counts answers `by: policy` (per predictor, `policyPredictorOf`: the Orchestrator, or what an older build stored) or `by: precedent`, with `overridden` (A-4) and `reversals`/`reversalsByKind` (A-5). An answer `by: orchestrator` is in neither figure (change-007 C4). Option: `workspaceId`. Every answer counts (no demotion, ADR-025).
- **Read-only RPC** `autonomy.ledger { workspaceId? }` → `{ cells, delegated }` (`server/autonomy-ledger-rpc.ts`). It gives numbers and times only, never a prediction. No usable data folder reads as none.
- **The Co-pilot proposal** (ADR-025, change-014 outcome 2). `decisions.list`, `decisions.get` and `decisions.confirm` return a decision through `ownerViewsOf` (`server/decision-override.ts`), which reads the policy once per call: an unsettled decision keeps `prediction.orchestrator { optionKey, reason }` while its project's prediction switch is on (a level of 1 or more, or a Custom project with the switch on) and comes without it otherwise; a settled one always shows it. An unreadable policy reads as every switch off. The card shows it as the Orchestrator's proposal (Dashboard design). `bm_decisions` hands out no prediction at all.

Detail for the challenger (bead `bm-autonomy-phase2-t9lm.7`; change-007 C1):
- **The switch.** `challenger[workspaceId]` in `policy.json`; absent or `false` is off (DQ-4). `autonomy.set-challenger { workspaceId, enabled }` → `{ policy }` (the whole policy) needs no confirmation (§B.9): it only records predictions. An unknown project or a value that is not a boolean → `E_AUTONOMY_INVALID`, before the data folder is looked at; then `E_DATA_HOME_UNAVAILABLE` and `E_AUTONOMY_WRITE_FAILED` as for `autonomy.set`. `false` is kept as the owner's answer rather than removed; a switch already in that state writes nothing; the project's cells are untouched, and `autonomy.reset` leaves the switch as it is.
- **The rule** (`predictionRefusalOf`, `shared/autonomy.ts`, pure). A prediction is asked and accepted for a decision the Orchestrator did not ask (`q:`, `f:`), still `open` (not waiting for a confirmation), of any class (ADR-025), in an `owner` or `shadow` cell, where that project's challenger is on, opened with its predictions recorded (a decision stored before them is in no cell) and not predicted by the Orchestrator yet. The rest of the project's policy does not matter. The event bus asks by it (§A.8), and `bm_predict` records by it.
- **`bm_predict { decisionId, optionKey, reason }`** (face in `shared/bm-tools.ts`, run by `server/orchestrator-decide-tools.ts`). The policy is read at the call, and the rule is checked again inside the store's write, so one decision holds one prediction. Refusals name why and write nothing: its own decision, an override or a held request, a settled or confirming one, a `delegate` cell, the challenger off, a second prediction, a decision stored before predictions, an option the decision does not have, an unknown id. It records `prediction.orchestrator { optionKey, reason (redacted, one line), at }` and nothing else: no answer, no delivery, no message to any agent, and no intervention (§G.3). Its answer tells the Orchestrator that the owner sees it on the decision as its proposal, with its reason, and to send nothing for it. A-7 counts it as its wake's action (evaluation design §4).
- **The switch in Settings.** No screen shows it: a level of 1 or more turns it on, Hands-on turns it off (§B.2).

### B.4 Delegation; no demotion

The owner delegates by choosing a level whenever they choose ([ADR-023](../adr/ADR-023-delegation-without-eligibility.md), [ADR-025](../adr/ADR-025-autonomy-levels.md)): agreement is shown as information in a project's Metrics, never required. **An override or a reversal is recorded, nothing more** (ADR-025 decision 4): it is stored with the decision (§B.3, §B.7) and counted in the agreement ledger, and it never changes a cell, a class or a level. The owner lowers the level by hand.

Detail (ADR-023, change-013; ADR-025, change-014): nothing checks agreement — neither `autonomy.set-level` nor `autonomy.set` — and there is no eligibility rule. The only confirmation is the level's (§B.2): Turbo and Full auto, in place, Cancel first. Nothing demotes: a reversal recorded by the materialiser or an override (§B.3, §B.7) changes nothing but the decision's record. A `demotions` map or an `autonomy-demoted` alert an older build left is skipped on read and dropped by the next write.

### B.5 Delegation

When a decision opens in a `delegate` cell, a `decision.opened` event asks the Orchestrator to decide it with `bm_decide { decisionId, optionKey, reason }`; it is delivered exactly as an owner answer would be (A.6). The Orchestrator is the only predictor (ADR-025 decision 5): nothing answers by the recommended option, and `resolveAtOpen` (`server/policy-resolve.ts`) applies precedents only (§B.6). Autopilot and **Allow…** are retired (§B.8).

Detail for the Orchestrator's predictor (bead `bm-autonomy-phase2-t9lm.11`; ADR-025, bead `bm-njdo.1`; REQ-121, REQ-123):
- **The rule** (`decideRefusalOf(policy, decision)`, `shared/autonomy.ts`, pure). The Orchestrator may decide a decision it did not ask — a Worker's question (`q:`) or a fallback incident (`f:`); its own `o:` stays the owner's whatever the cell (§B.9) — that is `open` and whose class (`decisionClassOf`), any class, is `delegate` in its project. Otherwise it names why: its own decision; an override or a held request; answered ("already answered by the owner / the Orchestrator / the policy / an owner precedent at …; the first answer stands"), needs confirmation, superseded (naming the replacement), withdrawn or expired; not delegated (an `owner` or `shadow` cell, another project's delegation). While the request stands finished-unverified, an option that acts on the finish is refused (§C.6). The event bus asks by it (`decision.opened`, `asks: "decision"`, §A.8) and `bm_decide` answers by it.
- **`bm_decide { decisionId, optionKey, reason }`** (face in `shared/bm-tools.ts`, run by `server/orchestrator-decide-tools.ts`). The policy is read at the call (unreadable = every class `owner`); the rule is checked on the stored decision, then the option must exist, then the rule is checked again inside the store's write. It stores `answerDecision { by: policy, via: inbox, optionKey, class, reason }`, the reason redacted and on one line (at most 300 characters): `via: inbox`, since nothing was typed in a chat. It grants the option's effects as the owner's choice would — a push, publish, deploy, migration, real data, security or cost effect included where its class is delegated (ADR-025). A refusal writes, delivers and logs nothing.
- **Delivered as an owner answer**, through the same `onSettled` (`settledByKind`): a `q:` answer reaches the Worker in the same `BM-DELIVERY answers` block as an owner answer, uncited (its provenance is shown to the owner, not to the Worker); an `f:` answer runs `fallback.act`. The tool's reply names the class, what the delivery did (sent, queued, failed; for an incident, the action ran or not), and asks the Orchestrator to send nothing more and tell the owner in one line. Its JSON: `decisionId`, `optionKey`, `class`, `answeredBy: "policy"`, `grant`, `delivery`. It never answers an `o:` decision, so it never produces a command, and a `q:` decision's grant authorises no command (`decisionId` takes only an `o:` decision).
- **Logged and measured.** The answer is an `answer` intervention (§G.3, `interventionOfDecision`: triggered by its wake's `decision.opened` when the wake carried it, else on the Orchestrator's own look), and its wake's action for A-7 (evaluation design §4). The ledger counts it in `delegated[]` under the Orchestrator, never as an owner agreement (§B.3). Re-asked, reopened or overridden, it is recorded as a reversal and demotes nothing (§B.4).
- **Shown to the owner.** The card reads **Decided**, "decided for you by the Orchestrator · <time>", with no answer buttons and no **Save as precedent**; Details has `Answered by: the Orchestrator (<class>)` and the reason. A `policy` answer an older build stored with the recommended predictor reads "decided for you by your earlier policy". A project's Requests timeline says `Decided for you by the Orchestrator: "<label>"`; the Inbox digest is §B.7's.
- **Not decided.** A decision the Orchestrator leaves stays open in the Inbox for the owner; nothing times out into an answer, and it is not told again.
- **Instructions** (`plugin/roles/orchestrator.md`): "Asked to decide (the owner delegated its class to you): choose as the owner would with `bm_decide`, your reason in one line."; the tools line names `bm_decide` "(a delegated decision)".

### B.6 Precedents

`<data>/autonomy/precedents.json`: `{ id, scope: <workspaceId> | all, subject, text, sourceDecisionId, createdAt, expiresAt (default 30 days), supersededBy }`. Created from an answered decision (**Save as precedent** on its card) or by the owner in Settings. At agent creation the hook appends `## Owner precedents` (active, the workspace's and global, newest 20) to the Manager's and the Worker's runtime facts. A decision opening with a `subject` equal to an active precedent's is resolved by it whatever its class (ADR-025), citing the precedent; where it cannot answer (below) it is shown on the card as a suggestion.

Detail (bead `bm-autonomy-phase2-t9lm.12`; injection and resolution are `t9lm.13` and `t9lm.14`):
- **Record** (`shared/precedents.ts`, pure). `id` is `p:<uuid>`; `subject` follows `SUBJECT_PATTERN`; `text` is at most 1,000 characters, an option label's cap rather than own words' 4,000, since it goes into agents' runtime facts; `sourceDecisionId` is null for one added in Settings.
  - `isActive(p, now)`: not superseded, and `expiresAt` later than now.
  - `activeFor(precedents, workspaceId, now)`: the workspace's and the global ones, newest first by `createdAt`.
  - The text an answered decision gives is its option's label, else the owner's words. A chat answer the owner confirmed has none, so the owner writes it.
- **Store** (`server/precedent-store.ts`): `{ version: 1, entries }`, with the policy store's file rules (0700 folder, 0600 file, atomic replace, no symlink, no lock).
  - An entry that does not validate, or repeats an id, is skipped alone and dropped by the next write. A newer `version` reads as none and is never written.
  - A save supersedes every active precedent of the same scope and subject in the same write (REQ-124 c). An expired one is left as it is. Supersession compares the text: an owner answer on the subject whose words differ from the precedent's — even one that means the same, such as an option label worded otherwise — ends it; a precedent saved with the option's own label avoids that.
  - **End** sets `expiresAt` to now; ending one already inactive writes nothing.
  - Every active precedent is kept, and the 500 newest inactive ones. The cleanup button deletes `autonomy/` with them.
- **RPCs** (`server/autonomy-rpc.ts`, beside the policy's). No agent tool saves or ends a precedent. Every refusal writes nothing.
  - `precedents.list { workspaceId? }` → `{ precedents }`: active only, newest first. No usable data folder, or an unreadable store, reads as none (one log line). `readActivePrecedents` is the same read for the plugin's own readers.
  - `precedents.save { decisionId?, scope, subject?, text?, expiresInDays? }` → `{ precedent, superseded }`, `expiresInDays` 1–365 (default 30).
    - With `decisionId`: the decision must be answered **by the owner** (not by the Orchestrator, the policy or a precedent) and carry a subject. The scope is `all` or the decision's own workspace; a given subject must be its own; a given text replaces the answer's.
    - Without it: `scope` (`all` or a workspace id), `subject` and `text`.
    - Checked in this order: the input alone → `E_PRECEDENT_INVALID`, before the data folder is looked at; no usable data folder → `E_DATA_HOME_UNAVAILABLE`; an unknown decision → `E_DECISION_NOT_FOUND`; a decision that cannot become a precedent → `E_PRECEDENT_INVALID`; a newer or unwritable store → `E_PRECEDENT_WRITE_FAILED`.
  - `precedents.end { id }` → `{ precedent }`. Not a precedent id → `E_PRECEDENT_INVALID`; unknown → `E_PRECEDENT_NOT_FOUND`.
- **The card** (`client/chat-card.tsx`; `precedentOfferView` in `chat-card-precedent.ts`). A decision the owner answered, with a subject, shows **Save as precedent…**, a secondary button; the Inbox's card is the same card.
  - It opens in place: what a precedent does, the answer to keep (prefilled, editable), **This project** / **All projects**, then Cancel first and **Save precedent** — one `precedents.save` with the decision's id.
  - Once saved, the card says for where and until when.
- **Settings → More → Precedents** (`client/settings-precedents.tsx`; model in `settings-autonomy-model.ts`). Read once when shown, and again after each change there or on a card.
  - Each active precedent, newest first: subject · project (by name, *All projects*, or *Unnamed project* — never an id), the answer, until when and the days left, and whether it came from your answer or was added in Settings.
  - **End** on each, with its confirmation in place, Cancel first.
  - **Add precedent…** opens a form: the Autonomy group's projects and *All projects* (the project shown is chosen first), the subject (checked as typed), the answer, Cancel first.
- **Injection** (bead `bm-autonomy-phase2-t9lm.13`; `server/role-instructions.ts` and `server/role-hook.ts`). `runtimeFactsText` adds `## Owner precedents` after `## Runtime facts`, for the Manager and the Worker only; the instructions are the role file, the runtime facts and the precedents, nothing else. One line per precedent, ``- `<subject>` — <text, on one line> (this project | all projects, until <YYYY-MM-DD>)``, newest first, at most 20 (`MAX_INJECTED_PRECEDENTS`); none → no heading.
  - The workspace: `manager.ensure` and a fallback Manager pass their own (`readInstructions(workspaceId)` → `currentInstructions(…, { workspaceId })`). The `agent.create` hook resolves it from `config.cwd`: the one live workspace `workspaces.list` gives that folder (`workspaceOfFolder`). None, several or an unreadable list → only the global precedents, never another project's.
  - Read with `readActivePrecedents`, in parallel with the mode and skill lookups and inside the hook's time budget. A read failure injects nothing, logs one line and never blocks the creation. A `BM-SETTINGS` notice (`childFactLine`) reads none.
  - The hook keeps a Manager prompt `manager.ensure` already built (its role text followed by Runtime facts, precedents or additions), so a store read a moment later never adds a second copy.
  - Only at creation: an existing agent keeps the precedents it started with. `bm.instructions` hashes the role file only, so precedents never make an agent outdated (§A.11).
  - The role files (§A.11): the Manager's brief carries the precedents that bear on the request in its **Context**; the Worker looks at its `## Owner precedents` before asking, follows and cites (by `subject`) one that answers the question, and asks what it leaves open, or what rule 1 guards, with that `subject`.

Resolution (bead `bm-autonomy-phase2-t9lm.14`; `server/precedent-resolve.ts`, the rules pure in `shared/precedents.ts`):
- **Which precedent** (`precedentFor`): an active one with the decision's `subject` that holds in its workspace — the workspace's own before a global one, the newest of each. A decision without a subject matches none.
- **At open, before any policy delegation** (`resolveByPrecedent`), where each kind opens: the materialiser (`q:`), `bm_ask_owner` (`o:`), a new fallback incident's listener (`f:`). `precedentResolutionOf` decides:
  - Any class is answered (ADR-025): `by: precedent`, `via: inbox`, its `precedentId`, the `reason` `The owner's precedent on "<subject>" [for all projects], saved <day>`, the `class`, at the time it is resolved. The answer is the option whose label is the precedent's text (whitespace aside), else the text as the owner's own words, with the grant an owner answer of that form gives. An `owner` or `shadow` cell does not stop it.
  - A fallback incident's decision (subject `fallback-<role>`) only with one of its options, since own words run no action, and only where its delivery can run at once: a new incident's listener hands the pass `fallback.act`; the start-up pass and the pass after an action do not, and leave it open.
  - The materialiser leaves to the owner a subject a precedent already answered in the same request: asked again, the same answer did not do. The re-ask is a reversal of that answer as any other (§B.3).
- **Delivered as an owner answer**, through `onSettled`. A `q:` answer's `BM-DELIVERY` cites it on one line per such question above the block (`Qn was answered by the owner's precedent <id> on "<subject>": it is the owner's standing answer.`); an `o:` answer's `BM-ANSWER` has a `precedent:` line; `bm_ask_owner` says it was answered at once and adds `answeredBy` and `precedentId` to its JSON. A `q:` resolved at open reaches the event bus answered, so no `decision.opened` goes out for it. A precedent's answer is not an Orchestrator intervention (§G.3) and is not logged as one.
- **The suggestion** on the card (`precedentSuggestionView` in `chat-card-precedent.ts`): while an open decision with a subject is shown, the card reads `precedents.list { workspaceId }` (one query per project). When an active precedent bears on it without having answered it — a fallback incident's words, a subject asked again, or a precedent saved after it opened — it shows "Precedent: <text> (saved <date>)" and **Use this answer**: its option as a tap on that option (a release, data, security or cost effect asks its confirmation first), or the own-words box filled with its text for the owner to send. **Use** is not offered while a confirmation or the own-words box is open, nor for a fallback incident's words. The Inbox's card is the same card.
- **Answered by a precedent**, the card says "answered by your precedent · <time>" (own words as "Your precedent: …"); Details has `Answered by: your precedent <id>` and the reason. Such an answer cannot be saved as a precedent in turn.
- **Supersession** (REQ-124 c; `supersedePrecedentsBy`, after `decisions.answer` and after the owner's answers the materialiser settles): the owner's answer with a text — an option's label or own words — on a decision with a subject supersedes the active precedents of that subject that hold in its workspace, in the order they apply, up to the first whose text it repeats; so the next decision meets the owner's latest word. `supersededBy` is then the decision's id: the field takes a precedent id or a decision id. A chat answer the owner confirmed has no text and supersedes nothing. The store's `supersede` writes once, and refuses a superseder that is neither id.

### B.7 Digest and override

Inbox → Decided for you: decisions answered `by: policy` or `by: precedent` since the owner last opened the Inbox, one line each with the reason; **Override** opens the decision as a new owner decision (`supersedes` the delegated one); the override is recorded only (ADR-025, §B.4).

Detail (bead `bm-autonomy-phase2-t9lm.15`):
- **Last look** (`server/inbox-seen-store.ts`, `<data>/inbox/seen.json` = `{ version: 1, seenAt, since }` on the JSON store factory). `inbox.seen {}` → `{ since, seenAt }`, called on each Inbox read while it is shown. A visit lasts while the Inbox is shown again within `INBOX_VISIT_GAP_MS` (5 min); within a visit `since` stays, and the next visit starts at the previous `seenAt` (never seen → `null`, everything listed). It writes at most every 30 s. No usable data folder → `E_DATA_HOME_UNAVAILABLE`; a newer or unwritable file → `E_INBOX_WRITE_FAILED`.
- **Digest.** `inbox.digest { since?, workspaceId? }` → `{ decisions, truncated }`: decisions answered `by: policy | precedent` after `since`, latest first, at most 100; reads only. It also answers `interventions` (the Orchestrator's intervention log entries after `since`, newest first, at most 100, with `interventionsTruncated`; each entry as stored plus `targetRole` — `manager`, `worker`, `owner` or null — and `reason`, redacted on read, one line, at most 300 characters: a command's `why`, an answer's reason or the advice question's first line). A log that cannot be read counts as empty, with one log line. The Inbox shows "Decided for you · N" (not counted in the tab), one line each — the question's first line → the answer, then "<project> · the Orchestrator" | "· your earlier policy" (a recommended-predictor answer of an older build) | "· your precedent" | "· your policy" (a held request the policy allowed), the reason and the time — ids under Details (change-014). Empty: "Nothing was decided for you since you last looked."; more than 100: "More was decided for you than the Inbox shows; each project's Requests tab has every decision." **Override** sits under the line on a phone and at its end on a wide screen; one press, no confirmation (it answers and sends nothing).
- **Override** (`decisions.override { id }` → `{ decision, overridden, created }`, `server/decision-override.ts`). In one synchronous write it records the reversal `overridden` on the delegated decision (which stays answered and delivered) and opens `r:<uuid>` with the same request, asker, question, subject and options, the answer's class and `supersedes` the delegated id; a second press returns the same override. It changes no cell, class or level (ADR-025 decision 4). An `r:` decision is never answered by a precedent or the policy (`resolveAtOpen` and `precedentResolutionOf` skip it) and is refused by `bm_decide` and `bm_predict`; its card offers no precedent and reads "You are overriding an answer made for you. Your answer goes to the same agent and replaces it." Refusals: open, owner-answered or a Phase 1 Orchestrator answer → `E_DECISION_NOT_DELEGATED`; superseded, withdrawn or expired → `E_DECISION_SETTLED`. The override keeps the original's recommended prediction for the ledger; when the owner's answer differs from a precedent's, it supersedes that precedent.
- **Delivery** (`server/override-delivery.ts`, the `override` kind of `settledByKind`), by the overridden decision's kind: a `q:` goes to the request's sole Worker as `BM-DELIVERY answers` with a correction line ("The owner changed the answer to Qn …") then `BM-ANSWERS`, queue kind `override:<id>`, with a Worker answer's guarantees (§A.6: `queued` → `sent` when a Worker turn record carries it or the queue no longer holds it; once per plugin run every undelivered one is sent again); an `o:` sends the chosen option's command on `authority: decision:r:…` through `command-send.ts` (counted by the loop guard, never refused), or a `BM-ANSWER` with an `overrides:` line; an `f:` runs `fallback.act` while its incident is still pending. An open override of a `q:` expires with its request's questions at the `finished` report (§A.3).
- **Known limitation:** the fallback handover still lists the delegated answer, not the owner's override.

### B.9 Decided when the plan was converted (2026-09-30)

Settled by Claude under the owner's delegation ([change-003](../archive/plans/paseo-bm-plan-autonomy-change-003-decisions-at-conversion.md)), re-checked at the Phase 2 start (change-007) and amended by ADR-023 and ADR-025. Code cites this section for these rules:

- **Classes.** The tag is `[class: <class>]` after a question's other tags. A decision with no proposed class and no effect that maps to one is `reversible-technical`; a stored decision without `class` reads the same way, a fallback incident's as `environment` (§B.1); the store stays `version: 1`.
- **Modes.** An absent cell reads as `owner` (REQ-121 b). `owner` and `shadow` behave alike when a decision opens: the owner decides and the predictions are recorded. `shadow` is what levels 1–4 set for the classes they do not delegate. The challenger, when the project's is on, predicts in both.
- **RPCs.** `autonomy.set-level` needs `confirmed: true` for Turbo and Full auto; `autonomy.set` needs it for `delegate`, any class; `autonomy.set-challenger` needs none (§B.2, §B.3). Nothing checks eligibility (ADR-023); a prepared change of advice (§G.4) may delegate one class.
- **Ledger.** Predictions and reversals are additive fields of the decision record; the ledger is derived on demand (§B.3). A reopen is a reversal only when its reason cites the decision id or its `Qn`.
- **Which decisions agents judge.** The Orchestrator predicts and decides only decisions it did not ask (`q:`, `f:`); its own `o:` stays the owner's whatever the cell. `decision.opened` is published per cell only (§A.8): an `owner` or `shadow` cell of a project whose challenger is on asks for a prediction (shown to the owner as the proposal, §B.3); a `delegate` cell asks for a decision (§B.5). The event scope that replaced Autopilot applies to `request.finished`, `request.stalled` and `worker.signal` only — every new cell reads `owner`, so a rule limited to scoped projects would never ask for a prediction. A `bm_predict` or `bm_decide` call is its wake's action for A-7, and A-1 counts a question `bm_decide` answered as answered by agents (Evaluation design §4).
- **Orchestrator commands without a decision** (replacing `authority: autopilot`). Authorised by the policy when every class its declared effects map to (§B.1, with `none` and `commit` counting as `reversible-technical`) is `delegate` for its project, carrying `authority: policy:<riskiest class>`; a release, data, security or cost effect is covered only where its class is delegated, otherwise it needs a grant. Otherwise only the owner's own word in the Orchestrator's chat (`authority: owner`) authorises it. Detail in §A.7; the backstop checks the text whatever the authority.
- **Precedents.** A decision without a `subject` cannot be saved. The resolving answer is the option whose label equals the precedent's text, else the text as the owner's words. A precedent is the owner's own standing answer, so it resolves a decision of any class, in an `owner` cell too (ADR-025). Injection resolves the workspace from `config.cwd`; when it cannot, only global precedents are injected (§B.6).
- **Digest and override.** The Inbox's last-opened time is kept in `<data>/inbox/seen.json`. An override is a new owner decision `r:<uuid>` with `supersedes: <delegated id>`, open until the owner answers it; the delegated answer already delivered is not recalled, the corrected answer follows it (§B.7).
- **A-4 and A-5.** Computed per delegated class in `eval-metrics.ts` from the overrides and the ledger's reversals of decisions answered `by: policy | precedent`. The owner's own reversal rate is the reference for A-5.
- **Retirement** (§B.8). The workflow assessment goes with the additional instructions; precedents, replay findings and proactive advice (§G.4) replace it (PRD Appendix B). Every runtime rule flag goes except `review.over-budget`, which feeds the stall pass.

The collector takes `exitCode` from the detail, else OpenCode's `metadata.exit`, else leaves it out. `status` is kept as a free string so a new Paseo status never breaks a record.
- **C.2 Detected checks** (`plugin/shared/evidence.ts`, pure). A check a report's `buildAndTests` names is labelled:
  - *detected*, when a shell evidence entry of the same request runs the same normalised command with a successful status after the request's last file edit. It is also detected as one segment of a chain joined only by `&&` whose run succeeded (change-008 C5);
  - *self-reported*, when only the report names it;
  - *unverified*, when the report says "not run" or nothing matches.

  A request none of whose shell entries carries a `status` (recorded before C.1) is *not checked*: neither detected nor unverified.
  - *As built* (bead `7gxw.3`): `verificationOf` → `{ checks, named[], files[], beads[], changedFiles }` (`CHECKS_VERDICTS`: `detected`, `self-reported`, `unverified`, `not-checked`; per claim `CLAIM_LABELS`). The request verdict, first match wins: shell entries exist and none carries `status` → `not-checked` (a request with no shell entry at all is judged as usual); the value is null, empty or says nothing ran → `unverified`; every named check detected → `detected`; else `self-reported`. A detected check is a successful call (`shellSucceeded`: an exit code decides, else only `status: completed`) begun after the last `file` entry of any of the request's records, whose `&&`-only chain (`andChainOf`) contains the check as consecutive segments; one call per `callId` (its latest state, placed where it began); quoted arguments are kept and redirections are not stripped. Records of every role count (a Reviewer's run detects a check). Files by path relative to the workspace (without the folder, a relative path matches an absolute one ending in it); beads by `brActions` close ids on a successful `&&`-only line, case-insensitive. For a `not-checked` request the per-claim labels are still computed; `checks` is read first. `buildAndTests` is stored with its backticks (`checksValueOrNull`, `shared/bm-report.ts`), and the "nothing ran" readers (`NOTHING_RAN`, `saysNothingRan`) ignore leading backticks. `shared/shell.ts` holds `normalisedCommand`, `shellFailureOf`, `shellSucceeded` and `andChainOf`. The Worker is told to name each check exactly as run, in backticks, with pass/fail, run after its last edit without pipes or redirections (`worker.md` "Proving a change" and its report template; the `bm_report` field description).

The Requests stage bar, the finished card and the `request.finished` event carry it, and a delegate (Part B) may not act on an unverified finish (§C.6). A request that is not checked is shown as before.
  - *As built* (bead `7gxw.4`): `requestFinishOf` (`shared/evidence.ts`) labels a request's latest report when it is `finished`: finished-unverified when its code changed and its named checks are `self-reported` or `unverified` (a `not-checked` request never is). It rides on the optional `traceSummarySchema.verification` (`traces.list` rows and `traces.get`; `traceStateSchema` unchanged). The Requests stage bar reads "Done — unverified" (warning), and the evidence lines label each check, file and bead (`client/verification-view.ts`); the finished card reads its request from the first page of `traces.list` (one query per workspace, 30 s) and shows "Finished — unverified". `request.finished` is also published for an unverified finish with nothing else left, carrying `unverified: true` (same dedupe key), its line telling the Orchestrator to check it with `bm_request` (which gained a `finish:` line). The delegation refusal of §C.6 reads the state at the call (`isFinishedUnverifiedNow`, `request-trace.ts`): in `bm_decide` (`decideRefusalOf(policy, decision, choice)`) and in `authorityOf` for `policy:<class>` commands (right after the pure `policyCoverOf`); an option or command acts on the finish when it declares or approves `commit` or has intent `release`. A store that cannot be read counts as unverified for delegation (left to the owner) and as not unverified for the event. The owner's own word and a grant are not refused.
- **C.4 Review lift.** `eval-metrics` adds, per tier and project: blocking findings per batch, findings acted on (a re-review with the finding fixed), and tokens per review; a project's Metrics show them. The review budget per tier is an owner setting in Settings → Coordination (§G.7), 2 / 2 / 4 by default. Only the owner changes it: in Settings, or by answering advice whose option carries the change (change-008 C6).
  - *As built* (bead `7gxw.5`, `eval-metrics/requests.ts` `reviewLiftOf`): `EvalMetrics.reviewLift` with `all`, `byTier` (Small, Medium, Large, unknown — a request's last reported tier) and `byWorkspace`: reviews per reviewed request; blocking findings per batch (every review of the batch; a batch with an unknown count is left out and counted apart); findings acted on — per batch reviewed more than once, the first review's blocking findings minus the last's, floored at 0, over the first reviews' findings, batches reviewed once counted apart; tokens per review (the Reviewer turns of a request over its reviews, only where every Reviewer turn has usage). Field figures: evaluation baseline report §6.6.

*Revised from the spike ([run note](../archive/operations/paseo-bm-action-boundary-spike-20260930.md)) and ADR-019's decision record, and re-checked at the Phase 4 start ([change-009](../archive/plans/paseo-bm-plan-autonomy-change-009-phase4-start.md)). **The boundary holds actions for Claude and Codex; every other provider keeps detection (§D.3). - **D.2 The boundary (Claude and Codex, in a project with it on).**
  - **The switch, per project** (change-010 C1–C5).

A Phase 2 or 3 file, a project with no entry and a malformed entry all read as **off**. `autonomy.reset` leaves it alone; deleting `autonomy/` turns it off everywhere.

    - *The confirmation says what changes.* Turning on: Workers and Reviewers created afterwards in the project run in the modes below; each held action waits for the owner unless the owner's grant to the Worker's question or a delegated class covers it; existing agents keep their mode. Turning off: agents created afterwards run in the usual modes under detection; those created while it was on keep their mode and are still answered.
    - *Read by the hook at creation:* the project of `cwd` (`workspaceOfFolder`, within the hook's 5 s budget) and its entry. **Off, or a project it cannot find:** the usual rule (`chooseModeId`, `runPostureOf`), and a creator's boundary mode (Runtime facts written while it was on) is moved back to the usual pick, so no agent asks with nobody answering. **On:** the table below.
  - **Modes, by the alias's base provider** (`aliasBases`, read in the hook's `prepare`; `role-mode.ts`, `role-hook.ts`):

    | Role | Claude | Codex |
    |---|---|---|
    | Worker | `default` | `auto` + `providerOptions { approval_policy: "untrusted", sandbox_mode: "danger-full-access", web_search: "disabled" }` — the sandbox is off so that an allowed release can run; the plugin is the barrier |
    | Reviewer | `default` | `auto` + `{ approval_policy: "untrusted", sandbox_mode: "workspace-write", web_search: "disabled" }` — a Reviewer never releases, so the sandbox stays as a second barrier |

    - *The creator's mode.* A Worker or Reviewer created in any other mode is moved to its boundary mode; only a mode hand-set on its profile wins (§D.4). A Manager created before Phase 4 still passes `bypassPermissions` from its Runtime facts.

    - *Runtime facts* (`role-instructions.ts`): the Manager is told the Worker mode and the Worker the Reviewer mode — the mode of their project's switch at their creation.
    - *The Codex gate passed* (Phase 4 live check): Paseo's MCP tools reach the plugin as permission requests and paseo-bm's pre-approved tools run without one, so the Codex column stands.
  - **Whether an agent runs under it.**
    - *The facts line:* each Worker's and Reviewer's Runtime facts carry `Action boundary: on` or `off — <why>`, written by the hook from what it applied. A missing line counts as off: the hook ran out of its 5 s lookup budget (no mode correction, no Codex options), or the plugin was down. A project with the switch off gives `off — the project's boundary is off`.
    - *The label:* `agent.created` labels `bm.boundary=on|off` from that line (`agent-labels.ts`, through `paseo-cli.ts`).
    - *Settings → Agents* says per role whether the boundary can apply (the provider, a hand-set mode) and points to Settings → Autonomy for the projects where it is on.
    - *The alert:* in a project whose boundary is on, a live Worker or Reviewer on Claude or Codex created after it was turned on (creation time ≥ the entry's `at`), whose `bm.instructions` is current, whose `bm.boundary` is not `on` and whose profile mode was not hand-set, raises one `boundary-off` Inbox alert. It clears when the agent is archived, replaced or gone, or when the project's switch is turned off. Turning the switch on raises nothing for agents already running. An agent with no instructions at all is already an `outdated-agent` alert (§A.11).
  - **Answering** (`plugin/server/action-boundary.ts`).
    - It registers `on("agent.permission_requested")` and acts only for agents on a `bm-worker*` or `bm-reviewer*` alias **that run under the boundary**: labelled `bm.boundary=on`, or, until the label is written, whose system prompt carries `Action boundary: on` (change-010 C5). Such an agent is still answered after its project's switch is turned off, so none is stranded. It answers through `context.paseo.agents.ref(id).respondToPermission({ requestId, response })`.
    - The answer is always a plain `{ behavior: "allow" }` (allow once) or `{ behavior: "deny", message }`: never Claude's `suggestions`, `updatedPermissions`, or OpenCode's `allow_always`.
    - Other agents' requests — a Worker or Reviewer created with the boundary off included — and a `kind` other than `tool` are left to Paseo's UI and keep the `permission-waiting` alert.
    - *One exception, outside the boundary's scope:* Claude's interactive box, `AskUserQuestion` (`name: "AskUserQuestion"`, `kind: "question"`, Paseo 0.10.2), is denied for every Manager, Worker and Reviewer — boundary on or off, whatever the base provider — with a plain `{ behavior: "deny", message }` naming the role's channel (`QUESTION_DENIED_MESSAGES`): the Manager asks in its reply, the Worker with `bm_questions` (or its report's questions), the Reviewer puts it in `notChecked`. The owner answers paseo-bm's questions on decision cards and in the chat, never in that box, so the role files no longer mention it (ADR-027, amended 2026-10-03). The restart scan denies one left pending. It is the only request the plugin answers for an agent not under the boundary; ADR-019's scope is otherwise unchanged.
    - `respond_to_permission`, `list_pending_permissions` and `set_agent_mode` stay in the Manager's and the Worker's `disabledTools` (`setup-roles.ts`); the Reviewer and the Orchestrator have no Paseo tools.
  - **Reading a request.**
    - *Claude* (the request carries no cwd; the agent's cwd is used): `Bash` → `detail.command`; `Edit` / `Write` / `NotebookEdit` → `detail.filePath`; `WebFetch` / `WebSearch` → network.
    - *Claude `mcp__*`:* Paseo's agent tools and paseo-bm's own are allowed by name, except `create_agent` whose `provider` is not a `bm-reviewer*` alias. That one is held with effect `security`, since it would start an agent outside the boundary. Another MCP server is unreadable.
    - *Codex:* `CodexBash` → `detail.command` + `detail.cwd`. `CodexFileChange` → the path of the pending timeline `tool_call` whose `callId` is the request's `metadata.itemId` (`timeline.refetch` tail; found 5 of 5 in 0–3 ms); not found → unreadable.
    - *Any other tool name* not in `ALLOWED_BY_NAME` (below) is unreadable.
    - *An unreadable request is held;* its Allow option declares `security`, so only the owner allows it, with a confirmation.
  - **Classes** (`shared/effectful-actions.ts`, one home with A-6 and the `danger` signal; each segment of `&&`, `;`, `|` and of `sh -c` / `bash -c` bodies, `shared/shell.ts`):
    - *release:* `git push`, `npm|pnpm|yarn publish`, `docker push`, the deploy CLIs (`kubectl apply|delete`, `terraform apply|destroy`, `helm install|upgrade|uninstall`, `vercel --prod`), `gh release create`. `npm|pnpm|yarn run <script>` (and `npm test` and similar) is classified by the script's body in the cwd's `package.json`; a script that cannot be read is unreadable.
    - *real-data / migration:* `DROP TABLE|DATABASE`, `TRUNCATE`, `DELETE FROM` without `WHERE`, a database CLI (`sqlite3`, `psql`, `mysql`, …) given a write statement, and migration runners.
    - *dependency-install:* `npm|pnpm|yarn add|install|i <package>`, `pip install <package>`, `brew install`, `cargo add|install`, `go get`, `gem install`. A bare `npm install` / `npm ci` from the lockfile is not held.
    - *network:* `curl`, `wget`, `ssh`, `scp`, `rsync` to a host, `nc`, and the provider's fetch tools. `git fetch|pull|clone` is not held.
    - *outside-workspace:* a write path (a file tool, `rm`, `mv`, `cp`, `>`, `>>`, `tee`, `mkdir`, `touch`, `ln`) that resolves outside the workspace folder.
    - *The scratch area* is the exception: the system temp roots (`/tmp`, `/private/tmp`, `/var/folders/*/*/T`, the daemon's `TMPDIR`), and a variable the same command assigned from `mktemp`.     - *The limit:* only the literal command is classified. What a script does inside is seen only by detection.

    - *Allowed at once:* no held effect.
    - *A live grant covers it:* the owner's answered `q:` or `o:` decision of the same request whose grant holds the effect (one use, 60 minutes, `GRANT_TTL_MS`). It is allowed and the grant spent (`useGrant`).
    - *A `delegate` cell covers it:* every held effect's class is `delegate` in the project — any class since ADR-025, so at Turbo a push, a real-data write or a migration, and at Full auto a `security` finding too (`policyCoverOf`, `server/action-boundary.ts`). It is allowed and stored as an `h:` decision answered at open `by: policy` (its class, no predictor), so Inbox → Decided for you shows it as "your policy (<class>)"; nothing is delivered. An unreadable request is never covered by the policy, and a grant never covers an unreadable or `security` finding.
    - *Otherwise it is held.* The request is left pending and becomes the decision `h:<agentId>:<requestId>`:
      - *kind:* a kind of its own in `decisionKindOf` / `deliveryKindOf`;
      - *record:* asked by `plugin` for the agent; class from the held effects (§B.1); subject `held-<class>`; the question names the masked command or path; its request is the agent's `bm.requestId` (a Reviewer's is its Worker's);
      - *options:* `allow` (the held effects, `permission { agentId, requestId, allow: true }`) and `deny` (`none`, `allow: false`); none recommended.
    - *What never answers it:* a precedent, or the Orchestrator (no prediction is recorded). It raises no `decision.opened`, and `bm_decide` and `bm_predict` refuse it.
    - *In the Inbox:* it replaces the `permission-waiting` alert for that request. Allow on release, data or security needs the in-place confirmation (X-4, `confirmed: true`). The `permission` delivery answers the request exactly once: a second answer is `E_DECISION_SETTLED`, and a re-delivery after a reload, or a request already resolved, answers nothing.
    - *In the Worker's chat* Paseo shows its own prompt; paseo-bm draws no card there.
    - *Answered elsewhere* (`agent.permission_resolved`): an allow — in Paseo's UI or `paseo permit` — records the decision answered `by: owner`, `via: paseo`, its grant spent at once. A deny or an interrupted turn withdraws it.
    - *When it ends:* a finished report never expires it. A Worker labelled `bm.replacedBy` has its open `h:` decisions withdrawn and its pending requests denied ("You were replaced").
  - **One Inbox item per action.** The live watch raises no `permission-waiting` alert for a held request. It raises `danger` only for an effectful action that no grant of its request covered before it ran.
  - **A-6.** `grantsOf` (`eval-metrics/scope.ts`) counts an owner-answered `h:` Allow as a grant of its request. The replay adds the held decisions per finished request (allowed, denied, withdrawn, open, the owner's wait), and splits A-6, the held figures and the estimate by boundary on / off / unknown per request, from the `bm.boundary` label of the request's Worker as the store records it (change-010 C9).
  - **Restart.**
    - Events are not replayed. At the first Paseo handle after the plugin starts — a hook, an RPC or the watch pass — the plugin scans `paseo.agents.list()` for the `pendingPermissions` of Workers and Reviewers running under the boundary and classifies each as if just raised; opening is idempotent by id.
    - While the plugin is down, requests wait in Paseo's UI for the owner (measured). An agent created meanwhile has no instructions and is flagged `outdated-agent`.
  - **Budget.** The added latency per allowed call is the plugin's classification plus the measured path (about 100–200 ms). The classification is synchronous except for the Codex file-change lookup.
  - **Field estimate.** The replay runs the classifier over the field's shell evidence (read-only, numbers only), after each request's grants and the scratch rule, and reports the held requests per finished request by class and as unreadable.
    - *At the Phase 4 start* (bead `loga.3`, read-only replay of the whole field store): 24.1 held and 18.8 unreadable per finished request, 6.9 unreadable without package scripts — mostly writes to a scratch variable set in an earlier call (`$S/…`) — against a bound of 0.2, plus about 3.4 environment holds (network, outside the workspace). Hence the switch per project, off by default (§D.5), and the Worker's literal scratch folder (change-010 C7).
    - *The gate* (change-010 C8): it is measured again in the combined field period over the projects with the boundary on (their held decisions, by class and as unreadable), and reported at the Phase 4 exit with the owner's decision on whether to recommend the boundary more widely. **0.2 unreadable per finished request stays the threshold for that recommendation.** The environment holds are reported beside it, with the part a grant or a `delegate` cell covered. ## Part G — Coordination control: measurement and advice (Phase 2), compaction and handoff (Phase 3) (ADR-021)

The owner's decisions are ADR-021's, with the field figures behind them (the Worker spends 93 % of the tokens; the heaviest 10 % of requests use 50 % of the Worker's). G.1–G.4 are Phase 2 (REQ-126–128), G.5–G.8 Phase 3 (REQ-134–136).

*Re-checked at the phase starts ([change-007](../archive/plans/paseo-bm-plan-autonomy-change-007-phase2-start.md), [change-008](../archive/plans/paseo-bm-plan-autonomy-change-008-phase3-start.md)); G.7's compaction and handoff defaults were derived at the Phase 3 start from the field data then available (evaluation baseline report §6).*

### G.1 The loop and the ladder

**The loop.**
- Code observes (trace records, reports, decisions, alerts, tokens) and detects (a threshold or an event). Only then is the Orchestrator woken (§A.8's rule: only a judgement wakes it).
- The Orchestrator diagnoses with its bounded read tools and picks the lightest intervention that will do.
- Code records the intervention with its expected outcome (G.3) and checks it after a window.

**The ladder**, lightest first:

| # | Intervention | How |
|---|---|---|
| 1 | Advise the Manager | a note, no command |
| 2 | Correct the Worker | a command, the Manager copied |
| 3 | Change the structure: compaction, handoff, a re-plan | a handoff always goes through the Manager |
| 4 | Stop | `interrupt` on a danger line |
| 5 | The owner | a decision |

**Who deals with the owner.** The Manager stays the owner's contact and the keeper of the request's context (PRD Q-100). The Orchestrator reaches the owner only through decisions and its own chat.

**What the Orchestrator never does:**
- skip or shorten a review or a check;
- waive a blocking finding;
- change what the owner asked;
- create, archive or delete an agent;
- read whole transcripts routinely.

### G.2 Measurement (Phase 2, REQ-126)

**Recorded** (as built, bead `t9lm.21`; every field additive, trace `v` unchanged, absent = unknown, never zero).

A value that is not a finite count is not kept, and a sum over turns never carries them. **Claude, Codex and OpenCode all report both, at every turn end**, compaction turns included (AGENTS.md, *Verified facts*; [run note](../archive/operations/paseo-bm-context-fields-run-20260930.md)).

Every provider first shows a `loading` item, and the timeline keeps both, so a `loading` item alone is no compaction. A Codex `/compact` runs as a turn of its own (`autonomous-…`) with no user message.

### G.3 The intervention log and outcomes (Phase 2, REQ-127)

**The store** (as built, bead `t9lm.22`: `plugin/server/intervention-store.ts`, shape in `plugin/shared/interventions.ts`). `<data>/orchestrator/interventions.json` = `{ version: 1, entries: [...] }`, oldest first, with the store rules of §A.8: the folder `0700` created only by a write, the file `0600` replaced atomically, symlinks refused, a missing or corrupt file read as empty, an entry that does not validate skipped on its own and dropped by the next write, a file of a newer version read as empty and never written; the newest 2,000 kept. The cleanup deletes it with `orchestrator/`. Ids, times and enums only. Each entry: `{ id, kind, workspaceId, requestId, targetAgentId, trigger, expected, windowMs, at, outcome: pending | met | missed | unknown, checkedAt }`, plus what its check reads when the kind has it: `decisionId` (`answer`, `advice`), `alertKey` (the stall of an `unblock`; the `stuck`, `permission-waiting` or `danger` alert of a `correct`) and `signal` (the Worker signal of a `correct` or `stop`).

- `trigger`: `decision.opened`, `request.stalled`, `worker.signal`, `advice.due` (the event of the wake), `owner` (the owner's word in the Orchestrator's chat), or `orchestrator` (no event of its wake behind it).
- `expected`: `worker-resumes`, `stall-clears`, `signal-clears-or-checks-pass`, `turn-ends`, `tokens-per-turn-down`, `successor-progresses`, `owner-answers` — one per kind.
- Recording never holds back or fails the intervention: a store failure is one log line.

**Kinds**, each with its expected outcome and window:

| Kind | Recorded from | Met when | Window |
|---|---|---|---|
| `answer` | `bm_decide` | the Worker resumes | 10 min |
| `unblock` | a command on a `request.stalled` event | the stall alert clears | 15 min |
| `correct` | a command on a `worker.signal` | the signal clears, or the next report's checks pass | the next report, at most 60 min |
| `stop` | an interrupt | the turn ends | 2 min |
| `compact` | `bm_compact` (G.5) | tokens per turn over the next three turns ≤ 60 % of the three before | three turns, at most 60 min |
| `handoff` | `bm_handoff` (G.6) | the successor's tokens per turn ≤ 50 % of the predecessor's last three, and the successor reports progress | 60 min |
| `advice` | G.4 | the owner answered the advice decision | 7 days |

**Which event a command answers** (as built). The event bus keeps the events of each Orchestrator wake in memory from its `BM-EVENTS` delivery to the end of that turn, beside the wake record (`wakeEventsOf`). A command `bm_send_command` or `bm_direct_worker` delivers in that turn is logged against them, after delivery:

- an `interrupt` is a `stop` (trigger the Worker's `worker.signal` when the wake carried one, else `owner` or `orchestrator`);
- else a `request.stalled` of the command's request is an `unblock` (a Worker's command without a request takes the Worker's);
- else a `worker.signal` of the Worker it went to is a `correct`;
- else, on the owner's word in the chat (authority `owner`), a `correct` with trigger `owner`; otherwise nothing is logged.

Every `bm_decide` answer is an `answer` to the Worker that asked, with trigger `decision.opened` when the wake carried that decision, else `orchestrator`. A reload forgets the events of the running wake: its commands then log only as the owner's. An `unblock`, `correct` or `stop` entry carries the `commandId` of the command it logs — its id in the commands store (`proposals.json`) — as an optional field; the file stays `version: 1`. A prepared command delivered on a decision's answer logs no intervention.

**The check** (as built). A pass on `agent.turn_ended`, throttled like the outdated-agents pass (once a minute), judges each pending entry from the stores. It runs at each turn end the collector records (its `onRecorded`), so it adds no lifecycle hook of its own and finds that turn's record in the store. It reads the decision store, the Inbox alerts and the trace records. It settles `met` as soon as the stores show the expected outcome within the window; `missed` once they show it did not come; `unknown` when the window is over and they cannot tell. An absence of evidence counts only a minute after the window ends, so a turn record written at its edge has landed.

- `answer`: met when the answer was sent to the Worker (`delivery.outcome: sent`), or one of its turns started, within the window. Missed when it was sent or resumed after the window, or the delivery is still `queued` or `failed`. Unknown with no delivery recorded and no turn, or the decision gone.
- `unblock`: met when the alert cleared within the window, or was cleared and raised afresh within it. Missed while it still holds after the window, or when it cleared late. Unknown when the alert is gone, or was raised afresh after the window.
- `correct`: met when the signal's alert cleared within the window, or the request's first report after the command, within the window, says its checks pass (`reportChecksOf` on `buildAndTests`). A signal without an alert (`failing`, `heavy`, `outside`) is settled by that report: missed when its checks fail, unknown when it names none or none came. A signal with an alert waits for the window's end: missed when the alert still holds or cleared late, or the report's checks failed.
- `stop`: met when the Worker's first turn from the interrupt on ended within the window; the turn it replaced does not count. Missed when that turn ended after the window, or none ended by then (a turn is recorded when it ends). Unknown without a Worker.
- `advice`: met when the owner answered the decision within the window. Missed when it is still open after the window, or was superseded, withdrawn or expired. Unknown when the decision is gone.
- `compact`, `handoff`: as §G.5 and §G.6 say.

**Where it shows.**
- **The Inbox's Decided for you** (as built, bead `t9lm.23`, §B.7): the interventions since the owner last looked are merged by time with the delegated decisions, newest first (a decision first on a tie). A line reads the kind and its target ("Unblocked the Worker"), the project · the Orchestrator, the reason — what set it off, then the Orchestrator's words when a store kept them — and the outcome, Pending, Met, Missed or Unknown, each in its own tone with its expectation. No Override; ids (intervention, command, request, agent, decision, alert) only under Details. An Orchestrator answer's outcome joins its decision's line instead of a second line. More than 100: "The Orchestrator intervened more often than the Inbox shows; a project's Metrics → Coordination counts every intervention." The heading count includes these lines; the Inbox tab's does not.
- A-12 per kind appears in a project's Metrics → Coordination (as built): one card per kind used in the window, met / (met + missed) with pending and unknown apart, against the 80 % target. `insights.summary` carries `interventions`, one row per kind. The replay reports `a12.byKind` and a headline row (evaluation design §4).
- A compaction or handoff kind below A-12's target is switched off until it recovers, with an Inbox alert. Another kind below it becomes an advice finding (G.4).

### G.4 Proactive advice (Phase 2, REQ-128; replaces the workflow assessment, §B.9)

**The trigger.**
- Each `finished` report the collector records counts toward its project.
- When the count since the last advice reaches `advice.everyFinished` (Settings, G.7; default 5; 0 = off), the event bus publishes `advice.due` for that project. It is a judgement wake.
- The owner can also ask in the Orchestrator's chat at any time.
- For the Phase 2 exit ("advice at least once per active project"), an **active project** is one with at least `advice.everyFinished` finished requests in the window (change-007).

**The tool.** `bm_findings { workspaceId }` is bounded (about 4,000 characters) and returns the project's findings, each with its figures:
- repeated question subjects without a precedent;
- blocked rounds per request;
- review rounds and blocking findings per tier;
- stall reasons;
- the heaviest requests and the compaction or handoff candidates of G.2;
- intervention kinds below target.

**The action.** For each finding worth acting on, the Orchestrator asks with `bm_ask_owner`, and one option carries a **prepared change** the plugin applies on the owner's answer:
- `precedent.save`
- `autonomy.set` (a delegable cell)
- `coordination.set` (a threshold or cadence of G.7)
- `review.budget`: a `coordination.set` on one of the review-budget keys of §G.7 (`review.smallBudget`, `review.mediumBudget`, `review.largeBudget`), not a separate kind (change-008 C6)

With no finding worth acting on, it writes a note; the wake still counts as acted on.

**Never** text appended to an agent's instructions (the retired assessment).

Detail (bead `bm-autonomy-phase2-t9lm.25`):
- **The count** (`server/advice-store.ts`, `<data>/orchestrator/advice.json` = `{ version: 1, entries: { <ws>: { counted[], at, dueAt } } }`, JSON store factory, deleted with `orchestrator/`). Only `finished` reports recorded in Manager turns count, each request once per advice cycle. The count resets in the write that makes advice due — also when no Orchestrator is open, so advice never piles up — so each count gives one event. `advice.due { workspaceId, finished, at }`, dedupe key `advice.due:<ws>@<time>`, is published for every project (not limited by the policy); with `advice.everyFinished` 0 nothing is counted, and an event queued before it was turned off is dropped at delivery. Its chat card reads "advice is due for a project".
- **The tool** (`server/orchestrator-findings.ts`; face in `shared/bm-tools.ts`). Reads only. A first line of guidance, then compact JSON, redacted, at most `FINDINGS_MAX_CHARS` (4,000; the last findings are dropped and counted in `omitted`): `{ workspaceId, window: { days: 30, since }, requests, settings: { advice.everyFinished, autonomy, challenger, activePrecedents }, findings: [...] }` — numbers, ids and short labels only, never message, question or answer text. Findings: `repeated-subject` (asked ≥ 2 times without a precedent, at most 5 → `precedent.save`), `agreement` (each class not delegated (any class, ADR-025) whose predictor has at least one counted answer in the project: `class`, `predictor`, `agreement`, `answers`, `reversals`, `mode`; most answers first, at most 3, `FINDINGS_PER_KIND.agreement` → `autonomy.set`; a plain figure with no threshold, change-013 C4), `intervention-below-target` (→ `coordination.set`), `blocked-rounds`, `reviews` per tier, `stalls` by the fixed reasons, `heavy-request` (at most 3), `compaction-candidates` (`estimate: true`). Window `FINDINGS_WINDOW_DAYS` = 30.
- **Prepared changes** (`shared/prepared-changes.ts`, `server/prepared-changes.ts`). A `bm_ask_owner` option may carry a `change` instead of a command, declaring `effects: ["none"]` and no command: `precedent.save { scope: project | all, subject, text, expiresInDays? }`, `autonomy.set { class, mode }` for the decision's own project (any class since ADR-025; `delegate` means the Orchestrator decides it; the project may then read Custom), `coordination.set { key, value }`. Checked when asked and again when applied (`preparedChangeCheckOf`; a change that would change nothing is refused when asked and writes nothing when applied). The plugin adds one line per change to the stored question ("Choosing a sets …"), so the owner reads exactly what a tap applies; the owner's tap is the confirmation. Applied through the same handlers as Settings (`precedents.save`, `autonomy.set`, `coordination.set`) in the delivery of the answered Orchestrator decision (`orchestrator-decisions.ts`); the `BM-ANSWER` gets a `change:` line saying whether it was applied (a failure is told to the Orchestrator and logged; the decision card does not show it).
- **Only the owner answers a decision that carries a change**: `answerDecision` refuses any other `by`; `resolveAtOpen` (policy and precedent) leaves it open and no precedent is suggested or superseded; `bm_decide` and `bm_predict` refuse it; `applyPreparedChange` requires `by: owner` on the stored answer. No Orchestrator tool writes `autonomy/` or `coordination/` (`test/orchestrator-boundary.test.ts`). Such decisions record no prediction (outside the agreement ledger) and never become precedents.
- **Intervention** (§G.3): a `bm_ask_owner` decision left open for the owner is logged as `advice` when it carries a change, or when it is about the whole project during that project's `advice.due` wake; trigger `advice.due`, else `owner`, else `orchestrator`; met when the owner answers within 7 days.
- **Role file:** the `advice.due` bullet — read the project's `bm_findings`, ask the owner with `bm_ask_owner` about each finding worth acting on with its change on an option, otherwise a note with `bm_note`; the owner may ask for advice at any time. A review budget is a `coordination.set` on its tier's review-budget key.

### G.5 Compaction (Phase 3, REQ-134)

**What the providers do** (bead `7gxw.8`, [run note](../archive/operations/paseo-bm-compaction-spike-20260930.md); AGENTS.md, *Verified facts*). A `/compact` sent as the app sends it starts a manual compaction on Claude, Codex and OpenCode: the timeline shows a `loading` then a `completed` `compaction` item with `trigger: manual`.
- **Claude honours a focus.** `/compact <focus>` keeps what the focus names; `preTokens` comes on Claude only, and the compaction's cost only in `totalCostUsd`.
- **Codex and OpenCode compact without a focus:** Paseo drops everything after `/compact`, so the plugin sends them a **bare `/compact`**, and the `BM-STATE` brief carries what must survive. Neither reports `totalCostUsd`. Codex compacts in a turn of its own (`autonomous-…`) with no user message; OpenCode's `/compact` turn repeats the counts of the turn before, and its result depends on the owner's own OpenCode configuration.
- **No provider needs the fallback** of REQ-134 c (a handoff for a Worker, nothing for a Manager).
- **Reading the context:** the figure reported right after a compaction understates the real one, so a threshold check reads the context at the **next** turn's end.
- **The message is the owner's to the collector unless the plugin says otherwise:** on all three the `/compact` is a `user_message` carrying `clientMessageId`, and a leading `/compact` cannot tell it apart, since the owner may type one too. The plugin therefore keeps a **send log** of what it sent (agent, time, text hash), and the collector classifies a matching message as the plugin's, never as the owner's words (A-6, the owner's texts, the owner's word in chat).

**What wakes the Orchestrator:** a `threshold.crossed` event of kind `compact` (§G.7, change-008 C1).

**The tool.** `bm_compact { agentId, reason }` (Orchestrator), in a tool module registered in `orchestrator-tools.ts`. The target is a Manager or a Worker of a project, never a Reviewer (short-lived) or the Orchestrator (it replaces itself). It is refused, writing nothing, when:
- compaction is off;
- the target is not a Manager or a Worker;
- the target is below its threshold (G.7);
- `compact.maxPerAgent` is reached. For a Worker, a handoff is suggested instead.

**The sequence.**
1. Wait for the target's next idle moment after a safe point: a Worker after a report; a Manager with no notice pending. Never inside a running turn (the notice queue).
2. The plugin sends `/compact` — with a focus from a fixed template on Claude (keep the request and the owner's words, the decisions taken, the plan and bead state, open review findings and files changed; drop tool output), bare on Codex and OpenCode — and records it in the send log.
3. It waits for the `compaction` item to complete.
4. It sends a **state brief** (`BM-STATE`, a plugin notice) built from the stores, so what matters is restored from artifacts rather than from the model's summary alone.

**As built** (bead `7gxw.10`). `bm_compact { agentId, reason }` lives in `server/orchestrator-coordination-tools.ts`; refused, writing nothing, in this order: compaction off; the target the Orchestrator, a Reviewer, not a paseo-bm Manager or Worker, archived or in no project; a compaction of it pending; `compact.maxPerAgent` reached (a Worker's refusal names `bm_handoff`); its provider cannot compact; its last measured turn below the threshold, or none measured since its last compaction. The provider comes from the alias's `extends`, else the turn's model id. Accepted: a `compact` intervention (trigger `threshold.crossed` when the wake carried that agent's event, else `owner` when the owner just spoke, else `orchestrator`), the compaction recorded with its reason masked, and a reply saying whether the `/compact` went now, is queued or waits. The runner (`server/compaction.ts`) sends at a safe point — a Worker's turn that just sent a `BM-REPORT`; a Manager's idle moment with no notice queued — as a one-item batch through the notice queue (Claude `/compact <COMPACT_FOCUS>`, Codex and OpenCode bare); a `/compact` held while the target turned busy is dropped after 60 s and sent again at the next safe point, never doubled; the next recorded turn with a completed `compaction` item (Codex: its own `autonomous-…` turn) triggers the `BM-STATE` brief. States `waiting | compacting | done | failed | dropped`; 60 min to find a safe point, 10 min for the compaction. **The send log** (`server/compaction-store.ts`, `<data>/orchestrator/compactions.json`, deleted with the folder): `{ agentId, at, hash, compactionId }` — the SHA-256 of the trimmed text, never the text — written just before the send; the collector records a would-be owner `user_message` of that agent with that hash, from 60 s before to 30 min after, as `origin: "agent"`, never parsed as a report. **The brief** (`BM-STATE`, a plugin notice) tells the agent to reply "noted" and end its turn: a Worker's holds its request id and the owner's first words, up to 3 later owner messages, up to 8 decisions with their answers and the report facts (phase, tier, files, beads, open findings, checks, `decided`, blockers); a Manager's its 5 newest requests (phase, Worker, open decisions, written `- req-…`) and the owner's 3 newest messages; masked, at most 6,000 characters. **The outcome** (§G.3): from the `/compact` being sent, at most 60 min, the mean tokens read over the next 3 measured turns against the 3 before — met at 60 % or less, else missed (the compaction's own turn and OpenCode's repeat turns left out; judged on 1–2 turns when the window ends early); unknown when the compaction never went out or no turn compares — so the A-12 guard (§G.7) can fire. The `threshold.crossed` event carries a `cycle` (the `/compact`s sent to that agent), is raised from `turnRecorded` (a turn holding a compaction is never judged), goes to every project and is dropped at delivery when compaction was turned off, the agent compacted, or a compaction was requested meanwhile. Work's live view (`live-timeline.ts`) checks typed messages against the send log with the collector's own matcher (`pluginSentBeside`) and leaves the plugin's `/compact` out of the owner's messages; `BM-STATE` is recognised by its marker and shown in chat as "State restored after compaction". Inbox → Decided for you reads a `compact` line's target role and masked reason from the compaction store (by its `interventionId`). The Manager handover drops what the send log says the plugin sent (bead `7gxw.11`).

### G.6 Handoff (Phase 3, REQ-135)

**What wakes the Orchestrator:** a `threshold.crossed` event of kind `handoff` (§G.7, change-008 C1).

**The tool.** `bm_handoff { workerId, reason }` (Orchestrator). It is refused, writing nothing, when:
- handoff is off;
- the target is not the Worker of an unfinished request;
- `handoff.maxPerRequest` is reached;
- the request is below its threshold.

When the Worker is not at a safe point, the request waits for the next one. Safe points are a bead closed with evidence (`bead-implemented`), `beads-done`, or a review verdict received.

**The sequence.**
1. **The outgoing Worker's note.** At the Worker's idle moment the plugin asks it for a short note: `bm_report` with `handoffNote`, at most 1,500 characters, saying what was tried and what is next. It waits for it within a bound (10 min) and goes on without it after.
2. **The brief.** The plugin builds it, bounded to about 6,000 characters, and keeps it at `<data>/handoffs/<id>.json`, written with the `data-files.ts` rules and masked with `redactText`; the cleanup deletes `handoffs/`. It extends the fallback Worker handover (`workerHandover`, `fallback-handover.ts`), which already gives the latest report, the review calls, the request's questions with their answers and the original request, built from the stores (change-008 C3). It holds:
   - the request and the owner's words;
   - the decisions taken;
   - the plan and doc paths;
   - the bead state (done, ready, blocked);
   - the last report (files, checks);
   - open review findings;
   - the branch and diff stat;
   - the note.
3. **The command to the Manager.** `BM-COMMAND`, carrying the brief's id: `intent: handoff`, `authority: coordination:handoff`, `effects: none`, `approved: none`, `to: manager` (change-008 C3).
   - *The authority* is the owner's Settings switch. None of the other authorities (a grant, the policy, the owner's word, §A.7) covers a handoff that ADR-021 lets the Orchestrator ask for on its own.
   - *Its checks:* the builder refuses `coordination:handoff` for any other intent, and the send refuses it while handoff is off. It goes through `command-send.ts` (counted by the loop guard), and its card reads "Coordination · handoff".

   The Manager:
   - creates the successor with `create_agent` (provider `bm-worker…`), the rendered brief as its first message and `bm.handoffFrom=<old>` among its labels, beside `bm.role` and `bm.requestId`. The creation hook adds instructions and runtime facts as for every Worker. It cannot set labels: Paseo 0.9.2's `before("agent.create")` sees `{ config, env }` only;
   - tells the outgoing Worker it is replaced. On `agent.created` the plugin checks the successor's label and labels that Worker `bm.replacedBy=<new>` through `paseo-cli.ts`, as the fallback switch does. Delivery, the materialiser and the chat peers already skip a replaced Worker. It stays idle and is never archived.
4. **The request continues.** It keeps its request id: the Requests timeline shows the handoff, and the Worker's reports continue.
5. **The successor proves again.** Its brief says to run the checks again before reporting anything done. Phase 3's detected evidence (C.2) holds it to that.

**Role text.**
- The Manager gets one bullet: executing a handoff.
- The Worker gets one bullet: the handoff note and working from a brief.
- Both within their budgets. The Manager's bullet names the `bm.handoffFrom` label.

**As built** (bead `7gxw.11`; `shared/handoff.ts`, `server/handoff.ts`, `server/handoff-store.ts`). `bm_handoff { workerId, reason }` (in `orchestrator-coordination-tools.ts`) is refused, writing nothing, when handoff is off; the target is not the live Worker of an unfinished request (not a Worker, archived, no project, no `bm.requestId`, already `bm.replacedBy`, or the request finished); the Worker has no live Manager; a handoff of the request is pending; `handoff.maxPerRequest` is reached; the request's tokens since it started (or since its last handoff) are below `handoff.requestTokens`; or the loop guard is full. Accepted: a `handoff` intervention and the runner's entry (states waiting → noting → briefed → commanded → done, or dropped / failed with an ending). **The note:** at the Worker's idle moment after a safe point (a successful `br close`, a `beads-done` / `bead-implemented` report, or a verdict of its own Reviewer) the plugin sends a `BM-HANDOFF` notice; the Worker answers with `bm_report`'s optional last field `handoffNote` (≤ 1,500 characters), which the collector records. With no note, the runner goes on at once when the note turn ends without one, else after 10 minutes at the next recorded turn. **The brief** (first line `BM-HANDOFF-BRIEF <id>`, at most 3,200 characters so it travels inside the 4,000-character command body; the stored file keeps the brief and the full note at `<data>/handoffs/<id>.json`, deleted by the cleanup) is built on `workerHandoverFacts` (extracted from `workerHandover`, whose output is unchanged): the owner's words, questions and decisions, plan and document paths, bead state, the last report and checks, open findings, branch and diff stat (read-only git) and the note, masked. **The command:** `intent: handoff` with `authority: coordination:handoff` only together, from the Orchestrator to the Manager, no copy, no effects, both fixed limits and no backstop (its body is the plugin's brief); refused while handoff is off; through `command-send.ts` (counted by the loop guard); sent when the Manager is idle with nothing queued, waiting up to 30 minutes; the card reads "Coordination · handoff". `bm_send_command`, `bm_direct_worker` and prepared commands cannot declare `handoff` (`DECLARED_COMMAND_INTENTS`). **The successor:** on `agent.created` (through `agent-labels.ts`'s existing hook), a Worker labelled `bm.handoffFrom` created by that Manager, in that workspace, for that request completes the handoff; the old Worker is labelled `bm.replacedBy` through `paseo-cli.ts` and never archived; the request keeps its id and the pairing check passes; a late successor (after 30 minutes) still completes it. **Proves again:** a check counts only if run after the request's last handoff (`evidence.ts`), which Work, the finished card, `request.finished` and the delegation refusal all read. **The event:** `threshold.crossed` kind `handoff`, key `threshold.crossed:handoff:<requestId>#<handoffs so far>` (only handoffs whose successor appeared count; tokens count again from the successor's creation), dropped at delivery when handoff is off, the request was handed over or has one pending, or it finished; its line names `bm_handoff`. **The outcome** (§G.3): from the successor's creation, met when its first three turns read at most 50 % of the old Worker's last three and it reports anything but `blocked` within 60 minutes; missed above 50 % or with no report; unknown with no successor or no turns to compare — so the A-12 guard can switch handoff off. The replacement Manager's handover drops a message the plugin's send log says it sent (`pluginSentBeside`). Work's timeline shows "Handed over to Worker 2 from Worker 1".

*After the Phase 3 live check* ([run note](../archive/operations/paseo-bm-phase3-live-check-20260930.md)): a Manager may pass the brief without its first line, so a successor is recognised by its `bm.handoffFrom` label (read into the agent facts, `handoffSuccessorsOf`), the `BM-HANDOFF-BRIEF` line being a second signal; "proves again" counts only checks run after that Worker's first recorded turn; `traces.get` carries an optional `handoffs: [{ agentId, from }]` that Work's timeline reads. The Manager's own message to the outgoing Worker may not arrive, so on the successor's `agent.created`, after `bm.replacedBy`, the plugin itself queues a `BM-REPLACED` notice to it (change nothing more, send no report, end the turn, stay idle); its chat card reads "Handed over to another Worker". A-7 counts a `compact` or `handoff` intervention recorded within a wake as its action.

When the request's Manager is bound with the creation tools (ADR-027), the plugin creates the successor itself and the handoff command only informs the Manager; an unbound Manager creates it as above ([base design §7.15](./paseo-bm.md)).

| `review.smallBudget`, `review.mediumBudget`, `review.largeBudget` | 3 | 2, 2, 4 review calls per request; bounds 2–8 (change-008 C6) |

*As built* (bead `7gxw.9`): the file is `{ version: 1, advice, compact: { enabled, managerTokensPerTurn, workerTokensPerTurn, contextShare, maxPerAgent }, handoff: { enabled, requestTokens, maxPerRequest }, guard: { compact, handoff } }`, each setting read on its own (a Phase 2 file reads the new ones as their defaults). Bounds (`COORDINATION_BOUNDS`, `coordinationRuleOf`; a value out of bounds → `E_COORDINATION_INVALID` with the key's rule): token thresholds 50,000–100,000,000 (request 10,000,000–1,000,000,000), whole; `contextShare` 0.1–0.9; `maxPerAgent` and `maxPerRequest` 1–5; switches true or false. `compact.enabled` is one switch, applied to `COMPACTION_PROVIDERS` (`compactionOnFor`). The crossing rules are pure (`shared/coordination.ts`): `compactCrossingOf(role, { coverage, tokensRead, contextShare })` — tokens read against the role's threshold only when the provider counts the whole turn, the context share on any turn, either crossing counts (reaching it is crossing), an unknown provider by its context share only; `handoffCrossingOf(requestTokensRead)`. Each returns `{ figure, value, threshold }` for `threshold.crossed`.

**Switched off under A-12** (`server/coordination-guard.ts`, wired after the intervention check). A mechanism that is on is judged over its newest 10 met-or-missed entries recorded since the owner last turned it on (`guard.<kind>.countsFrom`); fewer than 10 → no judgement. Below 80 % the store switches it off (`switchOff`, which can only switch off; `guard.<kind>.switchedOff = { at, met, checked }`) and one `coordination-off` Inbox alert is raised for all projects ("Only 6 of its last 10 compactions met their goal (target 8). Compaction stays off until you turn it on in Settings → Coordination."). Only the owner turns it back on — in Settings, or by answering advice that carries `coordination.set` — which sets `countsFrom` to now, clears `switchedOff` and ends the alert. Beads `7gxw.10` and `7gxw.11` check the outcome of `compact` and `handoff` entries, so the guard can fire. Settings → Coordination shows an Advice card and a Compaction and a Handoff card (status; Turn off at once, Turn on… after a confirmation with Cancel first; thresholds with − and + on a 1-1.2-1.5-2-2.5-3-4-5-6-8 ladder, the context share by 5 points; Save and Use the defaults). `coordination.set`, and a prepared `coordination.set`, accept all nine keys.

**The defaults as derived at the Phase 3 start** (evaluation baseline report §6).
- **The data:** the replay of the whole field store on 2026-09-30, 62 requests and 2,056 turns with usage, nearly all from builds before Phase 1.
- **The figures:** the p75 of tokens read per turn is 388,524 for the Manager and 5,713,582 for the Worker, and the request p80 is 150,553,952. The defaults are these, rounded to two significant figures; the earlier field alone gives the same within 1 %.
- **The candidates:** at those thresholds, compaction would have been proposed for 44 of 70 Workers (at a median third turn) and 6 of 15 Managers. Handoff would have been proposed for 13 requests, the heaviest fifth; their estimated saving is at most 34 % of the tokens they read.
- **Every saving is an upper bound.** A 1,500-token re-read is assumed after the crossing, and the call counts are lower bounds, since the field has no `toolCalls` yet.
- **`compact.contextShare`** is the design's 0.5: the field had no context figures when the defaults were derived.
- **Re-checked in the combined field period** (beads `t9lm.18`, `i8fc.6`). There, compaction and handoff lower the very distribution they are set from, so the re-check compares that window's figures with these before changing a default.

**Which figure a turn is judged by** (change-008 C2). A turn's tokens read are compared with its role's `compact.*TokensPerTurn` only when its provider counts the whole turn (Claude, `TOKEN_COVERAGE` `turn`). On Codex and OpenCode a turn reports its last call only: its tokens read are about its context, and the p75 of turn sums would never be reached. Such a turn is judged by `compact.contextShare` alone. Either figure crossing counts. `handoff.requestTokens` compares the request's tokens read since it started, or since its last handoff.

**The threshold event** (change-008 C1). Code detects a crossing and wakes the Orchestrator with `threshold.crossed { workspaceId, requestId, agentId, role, kind: compact | handoff, figure: tokensPerTurn | contextShare | requestTokens, value, threshold, at }`. It is raised from the collector's `onRecorded`, for a Manager's or a Worker's turn.
- **When `compact` is published:** while compaction is on for the agent's provider, the agent is below `compact.maxPerAgent` and no compaction of it is pending.
- **When `handoff` is published:** for a Worker's turn of an unfinished request, while handoff is on and the request is below `handoff.maxPerRequest`.
- **Scope:** every project, as `advice.due` is. The owner's Settings are its scope, not the autonomy policy.
- **Dropped at delivery** when the mechanism was turned off, the agent compacted, or the request was handed over or finished meanwhile.
- **One per cycle:** its dedupe key is `threshold.crossed:compact:<agentId>#<its compactions so far>` or `threshold.crossed:handoff:<requestId>#<its handoffs so far>`.
- **Its `BM-EVENTS` line** names `bm_compact` or `bm_handoff`.
- **A judgement wake.** The Orchestrator may leave it with a `bm_note`, which A-7 counts as acted on.
- **Its trigger** in the intervention log is `threshold.crossed`, added to `INTERVENTION_TRIGGERS` (the store stays `version: 1`).

**The review budget** (change-008 C6).
- **What they hold:** the three `review.*Budget` settings are the review calls per request of each tier, `REVIEW_BUDGET`'s numbers until the owner changes them.
- **Who reads them:** `review-budget.ts` (the budget notice and the stall pass's `review.over-budget`). A new Worker gets them in its `## Runtime facts`, and worker.md's budget line points there, within its budget. An existing Worker keeps the budget it started with.
- **Bounds:** never below one review and its re-review (§G.8).
- **Who changes them:** only the owner, in Settings → Coordination or by answering advice whose option carries `coordination.set` on one of these keys. That change is §G.4's `review.budget`; no separate prepared-change kind is built.

*As built* (bead `7gxw.12`): the file adds `review: { smallBudget, mediumBudget, largeBudget }` (whole 2–8, defaults 2 / 2 / 4, `REVIEW_BUDGET_KEYS`, `reviewBudgetOf`); `coordination.set` and a prepared `coordination.set` accept all twelve keys. `readReviewBudget` (`coordination-rpc.ts`, an unreadable store reads 2 / 2 / 4) is read by `review-budget.ts` (the Manager's notice and `review.over-budget`), the stall pass (once per pass) and `fallback-handover.ts`. A new Worker's `## Runtime facts` carry `Review calls per request: Small n, Medium n, Large n.` (read at creation; a Worker created earlier keeps its own), and `worker.md` points at them ("else 2 / 2 / 4"). Settings → Coordination → **Review budget** card (− and +, 2–8, Save, Use the defaults). Advice: the `bm_findings` `reviews` finding carries `budget`, `key` and `act: coordination.set`; `orchestrator.md` says a review budget is a `coordination.set` on its tier's key; applied only on the owner's own answer.

*Store and RPCs (bead `bm-autonomy-phase2-t9lm.24`):*
- **Schema** (`plugin/shared/coordination.ts`): `advice.everyFinished` is a whole number from 0 (off) to 50. Each setting is read on its own: missing or out of its bounds, it reads as its default and costs no other. Unknown keys are ignored and dropped by the next write. A newer `version` reads as the defaults and is never written.
- **Store** (`plugin/server/coordination-store.ts`): the alerts store's file rules (0700 folder and 0600 file created by a write only, atomic replace, symlinks refused). `readCoordinationSettings` is what the plugin's own readers use (the `advice.due` cadence): no usable data folder or an unreadable store reads as the defaults.
- **RPCs** (`plugin/shared/contracts/orchestrator.ts`, re-exported by `contracts.ts`; handlers and `readCoordinationSettings` in `plugin/server/coordination-rpc.ts`):
  - `coordination.settings {}` → `{ settings, defaults }`, reads only.
  - `coordination.set { key, value }` → `{ settings }`, one setting per call (the same `{ key, value }` a prepared change carries). An unknown key or a value out of its bounds → `E_COORDINATION_INVALID`, checked before the data folder is looked at; no usable data folder → `E_DATA_HOME_UNAVAILABLE`; a newer or unwritable store → `E_COORDINATION_WRITE_FAILED`. Every refusal writes nothing.
  - No agent tool sets these settings.
- **Settings → Coordination** (`plugin/client/settings-section.tsx`, `settings-model.ts`): the group after Autonomy, open by default. Its line is the cadence in words ("Advice after every 5 finished requests", "Advice off"). The advice card, titled "Orchestrator advice", has its meaning in one line, − and + within the bounds, Save (enabled only for a changed value) and "Use the default (5)". The Compaction, Handoff and Review budget cards follow it in the same group. **Reset coordination to defaults** (change-014) fills every card's draft with its default — each card's own Save sends it — and leaves the switches as they are.

### G.8 Guardrails and measures

**Quality comes first.** No review, check or blocking finding is traded for tokens or time. A-8's Phase 3 target on the heaviest requests holds only with no rise in:
- blocking findings per review batch;
- A-5;
- the finished-unverified share.

**Bounded.**
- Each intervention is logged (G.3), shown in the digest and measured (A-12).
- Settings switches compaction and handoff off at once.
- A release, data, security or cost effect needs a grant or a delegated class (§A.7), and its owner's tap a confirmation (§A.6).
- Agents belong to the owner.

**A-7 still holds** (< 20 % of wakes with no action): `advice.due` and the threshold events (`threshold.crossed`, §G.7) are judgement wakes, and the Orchestrator's own tokens are part of A-8.

**The Phase 3 exit's window and references** (change-008 C7; bead `bm-autonomy-phase3-7gxw.7`).
- **Window:** the combined field period's whole window (≥ 14 days from the final build's install, change-006/007), not its first 10 requests.
- **A-8's target** (−20 % on the heaviest 20 %, kept at the Phase 3 start: the replay's upper-bound estimate for the heaviest fifth is 34 %):
  - *The figure:* the p90 of Worker tokens read per request, which is the median of the heaviest fifth.
  - *The reference:* the same figure over the field before the final build's install, recorded at the install in the baseline report (§6.8).
  - *Why not the Phase 2 field:* under change-006 no Phase 2 build runs in the field without these mechanisms, so there would be no Phase 2 field figures to compare with.
  - *Minimum:* it needs ≥ 25 finished requests with usage (≥ 5 in the heaviest fifth); below that it is reported and the verdict reasoned, not passed.
- **The quality guardrails:**
  - blocking findings per review batch, against the same pre-install reference;
  - A-5, against the owner's own rate;
  - the finished-unverified share, which has no earlier value, so it is compared between the window's requests with a compaction or handoff and those without.
- **A-12** for `compact` and `handoff` is judged over every entry checked in the window. A kind with fewer than 10 checked entries is reported with its count, not called met.
