## Context

The first Orchestrator (ADR-013) assessed one request per click and let the plugin send `BM-NUDGE` hints into a running Manager's or Worker's chat. In the owner's test on a real daemon the nudge interrupted a Worker for a false positive and changed nothing, and the assessment answered a question the owner was not asking. What the owner needs is a **coordinator across projects**: something that notices when work stalls, knows what to tell the Manager, and can be asked how the Manager/Worker/Reviewer trio is working — while the owner keeps control of what is actually said to the agents.

Two things need an architecture decision: a **long-lived agent** that reads the work of every paseo-bm agent on the machine, and the plugin **delivering commands** to a Manager.

## Decision

1. **One Orchestrator agent per machine, created only on the owner's click.** It runs on the `bm-orchestrator` role (instructions, model, mode by the Reviewer's rule, no Paseo agent tools), in a workspace of its own rather than inside a project. The plugin creates it when the owner clicks **Open Orchestrator** and confirms; afterwards the same agent is reopened. The plugin never archives or deletes it (ADR-005).
2. **It sees; it does not act.** Its only window on the machine is a set of plugin tools that **read** paseo-bm data: requests and their state across workspaces, the signals of the rule catalogue, reports, and recent messages of paseo-bm's own agents (never another agent's). Content goes through the trace store's secret redaction. It has no Paseo agent tools, so it cannot message or create agents; editing files, beads or configuration is forbidden by its instructions and bounded by the Reviewer's mode rule, as for the Reviewer.
3. **Its one action is a proposal.** A `bm_propose_command` tool records a proposal — project, Manager, situation, command text, reason — in the plugin's own store. This extends ADR-010: the Orchestrator's endpoint may **read** plugin data and **record proposals**, and nothing more; it still never acts on an agent. The endpoint path carries a secret generated by the plugin, so a local process that does not know it cannot read the data or forge a proposal.
4. **Only the owner's click sends a command, and the command speaks with the owner's authority.** On **Approve & send** (after an optional edit) the plugin delivers the text to the Manager as the owner's own message — immediately if the Manager is idle, when its turn ends otherwise. The text may say anything the owner could say: answer a question, pick an option, redirect, stop part of the work. The owner can also type a command to a Manager, or a question to the Orchestrator, on the tab. Commands go to Managers only; the Manager directs its Worker (ADR-011).
5. **Stall watcher, behind a switch.** When the owner turns **Watch for stalled work** on (off by default), the plugin checks the trace store and the agent list at a fixed interval — no timeline read, no model call — for three situations: an unfinished request with no paseo-bm agent running for 5 minutes, a request waiting for the owner for 15 minutes, a request with review calls over budget or a broken report. Each situation of a request wakes the Orchestrator agent **once** (a `BM-STALL` notice to the Orchestrator only), if the agent exists; the situation is listed on the tab either way.
6. **Workflow assessment on click.** **Assess workflow** on a project sends the Orchestrator a request to assess that project's recent requests; it answers through the existing `bm_assessment` tool; the result is shown briefly and each recommendation is applied to a role's "Additional instructions" only by the owner's click.
7. **Removed from ADR-013:** the plugin no longer sends `BM-NUDGE` to anyone, no longer watches running Workers' timelines, and no longer creates an assessment agent per request.

## Consequences

- The owner has one place to see stalled work across projects and to unblock it with one click, and an advisor who has read every project.
- No message reaches a working agent without the owner's click: the risk of the first design (interrupting a Worker for a false positive) is gone. The cost is that a stall is only resolved when the owner looks; the tab and the Orchestrator's own chat are where they look.
- A long-lived agent exists once the owner opens it; each conversation, wake-up and assessment spends the owner's tokens on the provider they chose. With the watch switch on, each stall situation costs at most one wake-up.
- The Orchestrator reads redacted conversation content of **every** paseo-bm project, on one provider; the Open dialog says so.
- The plugin's localhost endpoint now serves reads of paseo-bm data; the per-run secret in its path keeps other local processes out.
- An approved command is indistinguishable, for the Manager, from the owner typing it — which is the intent ("full authority as the owner"), and why the click is mandatory.
- The Dashboard's "read-only" boundary has named exceptions — creating the Orchestrator agent, delivering an approved command, waking the Orchestrator — each behind a click or a switch, each with negative tests.
- ADR-013's `BM-NUDGE` sentences in the Manager's and Worker's role files are removed.

## Alternatives considered

- **Keep ADR-013 (nudges + per-request assessment)** — rejected by the owner after testing: it interrupted agents for false positives and did not help unblock stalled work.
- **Let the Orchestrator send commands itself (Paseo agent tools)** — rejected: the owner chose to approve every command; an agent holding `send_agent_prompt` could bypass the click.
- **Commands sent automatically for "safe" situations** — rejected by the owner (every command waits for the click).
- **One Orchestrator per workspace** — rejected by the owner: stalls must be seen across projects in one place, and one agent keeps cost and context in one conversation.
- **The plugin builds commands by rule, without an agent** — rejected: a useful command needs to understand the conversation (which options a question offers, what the user meant); rules only detect the stall.
- **Read tools return data through the timeline (as `bm_review`)** — not possible for reads: a read has to answer within the tool call. Recording proposals inside the call is accepted for the same reason; the path secret replaces ADR-010's "the endpoint does not know who calls" argument, since only the Orchestrator's configuration holds the secret.
